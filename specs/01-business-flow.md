## 1. 文档目的

本文档用于定义「食刻」一期的核心业务流程、用户操作路径、业务状态及关键规则。

本文档是后续数据模型、日程生成规则、页面交互和技术实现的业务依据。

### 1.1 一期业务目标

一期不是完整覆盖所有孕期及 0—36 月龄用户，而是通过两个具体场景验证产品核心价值：

**场景 A：孕 30 周左右的孕晚期用户**

帮助用户降低每日餐食决策成本，提供可执行、可替换、可调整的餐食日程。

**场景 B：2 岁左右幼儿的主要照护者**

帮助照护者降低幼儿日常餐食安排成本，结合家庭作息和饮食约束提供可执行的餐食日程。

### 1.2 核心业务闭环

```text
用户进入
   |
   v
创建用户档案
   |
   v
选择业务场景
   |
   +----------------------+
   |                      |
   v                      v
孕期档案                幼儿档案
   |                      |
   v                      v
阶段识别                阶段识别
   |                      |
   v                      v
补充必要信息            补充必要信息
   |                      |
   v                      v
生成孕期日程            生成幼儿日程
   |                      |
   +----------+-----------+
              |
              v
         查看每日任务
              |
              v
       完成 / 跳过 / 替换
              |
              v
         顺延 / 调整
              |
              v
         行为反馈记录
              |
              v
       后续日程动态调整
```

### 1.3 设计原则

1. 日程是帮助用户执行的默认方案，不是强制任务。
2. 用户可以完成、跳过、替换或调整任务。
3. 跳过和未完成是合法状态，不制造惩罚。
4. 安全规则优先于个性化偏好和用户手动操作。
5. 业务规则与内容数据分离，避免将业务判断写死在页面中。
6. 孕期和幼儿场景共享日程基础能力，但保留各自独立的业务规则。
7. 一期以单一主要照护者使用为主，不建设复杂家庭协作能力。
8. 不依赖 AI 直接生成未经审核的餐食推荐。

## 2. 一期业务范围

### 2.1 一期包含

| 业务模块         | 孕期场景                 | 幼儿场景     |
| ---------------- | ------------------------ | ------------ |
| 用户及档案       | 支持                     | 支持         |
| 阶段识别         | 孕周识别                 | 年龄阶段识别 |
| 基础信息维护     | 支持                     | 支持         |
| 餐食日程生成     | 支持                     | 支持         |
| 每日任务展示     | 支持                     | 支持         |
| 任务完成记录     | 支持                     | 支持         |
| 任务跳过         | 支持                     | 支持         |
| 餐食替换         | 支持                     | 支持         |
| 日程顺延         | 支持                     | 支持         |
| 过敏信息管理     | 根据实际需求记录相关约束 | 支持可选流程 |
| 新食物观察记录   | 不适用                   | 支持基础记录 |
| 基础行为数据采集 | 支持                     | 支持         |

### 2.2 一期不包含

以下能力不作为一期交付要求：

- 孕早期、孕中期的完整餐食内容体系。
- 所有孕晚期孕周的完整内容覆盖。
- 0—12 月龄完整喂养体系。
- 13—23 月龄完整餐食内容体系。
- 25—36 月龄完整餐食内容体系。
- 多成员家庭协作、权限分配和共同执行。
- 复杂营养计算及个体化医疗干预。
- AI 自动生成并直接发布餐食内容。
- 自动诊断食物过敏或判断医学上的过敏排除结果。
- 复杂 CMS 内容管理平台。

超出一期阶段覆盖范围时，不得使用未经审核的内容填充日程。

## 3. 全局业务流程

### 3.1 用户首次进入

```text
首次进入小程序
    |
    v
判断是否存在有效档案
    |
    +---- 是 ----> 进入已有档案对应的首页
    |
    +---- 否
           |
           v
       展示场景选择
           |
           +------------------+
           |                  |
           v                  v
         孕期                幼儿
           |                  |
           v                  v
       创建孕期档案        创建幼儿档案
           |                  |
           v                  v
       补充孕期信息        补充幼儿信息
           |                  |
           v                  v
       识别孕周            识别年龄阶段
           |                  |
           v                  v
       信息确认            信息确认
           |                  |
           +--------+---------+
                    |
                    v
               生成日程
                    |
                    v
                首页展示
```

### 3.2 档案管理

一期底层数据模型需要支持一个账号关联多个档案。

一期交互可以优先采用单个当前档案的简化体验，不要求实现复杂的档案切换和家庭成员管理。

档案至少包含：

- 档案 ID。
- 档案类型。
- 档案名称或展示标识。
- 核心日期信息。
- 当前阶段。
- 基础约束信息。
- 创建时间。
- 更新时间。
- 档案状态。

档案类型：

| 类型     | 标识        | 说明                  |
| -------- | ----------- | --------------------- |
| 孕期档案 | `pregnancy` | 孕妇相关信息          |
| 幼儿档案 | `child`     | 0—36 月龄幼儿相关信息 |

### 3.3 档案状态

建议统一采用以下档案状态：

| 状态     | 标识       | 说明                     |
| -------- | ---------- | ------------------------ |
| 初始化中 | `draft`    | 档案尚未完成必要信息填写 |
| 正常使用 | `active`   | 档案有效，可进入日程流程 |
| 暂停使用 | `paused`   | 用户主动暂停使用         |
| 已归档   | `archived` | 档案不再作为当前活跃档案 |

业务规则：

1. `draft` 状态不生成正式日程。
2. `active` 状态允许生成和查看日程。
3. `paused` 状态不继续自动生成新的日程。
4. `archived` 状态保留历史数据，不再生成新日程。
5. 档案状态变化不能直接删除历史执行记录。

## 4. 孕期场景业务流程

### 4.1 场景目标

针对孕 30 周左右的孕晚期用户，提供每日餐食日程及轻量执行管理。

一期重点解决：

- 每天不知道吃什么。
- 餐食安排缺乏规律。
- 食谱选择成本较高。
- 临时无法执行原有餐食计划。
- 希望根据个人情况调整餐食安排。

### 4.2 孕期档案创建

流程：

```text
选择孕期场景
    |
    v
填写孕期基础信息
    |
    +--> 预产期或用于识别孕周的日期信息
    |
    +--> 当前饮食偏好
    |
    +--> 已知饮食禁忌或约束
    |
    +--> 其他必要信息
    |
    v
系统计算当前孕周
    |
    v
判断是否属于一期支持范围
    |
    +---- 是 ----> 创建有效档案
    |
    +---- 否 ----> 展示阶段暂不支持说明
                    不生成未经审核的日程
```

说明：

- 日期字段及孕周计算口径需要在数据模型和规则 Spec 中进一步明确。
- 用户填写的孕期信息用于阶段识别，不代表医学诊断。
- 不应因为用户未填写非必要信息而阻断基础建档。

### 4.3 孕周识别与阶段判断

一期目标阶段为孕 30 周左右的孕晚期用户。

业务流程：

1. 根据用户提供的孕期日期信息计算当前孕周。
2. 根据配置的阶段规则识别当前孕期阶段。
3. 检查当前阶段是否存在已审核的餐食内容。
4. 存在可用内容时进入日程生成流程。
5. 不存在可用内容时展示阶段暂不支持说明。

阶段判断应由独立规则处理，不在页面中写死。

具体孕周边界、日期计算规则和支持范围，应在后续规则 Spec 中配置和确认。

### 4.4 孕期日程生成

一期采用每日执行、提前生成未来 7 天日程的方式。

流程：

```text
档案有效
    |
    v
识别当前孕周
    |
    v
读取个人饮食约束
    |
    v
获取对应阶段的内容候选
    |
    v
执行安全过滤
    |
    v
执行阶段及营养结构匹配
    |
    v
结合用户偏好筛选
    |
    v
生成未来 7 天日程
    |
    v
校验日程完整性
    |
    +---- 通过 ----> 保存并展示
    |
    +---- 不通过 --> 降级处理
                       不得放宽安全约束
```

日程生成规则：

1. 只使用已审核且处于有效状态的内容。
2. 只使用适用于当前阶段的内容。
3. 必须应用用户已记录的禁忌和安全约束。
4. 用户偏好只能影响候选排序，不得覆盖安全过滤。
5. 不得为了填满日程而引入未经审核的内容。
6. 如果某个餐次没有合适候选，应允许展示结构建议或暂缺状态。
7. 日程生成结果需要记录规则版本和内容版本，便于追溯。

具体营养结构、餐次配置、候选排序及安全判断由后续 `04-schedule-rules.md` 或对应规则文档定义。

### 4.5 孕期日程执行

用户进入首页后，查看当天餐食任务。

```text
进入孕期首页
    |
    v
展示当天餐食日程
    |
    v
选择某个餐食任务
    |
    +-------------------+
    |         |         |
    v         v         v
   完成      替换       跳过
    |         |         |
    v         v         v
记录完成   进入替换流程  记录跳过
    |         |         |
    |         v         |
    |      安全过滤     |
    |         |         |
    |         v         |
    |      更新任务     |
    |         |         |
    +---------+---------+
              |
              v
          更新日程状态
```

#### 4.5.1 完成任务

用户主动确认完成后：

- 更新任务状态为 `completed`。
- 记录完成时间。
- 保留原始推荐内容。
- 记录实际执行内容（如果与推荐不同）。
- 更新相关统计数据。

不能仅凭用户打开页面或查看食谱就认定任务完成。

#### 4.5.2 跳过任务

用户可以跳过当前餐食任务。

规则：

- 更新任务状态为 `skipped`。
- 允许记录跳过原因，但不强制填写。
- 不影响其他任务执行。
- 不产生惩罚或负面评价。
- 不应自动推断用户存在营养不足或健康异常。

#### 4.5.3 替换任务

用户可以对不适合当前情况的餐食进行替换。

流程：

1. 用户选择替换。
2. 系统获取同一任务适用的候选内容。
3. 执行安全约束过滤。
4. 展示可替换内容。
5. 用户选择替代内容。
6. 保存替换结果。
7. 更新任务关联内容。

规则：

- 已知禁忌内容不得进入替换候选。
- 用户手动操作不能绕过安全规则。
- 找不到合适候选时应明确提示，不得强行推荐。
- 替换记录应保留原内容及替换后内容。

### 4.6 孕期特殊约束处理

用户可能存在饮食偏好、已知食物禁忌或需要专业管理的特殊情况。

处理原则：

1. 普通偏好可以参与候选排序。
2. 已知禁忌必须进入安全过滤。
3. 特殊健康状况需要经过专业审核的规则支持。
4. 未配置、未审核的特殊状况规则不能自动推断。
5. 如果当前情况超出产品已审核的推荐范围，应暂停相关自动推荐并提示寻求专业意见。

产品提供的是日常餐食管理辅助，不提供疾病诊断、治疗方案或医疗替代建议。

## 5. 幼儿场景业务流程

### 5.1 场景目标

针对 2 岁左右幼儿的主要照护者，提供家庭餐食及日常喂养安排。

一期重点解决：

- 每天不知道给孩子准备什么。
- 幼儿餐食安排缺乏规律。
- 家庭餐与幼儿餐之间难以协调。
- 不清楚如何处理已知过敏食物。
- 新食物尝试过程缺少记录。
- 临时无法执行原有餐食安排。

### 5.2 幼儿档案创建

流程：

```text
选择幼儿场景
    |
    v
填写幼儿基础信息
    |
    +--> 出生日期
    |
    +--> 饮食习惯及偏好
    |
    +--> 已知食物过敏信息（可跳过）
    |
    +--> 其他必要信息
    |
    v
识别幼儿年龄阶段
    |
    v
判断是否属于一期支持范围
    |
    +---- 是 ----> 创建有效档案
    |
    +---- 否 ----> 展示阶段暂不支持说明
                    不生成未经审核的日程
```

基础规则：

1. 出生日期用于计算幼儿月龄。
2. 用户可以选择暂时跳过过敏信息设置。
3. 过敏信息不是完成建档的强制条件。
4. 不得将用户未填写过敏信息解释为医学上排除所有过敏。
5. 档案完成后进入日程生成流程。

### 5.3 幼儿年龄识别

一期重点支持 2 岁左右幼儿。

流程：

1. 根据出生日期计算当前年龄。
2. 识别对应年龄阶段。
3. 检查是否存在适用的审核内容。
4. 如果存在，允许生成日程。
5. 如果不存在，展示暂不支持说明。

注意：

- “2 岁左右”是一期目标用户描述，不应未经确认就转换为固定的月龄区间。
- 具体阶段边界需要由产品和专业审核共同确认。
- 月龄计算应考虑实际日期和跨月情况，避免简单使用天数除以 30。

### 5.4 过敏信息管理

过敏信息是可选流程。

用户可以在建档时设置，也可以在后续使用过程中随时补充或修改。

#### 5.4.1 过敏状态

| 状态               | 标识                | 业务含义                                               |
| ------------------ | ------------------- | ------------------------------------------------------ |
| 目前无已知食物过敏 | `none_known`        | 用户声明目前没有已知食物过敏，不代表医学上排除所有过敏 |
| 已知存在过敏       | `confirmed_allergy` | 用户声明存在已知过敏食物，需要建立禁忌清单             |
| 正在观察新食物     | `observing`         | 用户正在记录新食物及相关观察情况                       |
| 暂时跳过           | `skipped`           | 用户暂时不设置过敏信息，之后可以补充                   |

状态必须明确区分：

- `none_known` 不等于 `skipped`。
- `skipped` 不等于没有过敏。
- 用户声明的过敏信息不代表产品进行过医学诊断。
- 产品记录完成不代表医学上确认不过敏。

#### 5.4.2 首次设置流程

```text
进入过敏信息设置
       |
       v
展示状态选择
       |
       +--------------------------+
       |             |            |
       v             v            v
    无已知过敏     已知过敏      暂时跳过
       |             |            |
       v             v            v
  保存声明状态    添加过敏食物   保存 skipped
       |             |            |
       |             v            |
       |          保存禁忌清单     |
       |             |            |
       +-------------+------------+
                     |
                     v
                进入基础日程
```

如果用户选择 `observing`，则进入新食物观察记录流程。

#### 5.4.3 已知过敏处理

当用户选择 `confirmed_allergy` 时：

1. 用户添加已知过敏食物。
2. 系统保存食物禁忌清单。
3. 日程生成时过滤相关食物。
4. 食谱替换时继续执行相同过滤。
5. 用户手动选择餐食时仍然执行过滤。
6. 如果已生成日程中存在相关食物，重新校验未执行任务。

安全规则：

- 已知过敏食物必须被强制过滤。
- 不能通过手动替换绕过禁忌。
- 不得因为用户完成某次观察就自动移除禁忌。
- 只有用户主动修改相关信息后，系统才能更新用户声明的状态。
- 用户修改后，必须重新校验未来尚未执行的日程。

#### 5.4.4 暂时跳过处理

当用户选择 `skipped` 时：

- 保存 `skipped` 状态。
- 不启动新食物观察流程。
- 不阻断基础日程生成。
- 不阻断日常餐食推荐。
- 不产生惩罚或负面提示。
- 允许用户以后重新设置。

不得将跳过解释为用户没有过敏。

### 5.5 新食物观察流程

新食物观察记录用于帮助照护者记录实际尝试情况，不承担医学诊断功能。

流程：

```text
用户选择新食物观察
       |
       v
选择食物
       |
       v
记录尝试时间
       |
       v
记录食用情况
       |
       v
记录观察情况
       |
       +------------------------+
       |                        |
       v                        v
    未发现异常                疑似出现反应
       |                        |
       v                        v
  保存观察记录             停止该食物自动安排
       |                        |
       v                        v
  可继续记录其他食物       展示风险提示
                                |
                                v
                         必要时寻求医疗帮助
```

观察记录至少包含：

- 食物。
- 尝试时间。
- 食用情况。
- 观察结果。
- 反应描述。
- 反应发生时间（如有）。
- 记录时间。

业务规则：

1. 用户可以新增、查看和补充观察记录。
2. 未发现异常只代表本次记录未发现异常。
3. 不得自动将该食物标记为医学上确认不过敏。
4. 出现疑似反应后，停止该食物自动安排。
5. 不自动安排未来再次试吃。
6. 严重或可能危及生命的反应，应提示立即寻求紧急医疗帮助。
7. 观察流程不能替代专业医疗评估。

### 5.6 幼儿日程生成

流程：

```text
幼儿档案有效
       |
       v
识别当前年龄阶段
       |
       v
读取饮食偏好和约束
       |
       v
读取过敏状态
       |
       v
获取适用阶段的审核内容
       |
       v
执行安全过滤
       |
       v
执行阶段及营养结构匹配
       |
       v
结合家庭场景筛选
       |
       v
生成未来 7 天日程
       |
       v
校验日程
       |
       +---- 通过 ----> 保存并展示
       |
       +---- 不通过 --> 降级处理
                         不得放宽安全约束
```

生成规则：

1. 只使用已审核的幼儿餐食内容。
2. 必须匹配当前年龄阶段。
3. 必须执行已知过敏食物过滤。
4. 需要考虑食物质地及阶段适配要求。
5. 不得将不适用的成人餐食直接作为幼儿餐食推荐。
6. 用户饮食偏好不得覆盖安全规则。
7. 观察中的食物应按照后续安全规则 Spec 确定其是否允许进入候选。
8. 候选不足时允许展示结构建议或暂缺状态，不得使用未经审核的内容补齐。

### 5.7 幼儿日程执行

幼儿端执行方式与孕期端共享基础任务管理能力。

用户可以：

- 查看当天餐食安排。
- 查看餐食详情。
- 标记完成。
- 跳过任务。
- 替换餐食。
- 调整执行安排。
- 记录新食物尝试及观察情况。

但幼儿端必须额外执行：

- 年龄阶段适配校验。
- 食物过敏约束校验。
- 新食物观察状态校验。
- 已审核的质地和食物安全要求。

页面层可以复用任务组件，但不能因此将孕期和幼儿的安全规则合并成同一套业务判断。

## 6. 共享日程与任务管理流程

### 6.1 日程生成周期

一期统一采用：

- 每日执行。
- 提前生成未来 7 天日程。
- 用户进入日程时展示当天任务。
- 每日可以根据阶段变化、约束变化和用户操作重新校验后续日程。

日程生成和日程执行是两个独立过程。

### 6.2 日程状态

建议日程实例状态：

| 状态     | 标识                  | 说明                           |
| -------- | --------------------- | ------------------------------ |
| 待执行   | `pending`             | 日程已生成，尚未开始执行       |
| 执行中   | `in_progress`         | 日程中已有任务进入执行状态     |
| 已完成   | `completed`           | 当日日程全部达到完成条件       |
| 部分完成 | `partially_completed` | 当日日程部分完成               |
| 已调整   | `adjusted`            | 日程因用户操作或规则变化而调整 |
| 已失效   | `invalidated`         | 日程因阶段或安全约束变化而失效 |

说明：

- 日程状态与任务状态分开管理。
- 不应仅因为用户跳过一个任务就将整日日程判定为失败。
- 已失效的日程需要保留历史记录和失效原因。

### 6.3 任务状态

建议任务状态：

| 状态   | 标识          | 说明                       |
| ------ | ------------- | -------------------------- |
| 待执行 | `pending`     | 等待用户执行               |
| 已完成 | `completed`   | 用户确认完成               |
| 已跳过 | `skipped`     | 用户主动跳过               |
| 已替换 | `replaced`    | 用户完成替换操作           |
| 已顺延 | `deferred`    | 用户调整执行时间           |
| 已取消 | `cancelled`   | 任务不再执行               |
| 已失效 | `invalidated` | 因规则或安全约束变化而失效 |

任务状态需要保留必要的变更记录，不能只覆盖当前状态而丢失历史。

### 6.4 任务完成

```text
待执行任务
    |
    v
用户选择完成
    |
    v
记录完成状态和时间
    |
    v
更新日程统计
```

只有用户明确确认后，任务才进入 `completed`。

### 6.5 任务跳过

```text
待执行任务
    |
    v
用户选择跳过
    |
    v
可选填写原因
    |
    v
更新为 skipped
    |
    v
保留其他任务
```

跳过不影响其他任务，也不触发惩罚机制。

### 6.6 任务替换

```text
用户选择替换
    |
    v
获取适用候选
    |
    v
安全过滤
    |
    +---- 有候选 ----> 用户选择替代内容
    |                      |
    |                      v
    |                  保存替换关系
    |                      |
    |                      v
    |                  更新任务内容
    |
    +---- 无候选 ----> 提示暂无合适替代内容
                           |
                           v
                       保留原任务
```

替换必须保存：

- 原始内容 ID。
- 替换后内容 ID。
- 替换时间。
- 替换原因（可选）。
- 操作来源。

### 6.7 任务顺延

用户临时无法按原计划执行时，可以调整任务时间。

流程：

1. 用户选择顺延。
2. 选择新的执行时间或日期。
3. 系统检查新的执行安排是否有效。
4. 保存调整结果。
5. 更新相关日程展示。

约束：

- 顺延不能改变食物的安全属性。
- 顺延后仍需满足阶段适配要求。
- 不应自动把过期任务无限累积到后续日期。
- 具体顺延范围、跨日处理和冲突处理策略由日程规则 Spec 定义。

### 6.8 日程重新校验

以下情况触发未来未执行日程重新校验：

- 用户修改已知过敏信息。
- 用户修改饮食禁忌。
- 用户修改阶段相关基础信息。
- 档案阶段发生变化。
- 内容被撤回或安全状态发生变化。
- 规则版本更新且需要重新执行安全校验。

处理流程：

```text
发生档案或规则变化
       |
       v
确定受影响的未来任务
       |
       v
重新执行安全校验
       |
       +---- 全部有效 ----> 保留原日程
       |
       +---- 存在无效任务
                    |
                    v
                标记失效
                    |
                    v
                重新生成候选
                    |
                    v
                安全校验
                    |
                    +---- 有合适候选 ----> 更新日程
                    |
                    +---- 无合适候选 ----> 展示暂缺状态
```

已经完成的历史任务不能因为规则更新而被静默改写。

## 7. 阶段变化与日程衔接

### 7.1 孕期阶段变化

当孕周发生变化时：

1. 系统重新计算当前孕周。
2. 判断是否仍属于一期支持范围。
3. 判断是否存在新阶段适用内容。
4. 对未来未执行任务重新校验。
5. 不适用的内容不得继续自动安排。

如果进入一期尚未覆盖的阶段：

- 保留历史日程。
- 停止生成缺乏审核内容的新日程。
- 展示阶段暂不支持说明。
- 不自动使用其他阶段的食谱替代。

### 7.2 幼儿年龄阶段变化

当幼儿月龄变化时：

1. 重新计算当前月龄。
2. 识别当前阶段。
3. 检查对应阶段的内容是否可用。
4. 重新校验未来未执行任务。
5. 不符合当前阶段要求的内容不得继续推荐。

阶段变化不得简单通过替换年龄标签处理，必须重新执行适用性和安全规则。

## 8. 异常及边界流程

### 8.1 档案信息不完整

场景：

用户没有完成必要信息填写。

处理：

- 保留草稿。
- 明确展示缺少的信息。
- 不生成正式日程。
- 允许用户稍后继续填写。

### 8.2 当前阶段没有审核内容

场景：

用户当前阶段没有可用的审核食谱。

处理：

- 不生成虚假日程。
- 不使用相邻阶段内容直接替代。
- 展示暂不支持说明。
- 保留档案和基础功能。

### 8.3 候选食谱不足

场景：

安全过滤后，满足条件的食谱数量不足。

处理：

- 不降低安全规则优先级。
- 不强行凑齐日程。
- 允许部分餐次暂缺。
- 可以展示经过审核的结构建议，但必须明确其不是具体食谱推荐。

### 8.4 用户修改过敏信息

场景：

用户从 `skipped` 改为 `confirmed_allergy`，或者新增已知过敏食物。

处理：

1. 更新用户声明的过敏状态。
2. 更新禁忌清单。
3. 找出未来未执行日程。
4. 重新执行安全过滤。
5. 使不符合条件的任务失效。
6. 重新寻找合适候选。
7. 无候选时展示暂缺状态。

### 8.5 观察中出现疑似反应

处理：

- 记录疑似反应。
- 停止该食物自动安排。
- 不自动安排未来再次尝试。
- 提供适当风险提示。
- 严重或可能危及生命的情况提示立即紧急医疗求助。

### 8.6 用户长时间未执行日程

处理原则：

- 不将未完成任务自动认定为已完成。
- 不对用户进行惩罚。
- 不无限累积未执行任务。
- 后续日程仍以当前日期和当前阶段为依据。
- 历史执行记录保留。

### 8.7 内容被撤回

当内容因安全问题或审核问题被撤回：

1. 将内容标记为不可继续推荐。
2. 查询未来未执行任务。
3. 使关联任务失效。
4. 重新筛选合规候选。
5. 保留历史任务和操作记录。
6. 无合适候选时展示暂缺状态。

## 9. 业务规则优先级

所有推荐和用户操作必须遵循以下优先级：

| 优先级 | 规则层             | 说明                                 |
| ------ | ------------------ | ------------------------------------ |
| L0     | 安全规则           | 最高优先级，必须执行，不能被覆盖     |
| L1     | 阶段规则           | 判断内容是否适用于当前孕周或幼儿阶段 |
| L2     | 营养及餐食结构规则 | 判断餐次及内容结构是否符合配置要求   |
| L3     | 个性化规则         | 用户偏好、家庭场景、操作便利性等     |

执行顺序：

```text
候选内容
    |
    v
L0 安全过滤
    |
    v
L1 阶段过滤
    |
    v
L2 营养及结构匹配
    |
    v
L3 个性化排序
    |
    v
最终候选
```

关键约束：

- L3 不得覆盖 L0。
- 手动选择不代表可以绕过 L0。
- 内容缺失时不得降低安全规则。
- 所有推荐结果应能够追溯对应规则和内容版本。

| 事件         | 标识                       | 触发时机         |
| ------------ | -------------------------- | ---------------- |
| 创建档案     | `profile_created`          | 档案创建成功     |
| 生成日程     | `schedule_generated`       | 日程生成成功     |
| 查看日程     | `schedule_viewed`          | 用户查看日程     |
| 完成任务     | `task_completed`           | 用户确认任务完成 |
| 跳过任务     | `task_skipped`             | 用户跳过任务     |
| 替换餐食     | `recipe_replaced`          | 替换操作成功     |
| 查看食谱     | `recipe_viewed`            | 用户查看食谱详情 |
| 顺延任务     | `schedule_deferred`        | 用户完成顺延操作 |
| 阶段变化     | `stage_changed`            | 档案阶段发生变化 |
| 修改过敏状态 | `allergy_status_updated`   | 用户修改过敏状态 |
| 创建观察记录 | `food_observation_created` | 用户新增观察记录 |
| 触发安全规则 | `safety_rule_triggered`    | 安全规则被触发   |

### 10.1 数据分析原则

孕期和幼儿两个场景需要分别统计，不得简单合并。

重点关注：

- 建档完成率。
- 首次日程生成成功率。
- 日程查看率。
- 任务完成率。
- 任务跳过率。
- 餐食替换率。
- 日程持续使用情况。
- 过敏信息设置及跳过比例。
- 新食物观察记录使用情况。

健康相关信息属于敏感数据，应遵循最小必要、明确告知、权限控制和安全存储原则。

不得默认将敏感健康数据用于广告画像或无边界的数据分析。

## 12. 一期关键验收标准

### 12.1 档案流程

- [ ] 用户能够创建孕期档案。
- [ ] 用户能够创建幼儿档案。
- [ ] 能够识别当前孕期或幼儿阶段。
- [ ] 一期支持范围外的阶段不会生成未经审核的日程。
- [ ] 底层模型支持一个账号关联多个档案。

### 12.2 孕期流程

- [ ] 孕 30 周左右的目标用户能够完成建档。
- [ ] 系统能够识别适用的孕期阶段。
- [ ] 能够生成未来 7 天的餐食日程。
- [ ] 能够查看餐食详情。
- [ ] 能够完成、跳过、替换和顺延任务。
- [ ] 已知饮食禁忌能够参与安全过滤。
- [ ] 特殊状况规则未经专业审核时不得直接用于自动推荐。

### 12.3 幼儿流程

- [ ] 2 岁左右幼儿照护者能够完成建档。
- [ ] 系统能够识别适用的年龄阶段。
- [ ] 能够生成未来 7 天的餐食日程。
- [ ] 过敏信息可以跳过。
- [ ] `none_known` 与 `skipped` 状态明确区分。
- [ ] 已知过敏食物能够在日程生成和替换时强制过滤。
- [ ] 用户能够新增新食物观察记录。
- [ ] 疑似反应后停止该食物自动安排。
- [ ] 用户能够完成、跳过、替换和顺延任务。

- [ ] 安全规则优先级高于偏好和手动选择。
- [ ] 无合适候选时允许暂缺，不得强行凑齐日程。
- [ ] 历史已完成任务不会因规则更新而被静默修改。

### 12.5 数据记录

- [ ] 核心业务事件能够正常采集。
- [ ] 孕期与幼儿场景能够独立统计。
- [ ] 不将健康敏感信息默认用于广告画像。
- [ ] 关键推荐结果能够追溯内容版本及规则版本。

数据模型需要重点解决：

1. 一个账号关联多个档案的关系。
2. 孕期和幼儿档案的差异化字段。
3. 阶段规则及阶段变化记录。
4. 日程实例与任务实例的关系。
5. 食谱、食材及内容版本的关系。
6. 过敏状态与禁忌清单的关系。
7. 新食物观察记录的数据结构。
8. 日程替换、跳过、顺延的操作历史。
9. 安全规则触发及日程重新校验记录。

数据模型应以本文档定义的业务流程为依据，不应为了追求字段统一而强行合并孕期和幼儿的领域概念。
