## 1. 文档目的

本文档定义「食刻」一期的内容体系、食材分类、食谱结构、阶段适配、营养数据、过敏原标签、内容审核、版本管理及发布流程。

本文档是以下模块的共同依据：

- 内容数据维护。
- 食谱管理后台。
- 日程生成引擎。
- 食谱候选筛选。
- 安全规则中心。
- 食谱展示页面。
- 内容审核及发布流程。

### 1.1 核心目标

建立统一的内容标准，使每条食谱都具备明确的业务属性、适用范围和审核状态，能够被规则引擎准确识别。

内容体系需要回答：

1. 这是什么食物或食谱？
2. 包含哪些食材？
3. 适用于哪个业务场景？
4. 适用于哪个阶段？
5. 是否存在已知安全限制？
6. 是否满足对应阶段的质地及制作要求？
7. 是否具备必要的营养数据？
8. 内容是否经过专业审核？
9. 当前内容是否允许进入日程推荐？
10. 历史日程使用的是哪个内容版本？

### 1.2 内容管理原则

**原则一：内容数据化。**

食材、食谱、营养信息、适用阶段、过敏原标签等均应采用结构化数据维护，不依赖自然语言描述进行核心业务判断。

**原则二：规则与内容分离。**

食谱负责描述自身属性，规则引擎负责判断是否适用。不得在食谱名称或描述中隐藏关键业务规则。

**原则三：安全信息优先。**

安全相关字段必须具备明确来源和审核状态。未知信息不能默认视为安全。

**原则四：内容必须经过审核。**

未经审核的食谱不能进入生产推荐池。AI 生成内容不能直接发布。

**原则五：内容版本不可覆盖。**

已发布食谱发生重要修改时，需要产生新版本，历史日程保留原有内容依据。

**原则六：允许数据不完整。**

营养数据或其他非必要数据尚未核验时允许为空，不得为了填充字段而编造数值。

**原则七：一期内容范围收敛。**

一期只建设孕 30 周左右孕晚期和 2 岁左右幼儿所需的内容，不提前批量建设其他阶段内容。

## 2. 一期内容范围

### 2.1 一期内容分类

一期内容分为两个独立业务域。

| 业务域   | 一期目标           | 内容方向               |
| -------- | ------------------ | ---------------------- |
| 孕期内容 | 孕 30 周左右孕晚期 | 孕期日常餐食及适用食谱 |
| 幼儿内容 | 2 岁左右幼儿       | 幼儿家庭餐及适用食谱   |

两个业务域可以共享食材基础数据和食谱数据结构，但必须分别维护适用阶段、安全要求和审核结果。

### 2.2 一期不覆盖的内容

以下内容不作为一期完整内容建设目标：

- 孕早期完整食谱。
- 孕中期完整食谱。
- 所有孕晚期孕周的完整食谱。
- 0—6 月龄婴儿喂养内容。
- 6—9 月龄辅食内容。
- 10—12 月龄辅食内容。
- 13—23 月龄幼儿过渡餐食内容。
- 25—36 月龄幼儿完整内容。

后续扩展时，应沿用本 Spec 的内容结构，不应为不同年龄阶段另建一套互不兼容的数据模型。

### 2.3 内容交付优先级

一期建议按照以下优先级准备内容：

| 优先级 | 内容               | 目的                     |
| ------ | ------------------ | ------------------------ |
| P0     | 一期适用阶段定义   | 确保内容能够被准确筛选   |
| P0     | 食材标准库         | 建立统一食材标识         |
| P0     | 食谱标准数据结构   | 保证内容可被程序读取     |
| P0     | 安全标签及审核信息 | 保证内容具备基本安全约束 |
| P0     | 孕期一期基础食谱   | 支持孕期日程生成         |
| P0     | 幼儿一期基础食谱   | 支持幼儿日程生成         |
| P1     | 食谱替换关系及标签 | 支持替换和个性化筛选     |
| P1     | 营养数据完善       | 支持后续营养结构匹配     |
| P1     | 内容维护工具       | 降低后续内容维护成本     |

具体食谱数量、每日餐次及内容覆盖率需要结合日程规则 Spec 确定，不在本文件中预设未经验证的数量。

## 3. 内容体系架构

### 3.1 三层内容体系

内容体系分为三层：

```text
                内容体系
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
    营养结构层   标准食谱层   场景适配层
       |           |           |
       v           v           v
    营养要求     食谱数据     孕期/幼儿
    餐次结构     食材用量     阶段适配
    食物分类     制作步骤     质地要求
    结构标签     营养数据     用户约束
       |           |           |
       +-----------+-----------+
                   |
                   v
               日程引擎
                   |
                   v
               日程推荐
```

### 3.2 营养结构层

职责：

- 定义不同业务域的餐食结构。
- 定义餐次类型。
- 定义食物分类。
- 提供经过审核的营养结构要求。
- 为日程引擎提供匹配依据。

营养结构层不直接生成具体食谱。

具体营养要求、指标及计算口径必须依据经过核验的专业资料，不得由开发人员自行设定。

### 3.3 标准食谱层

职责：

- 维护标准食材。
- 维护标准食谱。
- 维护食谱与食材的关系。
- 维护制作步骤。
- 维护营养数据。
- 维护食谱标签。
- 维护内容审核及版本信息。

标准食谱层不负责判断用户当前是否适合某条食谱。

### 3.4 场景适配层

职责：

- 识别孕期或幼儿业务场景。
- 维护适用阶段。
- 维护质地要求。
- 维护特殊场景标签。
- 关联安全规则。
- 提供食谱是否适用的判断依据。

最终是否推荐，由日程引擎结合用户档案及安全规则决定。

## 4. 食材标准库

### 4.1 FoodItem 定义

FoodItem 表示一个标准食材。

一个食材可以被多个食谱引用。

食材是内容体系的基础实体，不能直接用食谱中的自由文本代替标准食材数据。

### 4.2 食材字段规范

| 字段               | 类型     | 必填 | 说明           |
| ------------------ | -------- | ---- | -------------- |
| `_id`              | string   | 是   | 食材唯一 ID    |
| `foodCode`         | string   | 是   | 食材业务编码   |
| `name`             | string   | 是   | 标准名称       |
| `aliases`          | array    | 否   | 别名           |
| `categoryCode`     | string   | 是   | 食材分类       |
| `allergenCodes`    | array    | 否   | 过敏原分类标签 |
| `textureTags`      | array    | 否   | 质地相关标签   |
| `status`           | string   | 是   | 食材状态       |
| `sourceReferences` | array    | 否   | 数据来源       |
| `reviewStatus`     | string   | 是   | 审核状态       |
| `reviewedBy`       | string   | 否   | 最近一次**发布审核**通过的操作者 ID；随实体发布写入 |
| `reviewedAt`       | datetime | 否   | 最近一次发布审核通过时间 |
| `version`          | string   | 是   | 内容版本号（与 `ContentVersion` 或发布快照一致，见 §4.2.1） |
| `createdAt`        | datetime | 是   | 创建时间       |
| `updatedAt`        | datetime | 是   | 更新时间       |

### 4.2.1 别名与实体级审核（F-04.3-05）

**审核粒度**：`FoodItem.aliases[]` 与 `FoodAllergen.aliases[]` 采用**实体级**审核，不对单个别名单独维护审核状态。

**责任边界**：

| 实体 | 别名维护 | 发布审核 |
| --- | --- | --- |
| `FoodItem` | 内容运营/专业人员 | 与 `FoodItem.status` / `reviewStatus` 同一发布流程 |
| `FoodAllergen` | 内容运营/专业人员 | 与字典项 `status` / `reviewStatus` 同一发布流程 |

**生命周期**：

1. 新增或修改 `aliases[]` 后，实体须进入 `pending_review`（或保持不可发布状态），直至再次审核发布。
2. **仅当** `FoodItem.status=published` 且 `reviewStatus` 为 `approved`/`published` 时，当前 `aliases[]` 整包视为已审核，可参与 S1 自动匹配（05 §5.3.2.4）。
3. 审核未通过或仍为草稿的 `aliases` **不得**参与 `matched` / `not_matched`。
4. 别名撤销或修改并重新发布后，`reviewedBy`、`reviewedAt`、`version` 更新；历史匹配追溯依赖任务/日程生成时点的内容版本快照，而非 retroactive 改写。
5. **不**新建独立别名集合；审计复用 `ContentVersion` 与实体 `version` 字段。

**与 05 对齐**：字段名 `reviewedBy`、`reviewedAt`、`version` 语义与 05 §5.4、`§5.3.2.4` 一致。

### 4.3 食材分类

建议采用可配置分类字典。

分类示例：

| 分类编码    | 分类名称       | 示例                       |
| ----------- | -------------- | -------------------------- |
| `grain`     | 谷物及主食类   | 米、面等                   |
| `vegetable` | 蔬菜类         | 叶菜、根茎类等             |
| `fruit`     | 水果类         | 常见水果                   |
| `protein`   | 蛋白质食材类   | 肉类、鱼类、蛋类、豆制品等 |
| `dairy`     | 乳及乳制品类   | 奶及相关制品               |
| `legume`    | 豆类及豆制品类 | 豆类及相关制品             |
| `oil`       | 油脂类         | 食用油等                   |
| `other`     | 其他           | 无法归入以上分类的食材     |

说明：

- 以上为产品数据分类建议，不代表营养学分类标准。
- 具体分类字典可以根据专业审核结果调整。
- 同一食材原则上应有一个主要分类。
- 不应仅根据食材名称推断营养属性或安全属性。

### 4.4 过敏原字典（FoodAllergen）

持久化实体 `FoodAllergen`，集合 `food_allergens`（02 §7.0、05 §5.4）。`FoodItem.allergenCodes` 为内容侧分类标签，**不能**替代已审核的 `FoodSafetyProfile.allergenIds` 用于 S1 门禁（05 §5.3.2.1）。

**字典项字段**（与 02/05 一致）：

| 字段               | 类型     | 必填 | 说明       |
| ------------------ | -------- | ---- | ---------- |
| `_id` / `allergenId` | string | 是   | 过敏原 ID  |
| `allergenCode`     | string   | 是   | 统一编码   |
| `allergenName`     | string   | 是   | 标准名称   |
| `aliases`          | array    | 否   | 别名（实体级审核，见 §4.2.1） |
| `description`      | string   | 否   | 说明       |
| `sourceReferences` | array    | 否   | 来源依据   |
| `relatedFoodItems` | array    | 否   | 关联食材 ID（须与已审核 `FoodSafetyProfile` 一致，不得仅名称推断） |
| `status`           | string   | 是   | `active` / `inactive` |
| `reviewStatus`     | string   | 是   | 内容审核状态（同 §4.5 枚举语义） |
| `reviewedBy`       | string   | 否   | 最近一次发布审核操作者 |
| `reviewedAt`       | datetime | 否   | 最近一次发布审核时间 |
| `version`          | string   | 是   | 字典版本号 |

**名称与映射（F-04.3-03）**：

1. 用户自由输入的名称 **不得** 自动写入 `aliases`。
2. 无法映射到唯一已发布 `FoodItem` 或 `FoodAllergen` 的用户输入，在 S1 中按 05 §5.3.2.5 返回 `unresolved`。
3. 复合食品须维护可展开的结构化成分（Recipe / `RecipeIngredient`）；成分不完整时 **不得** 作为完整安全数据参与 `not_matched`。

**食材 `allergenCodes`（`FoodItem`）**：须有依据并经审核；不得仅关键词认定；未确认不得默认无过敏原；与 `FoodSafetyProfile.allergenIds` 的 S1 职责区分见 §4.5 末及 05 §5.3.2.1。

### 4.5 食材状态

枚举与 `Recipe.status` 相同，权威定义见 `specs/02-data-model.md` §5.1.1。本章仅保留业务释义：

- `draft`：草稿。
- `pending_review`：待审核。
- `approved`：审核通过。
- `published`：已发布。
- `withdrawn`：已撤回。
- `archived`：已归档。

未发布或已撤回的食材，不得作为新发布食谱的有效食材引用。

**`allergenCodes`（内容标签）**：可引用 §4.4 字典编码，用于展示与内容检索；S1 硬过滤以 `FoodSafetyProfile` 已审核关联为准（05 §5.3.2.1）。

## 5. 标准食谱模型

### 5.1 Recipe 定义

Recipe 表示一条经过结构化维护的标准食谱。

食谱至少需要具备：

- 基本信息。
- 适用业务域。
- 适用阶段。
- 餐次类型。
- 食材组成。
- 制作步骤。
- 质地及制作属性。
- 营养数据（如已核验）。
- 安全标签。
- 内容审核状态。
- 内容版本信息。

### 5.2 食谱字段规范

| 字段                     | 类型     | 必填 | 说明             |
| ------------------------ | -------- | ---- | ---------------- |
| `_id`                    | string   | 是   | 食谱唯一 ID      |
| `recipeCode`             | string   | 是   | 业务编码         |
| `name`                   | string   | 是   | 食谱名称         |
| `description`            | string   | 是   | 食谱简介         |
| `coverImage`             | string   | 否   | 封面图片         |
| `mealType`               | string   | 是   | 餐次类型         |
| `applicableProfileTypes` | array    | 是   | 适用业务域       |
| `applicableStageCodes`   | array    | 是   | 适用阶段         |
| `ingredients`            | array    | 是   | 食材及用量关系   |
| `preparationSteps`       | array    | 是   | 制作步骤         |
| `preparationTimeMinutes` | number   | 否   | 制作时间         |
| `difficulty`             | string   | 否   | 制作难度         |
| `nutritionData`          | object   | 否   | 营养数据         |
| `textureTags`            | array    | 否   | 质地标签         |
| `sceneTags`              | array    | 否   | 场景标签         |
| `dietTags`               | array    | 否   | 饮食属性标签     |
| `allergenCodes`          | array    | 否   | 食谱过敏原标签   |
| `safetyNotes`            | string   | 否   | 经审核的安全说明 |
| `status`                 | string   | 是   | 内容状态         |
| `currentVersionId`       | string   | 是   | 当前发布版本     |
| `createdAt`              | datetime | 是   | 创建时间         |
| `updatedAt`              | datetime | 是   | 更新时间         |

说明：

- `ingredients` 的实际数据关系以 RecipeIngredient 为准。
- `allergenCodes` 可以由食材及配料关系生成，再经过审核确认。
- 不能只依赖食谱层标签替代食材层安全信息。
- 关键安全属性需要保留可追溯依据。
- 食谱字段可以根据业务需要增加，但不得改变字段的既定业务含义。

### 5.3 食谱业务域

`applicableProfileTypes`：

- `pregnancy`
- `child`

同一食谱可以适用于多个业务域，但必须分别完成适用性审核。

例如：

一条普通家庭餐食谱可能同时具备孕期及幼儿场景的使用价值，但不能因为食材相同就自动认定两个场景均适用。

如果同一食谱用于两个业务域：

1. 需要明确各自的适用阶段。
2. 需要审核各自的制作要求。
3. 需要审核各自的安全属性。
4. 需要明确是否需要调整份量、质地或制作方式。
5. 必要时拆分为不同的 Recipe 记录。

### 5.4 餐次类型

建议统一采用：

| 编码        | 名称 |
| ----------- | ---- |
| `breakfast` | 早餐 |
| `lunch`     | 午餐 |
| `dinner`    | 晚餐 |
| `snack`     | 加餐 |
| `other`     | 其他 |

餐次配置由日程规则 Spec 控制。

食谱支持某个餐次，不代表系统必须在每个日程中安排该餐次。

### 5.5 食谱标签体系

标签分为以下几类：

| 标签类别   | 字段                   | 用途               |
| ---------- | ---------------------- | ------------------ |
| 食材分类   | `categoryCodes`        | 描述食材结构       |
| 餐次标签   | `mealType`             | 匹配餐次           |
| 场景标签   | `sceneTags`            | 描述家庭和制作场景 |
| 饮食属性   | `dietTags`             | 描述食谱属性       |
| 质地标签   | `textureTags`          | 描述食物质地       |
| 难度标签   | `difficulty`           | 估计制作难度       |
| 过敏原标签 | `allergenCodes`        | 支持安全过滤       |
| 阶段标签   | `applicableStageCodes` | 支持阶段匹配       |

标签必须采用受控字典。

不允许开发人员或内容录入人员随意创建同义但不同编码的标签。

### 5.6 难度等级

建议使用：

- `easy`
- `medium`
- `hard`

难度用于帮助用户选择制作成本合适的餐食。

不参与安全判断。

### 5.7 场景标签

建议支持以下类型的标签：

- `quick_prep`：准备时间较短。
- `family_meal`：家庭餐场景。
- `batch_prep`：适合集中准备。
- `simple_ingredients`：食材组成较简单。

以上标签只是内容分类建议，必须有明确的定义和审核口径。

场景标签不得承担营养或医疗判断功能。

## 6. 食谱与食材关系

### 6.1 RecipeIngredient 关系模型

一条食谱可以关联多个食材，一个食材也可以被多个食谱使用。

建议字段：

| 字段                | 类型        | 必填 | 说明         |
| ------------------- | ----------- | ---- | ------------ |
| `_id`               | string      | 是   | 关系 ID      |
| `recipeId`          | string      | 是   | 食谱 ID      |
| `foodItemId`        | string      | 是   | 食材 ID      |
| `quantity`          | number/null | 否   | 用量         |
| `unit`              | string/null | 否   | 用量单位     |
| `preparationMethod` | string      | 否   | 食材处理方式 |
| `isMainIngredient`  | boolean     | 是   | 是否主要食材 |
| `sortOrder`         | number      | 是   | 展示顺序     |

### 6.2 用量管理

食材用量应尽量采用结构化数据。

例如：

```json
{
  "foodItemId": "food_xxx",
  "quantity": 100,
  "unit": "g",
  "preparationMethod": "chopped",
  "isMainIngredient": true,
  "sortOrder": 1
}
```

以上仅为字段格式示例，不代表实际推荐用量。

约束：

1. 数值必须大于合理的业务下限，具体校验范围由数据规范确定。
2. 用量和单位必须匹配。
3. 不知道实际用量时允许为空。
4. 不得通过默认值填充未知用量。
5. 食谱中的用量必须明确对应的计量口径。
6. 需要区分生重、熟重、可食部分等不同计量口径。

### 6.3 食谱份量

建议食谱增加：

```json
{
  "servingInfo": {
    "servings": null,
    "servingDescription": null,
    "quantityBasis": null
  }
}
```

字段含义：

- `servings`：该食谱对应的份数。
- `servingDescription`：份量描述。
- `quantityBasis`：食材用量所对应的计量基准。

未确认的份数及用量基准允许为空。

孕期与幼儿的份量需求不能简单通过同一份食谱的份数自动推断。

## 7. 孕期内容规范

### 7.1 一期内容目标

一期孕期内容面向孕 30 周左右的孕晚期用户。

内容需要支持：

- 日常餐食安排。
- 餐次选择。
- 食材及制作信息。
- 适用阶段识别。
- 饮食偏好筛选。
- 已知禁忌过滤。
- 经过审核的特殊场景适配。

### 7.2 孕期食谱适用字段

建议增加孕期业务扩展对象：

```json
{
  "pregnancyApplicability": {
    "enabled": true,
    "stageCodes": ["pregnancy_late"],
    "reviewStatus": "approved",
    "reviewVersion": "v1"
  }
}
```

说明：

- `stageCodes` 必须与阶段配置字典保持一致。
- `reviewStatus` 表示该业务域的适用性审核状态。
- 同一食谱在幼儿场景通过审核，不代表孕期场景自动通过。
- 孕期具体适用周数由阶段配置和专业审核确定。

### 7.3 孕期特殊场景标签

特殊场景需要采用受控配置，不允许直接根据用户自然语言说明进行自动诊断。

例如：

- 用户饮食偏好。
- 用户主动声明的饮食禁忌。
- 经专业审核支持的特殊饮食场景。

对于涉及特殊健康状况的内容：

1. 必须有明确专业依据。
2. 必须经过对应专业能力人员审核。
3. 必须明确适用人群及限制。
4. 必须明确内容有效期。
5. 未审核的特殊场景不得进入自动推荐。

### 7.4 孕期内容审核重点

审核人员需要确认：

- 适用阶段是否正确。
- 食材信息是否准确。
- 制作方式是否符合适用场景要求。
- 相关安全信息是否完整。
- 营养数据是否有可靠依据。
- 是否存在不适用的特殊场景。
- 是否存在超出产品能力范围的医疗建议。

不得在内容文案中承诺治疗、预防疾病或替代医疗指导。

## 8. 幼儿内容规范

### 8.1 一期内容目标

一期幼儿内容面向 2 岁左右幼儿。

内容以适龄家庭餐及日常喂养安排为主。

需要明确：

- 适用年龄阶段。
- 食材组成。
- 食物质地。
- 制作步骤。
- 食材处理要求。
- 已审核的安全说明。
- 过敏原信息。
- 营养数据（如已核验）。

### 8.2 幼儿食谱适用字段

建议增加幼儿业务扩展对象：

```json
{
  "childApplicability": {
    "enabled": true,
    "stageCodes": ["child_toddler"],
    "textureTags": [],
    "reviewStatus": "approved",
    "reviewVersion": "v1"
  }
}
```

以上 `child_toddler` 只是业务阶段编码示例，实际年龄范围需要在阶段规则 Spec 中确认。

### 8.3 质地标签

质地标签需要采用受控字典。

建议先建立字典管理机制，具体分类及定义由专业审核人员确认。

数据字段建议：

| 字段               | 类型   | 说明     |
| ------------------ | ------ | -------- |
| `code`             | string | 质地编码 |
| `name`             | string | 质地名称 |
| `description`      | string | 质地说明 |
| `applicableStages` | array  | 适用阶段 |
| `sourceReferences` | array  | 来源依据 |
| `reviewStatus`     | string | 审核状态 |
| `version`          | string | 字典版本 |

质地标签不应只用于页面展示，还需要被日程引擎用于候选过滤。

不得仅凭食谱名称推断其质地适用性。

### 8.4 制作及食用说明

幼儿食谱应明确必要的制作及食用信息。

建议字段：

```json
{
  "childPreparation": {
    "preparationNotes": [],
    "textureDescription": null,
    "servingNotes": [],
    "safetyNotes": []
  }
}
```

具体要求由专业审核人员根据适用阶段及食谱内容确认。

不应在缺少依据时由开发人员自行补充具体的食物尺寸、时间、温度或其他安全参数。

### 8.5 幼儿过敏原信息

幼儿食谱必须能够被安全规则中心检查。

检查范围包括：

- 食谱直接使用的食材。
- 食材对应的过敏原标签。
- 复合食品的配料信息（如适用）。
- 已知的加工及交叉接触风险信息（如有可靠资料）。

约束：

1. 食谱的过敏原信息不能只依赖人工输入的一段文本。
2. 食材层标签和食谱层标签需要建立关联。
3. 不确定的过敏原信息必须能够被识别。
4. 未知不能等同于无风险。
5. 具体未知信息如何处理，由安全规则 Spec 确定。
6. 已知过敏禁忌必须在推荐和替换时执行强制过滤。

### 8.6 新食物观察相关内容

食谱可以关联新食物相关提示，但必须区分：

- 食谱内容。
- 新食物观察记录。
- 用户声明的已知过敏信息。
- 专业审核的安全规则。

食谱被标记为某种新食物，不代表系统可以自动安排尝试。

是否允许进入推荐候选，必须由安全规则中心判断。

## 9. 营养数据规范

### 9.1 基本原则

营养数据用于支持后续营养结构匹配和内容说明。

一期不要求所有食谱都具备完整的营养成分分析。

只允许录入有可靠来源或经过合理计算、核验的数据。

### 9.2 营养字段

建议采用统一结构：

```json
{
  "nutritionData": {
    "energyKcal": null,
    "proteinG": null,
    "fatG": null,
    "carbohydrateG": null,
    "fiberG": null,
    "sodiumMg": null,
    "calculationBasis": null,
    "dataSource": null,
    "verifiedAt": null,
    "reviewStatus": "not_provided"
  }
}
```

以上为字段示例，不代表一期必须采集全部指标。

### 9.3 营养数据状态

建议：

- `not_provided`：尚未提供。
- `pending_review`：待核验。
- `verified`：已核验。
- `rejected`：核验不通过。
- `expired`：数据依据已失效或需要重新核验。

### 9.4 营养数据来源

建议记录：

- 来源名称。
- 发布机构。
- 来源版本。
- 对应条目或章节。
- 数据计量基准。
- 计算方法（如适用）。
- 核验人员。
- 核验时间。

来源资料应能够被后台人员定位和复核。

### 9.5 营养数据使用限制

1. 未核验数据不得用于精确营养匹配。
2. 缺少营养数据不代表食谱一定不适用。
3. 是否允许缺少营养数据的食谱进入日程，需要由日程规则明确。
4. 不同计量基准的数据不能直接比较。
5. 食材数据和成品食谱数据不能混淆。
6. 不得将估算值展示为精确检测值。
7. 涉及专业营养建议的数值必须有明确依据和审核记录。

## 10. 内容来源与依据管理

### 10.1 SourceReference 来源记录

所有涉及专业判断的内容应尽可能关联来源依据。

建议结构：

```json
{
  "sourceId": "source_xxx",
  "sourceName": null,
  "publisher": null,
  "version": null,
  "sectionReference": null,
  "sourceUrl": null,
  "publishedAt": null,
  "verifiedAt": null,
  "reviewerId": null
}
```

### 10.2 来源类型

建议支持：

- `official_guideline`
- `professional_consensus`
- `academic_publication`
- `nutrition_database`
- `professional_review`
- `other`

来源类型只是分类，不能自动代表资料可信度。

### 10.3 来源审核要求

审核人员需要确认：

1. 来源是否真实存在。
2. 发布机构是否明确。
3. 版本是否准确。
4. 是否适用于目标人群。
5. 是否支持当前内容结论。
6. 是否存在更新版本。
7. 是否需要设置重新核验时间。

如果来源不能支持具体结论，应删除该结论或将其标记为待核验，不得自行补充推断。

## 11. 内容审核流程

### 11.1 审核流程

```text
内容创建
   |
   v
草稿保存
   |
   v
基础数据校验
   |
   v
提交审核
   |
   v
专业审核
   |
   +---------------------+
   |                     |
   v                     v
审核通过              审核不通过
   |                     |
   v                     v
内容审批              返回修改
   |                     |
   v                     |
发布                    |
   |                     |
   v                     |
进入内容候选池          |
                         |
                         +----> 修改后重新提交
```

### 11.2 审核角色

建议分离以下角色：

| 角色         | 职责                     |
| ------------ | ------------------------ |
| 内容编辑     | 创建和维护食材、食谱内容 |
| 内容审核人员 | 审核内容完整性和规范性   |
| 专业审核人员 | 审核营养及相关安全适用性 |
| 发布审批人员 | 确认内容符合发布条件     |
| 管理员       | 管理人员、权限及系统配置 |

一期可以由少量人员兼任多个角色，但重要安全内容不应缺少独立专业审核。

### 11.3 审核维度

| 审核维度   | 检查内容                     |
| ---------- | ---------------------------- |
| 内容完整性 | 食材、步骤、适用信息是否完整 |
| 食材准确性 | 食材名称、分类及用量是否准确 |
| 阶段适配   | 是否适用于对应阶段           |
| 营养依据   | 营养数据及来源是否可靠       |
| 安全信息   | 过敏原及相关风险信息是否完整 |
| 制作要求   | 制作方式及适用要求是否明确   |
| 文案规范   | 是否存在不准确或误导性表达   |
| 版本信息   | 是否记录正确的版本及来源     |

### 11.4 审核记录

建议建立 `ContentReviewLog`。

字段：

| 字段               | 类型     | 说明        |
| ------------------ | -------- | ----------- |
| `_id`              | string   | 审核记录 ID |
| `contentId`        | string   | 内容 ID     |
| `contentVersionId` | string   | 内容版本 ID |
| `reviewType`       | string   | 审核类型    |
| `reviewerId`       | string   | 审核人      |
| `result`           | string   | 审核结果    |
| `comments`         | string   | 审核意见    |
| `sourceReferences` | array    | 审核依据    |
| `createdAt`        | datetime | 审核时间    |

审核结果：

- `approved`
- `rejected`
- `needs_revision`

审核记录原则上只追加，不允许通过修改旧记录掩盖历史审核结果。

## 12. 内容状态与发布规范

> **枚举权威**：`Recipe.status`、`FoodItem.status` 的持久化取值以 `specs/02-data-model.md` §5.1.1 为准。本章定义生命周期含义、状态迁移及推荐池规则。

### 12.1 内容状态机

建议状态：

```text
draft
  |
  v
pending_review
  |
  +------> rejected
  |           |
  |           v
  |        draft
  |
  v
approved
  |
  v
published
  |
  +------> withdrawn
  |
  +------> archived
```

说明：

- `draft`：草稿。
- `pending_review`：待审核。
- `approved`：审核通过，等待发布。
- `published`：正式发布。
- `rejected`：审核未通过。
- `withdrawn`：已撤回。
- `archived`：已归档。

**命名对照（勿再使用）**：PRD 旧称 `reviewing` → `pending_review`；旧称内容 `disabled` → `withdrawn` 或 `archived`（按业务选择，不用用户/档案的 `disabled`）。

**分层提醒**：营养数据 `reviewStatus` 中的 `expired`（§9.3）与主实体 `status` 无关；主实体不设 `expired` 枚举值。

### 12.1.1 合法状态迁移与触发条件

| 迁移 | 触发条件 |
| --- | --- |
| `draft` → `pending_review` | 编辑提交审核 |
| `pending_review` → `approved` | 审核通过 |
| `pending_review` → `draft` | 审核驳回（`ContentReviewLog.result = rejected`）或撤回提交 |
| `approved` → `published` | 发布审批通过 |
| `published` → `withdrawn` | 内容撤回（安全/依据/适用性等问题） |
| `published` → `archived` | 内容下线归档 |
| `withdrawn` → `archived` | 撤回后长期不再使用 |

禁止：AI 自动将状态改为 `approved` 或 `published`；未经审核进入 `published`。

### 12.1.2 撤回、归档、过期对未来日程的影响

| 情况 | 对新候选池 | 对未来未执行 `ScheduleTask` | 对历史已完成任务 |
| --- | --- | --- | --- |
| `withdrawn` | 禁止进入 | 触发重校验/替换流程 | 保留原 `contentVersionId` |
| `archived` | 禁止进入 | 不再安排新任务 | 保留追溯 |
| 版本/营养 `expired`（动态） | 视为不满足 §12.2 条件 | 重校验未执行任务 | 不变 |

### 12.2 进入生产推荐池的条件

食谱必须同时满足：

1. 内容状态为 `published`。
2. 当前内容版本审核通过。
3. 业务域适配审核通过。
4. 阶段适配信息明确。
5. 必需的安全字段通过校验。
6. 内容没有过期或撤回。
7. 当前规则允许该内容进入候选池。

以上条件只是进入候选池的必要条件，不代表最终一定会推荐给用户。

最终推荐仍需执行用户级安全过滤和个性化筛选。

### 12.3 内容发布前校验

发布前至少执行：

- 食谱基本字段校验。
- 食材引用有效性校验。
- 用量与单位格式校验。
- 业务域校验。
- 阶段适用性校验。
- 过敏原信息校验。
- 营养数据状态校验。
- 专业审核状态校验。
- 图片及内容资源校验。
- 版本信息校验。

存在关键安全字段缺失或审核未完成时，不允许发布。

### 12.4 内容撤回

出现以下情况时应支持撤回：

- 内容存在安全问题。
- 内容来源依据存在重大问题。
- 内容适用阶段错误。
- 发现过敏原信息错误。
- 专业审核结论发生变化。
- 内容不再满足当前产品规范。

撤回处理：

1. 将内容标记为 `withdrawn`。
2. 记录撤回原因、时间及操作人员。
3. 禁止进入新日程候选。
4. 查询未来未执行任务中引用该内容的记录。
5. 触发重新校验和替换流程。
6. 保留历史版本及历史任务记录。
7. 对已发布内容的安全问题进行必要影响范围排查。

## 13. 内容版本管理

### 13.1 版本原则

已发布内容不可直接覆盖。

发生以下变化时，应考虑创建新版本：

- 食材变化。
- 食材用量变化。
- 制作步骤变化。
- 营养数据变化。
- 适用阶段变化。
- 安全标签变化。
- 过敏原信息变化。
- 重要文案及安全说明变化。

### 13.2 版本数据结构

```json
{
  "_id": "content_version_xxx",
  "contentType": "recipe",
  "contentId": "recipe_xxx",
  "version": "1.0.0",
  "snapshot": {},
  "reviewStatus": "approved",
  "reviewerId": null,
  "reviewedAt": null,
  "effectiveAt": null,
  "expiresAt": null,
  "changeSummary": null,
  "createdAt": null
}
```

### 13.3 版本与日程关系

日程任务必须关联具体内容版本。

例如：

```text
ScheduleTask
    |
    +--> recipeId
    |
    +--> contentVersionId
```

如果食谱从 V1.0 更新为 V1.1：

- 新生成的日程使用符合当前条件的版本。
- 历史日程仍保留 V1.0 的引用。
- V1.0 如果因安全问题撤回，需要根据影响范围处理未来未执行任务。
- 不允许仅更新 Recipe 的 `currentVersionId` 就忽略历史日程的内容状态。

### 13.4 版本号规则

建议采用语义化版本号：

- 主版本：重大内容结构或适用性变化。
- 次版本：重要内容调整。
- 修订版本：一般文字或非关键展示信息修正。

版本升级规则可以根据实际内容管理流程简化，但必须保证每次发布都能唯一识别。

## 14. 一期内容维护工具

### 14.1 建设目标

一期不建设复杂 CMS。

建议先实现轻量受控后台或数据维护工具，满足：

- 食材维护。
- 食谱维护。
- 食谱与食材关联。
- 标签维护。
- 来源依据维护。
- 审核记录。
- 内容版本管理。
- 发布及撤回。
- 内容导入和导出。

### 14.2 后台功能范围

| 功能           | 一期要求 |
| -------------- | -------- |
| 食材列表       | 必须     |
| 食材新增和编辑 | 必须     |
| 食谱列表       | 必须     |
| 食谱新增和编辑 | 必须     |
| 食材关联       | 必须     |
| 阶段标签维护   | 必须     |
| 过敏原标签维护 | 必须     |
| 营养数据录入   | 支持     |
| 来源依据录入   | 必须     |
| 审核状态管理   | 必须     |
| 内容发布       | 必须     |
| 内容撤回       | 必须     |
| 版本查询       | 必须     |
| 复杂工作流     | 暂不需要 |
| 多组织协作     | 暂不需要 |

### 14.3 批量导入

一期可以支持通过结构化 JSON 或 CSV 导入食材及食谱基础数据。

批量导入必须经过：

1. 格式校验。
2. 必填字段校验。
3. 字典值校验。
4. 关联 ID 校验。
5. 重复数据检查。
6. 导入结果报告。

批量导入不代表自动审核通过，也不允许绕过发布流程。

### 14.4 AI 辅助内容维护

可以将 AI 用于：

- 食谱文案初稿。
- 字段结构化整理。
- 标签建议。
- 数据格式检查。
- 来源资料摘要。
- 重复内容发现。

但必须遵循：

1. AI 输出默认进入草稿状态。
2. AI 不得自动将内容标记为已审核。
3. AI 不得自动发布食谱。
4. AI 不得自行编造营养数值。
5. AI 不得自行判定过敏原安全属性。
6. 涉及孕期及幼儿安全的信息必须由专业审核人员确认。

## 15. 内容质量控制

### 15.1 内容完整度

每条食谱应能够通过内容完整性检查。

建议划分：

**基础字段**

- 食谱名称。
- 食谱简介。
- 餐次类型。
- 适用业务域。
- 适用阶段。
- 食材关系。
- 制作步骤。
- 内容状态。

**安全及适配字段**

- 食材分类。
- 过敏原信息。
- 阶段适配审核状态。
- 必要的制作及质地信息。
- 来源依据。
- 审核记录。

**扩展字段**

- 营养数据。
- 制作时间。
- 难度。
- 场景标签。
- 图片。
- 其他展示信息。

缺少基础字段时不得进入审核。

缺少适用场景所需的关键安全字段时不得发布。

扩展字段可以根据一期范围逐步完善。

### 15.2 重复内容检查

食谱维护时应检查：

- 相同食谱名称。
- 相同食材组合。
- 相同制作方式。
- 相同适用阶段。
- 不同名称但实际内容高度相似的食谱。

重复检查用于提醒内容维护人员，不应仅凭相似度自动删除或合并食谱。

### 15.3 内容失效检查

建议定期检查：

- 来源依据是否有更新。
- 过敏原标签是否需要重新核验。
- 食谱适用阶段是否仍有效。
- 内容审核是否过期。
- 内容是否被撤回。
- 图片资源是否失效。

涉及安全属性的变化，应优先处理。

## 16. 内容与日程引擎的接口边界

### 16.1 内容中心负责

- 提供已发布内容。
- 提供食谱结构化字段。
- 提供食材关系。
- 提供适用阶段。
- 提供安全相关标签。
- 提供内容版本。
- 提供审核及发布状态。

### 16.2 日程引擎负责

- 识别当前用户阶段。
- 判断食谱是否适用于当前档案。
- 执行用户级约束过滤。
- 执行安全规则。
- 匹配营养结构。
- 结合用户偏好排序。
- 生成日程。
- 记录生成依据。

### 16.3 推荐流程

```text
内容中心
   |
   v
获取已发布食谱
   |
   v
日程引擎读取候选
   |
   v
业务域匹配
   |
   v
阶段匹配
   |
   v
安全过滤
   |
   v
营养结构匹配
   |
   v
个性化排序
   |
   v
最终候选
   |
   v
生成日程
```

内容中心不能根据用户个人档案直接决定最终推荐。

日程引擎不能自行修改食谱的专业审核结论。

## 17. 一期内容验收标准

### 17.1 食材数据

- [ ] 食材具有唯一业务编码。
- [ ] 食材分类采用受控字典。
- [ ] 食材可以维护别名。
- [ ] 食材可以关联过敏原标签。
- [ ] 过敏原标签具有来源及审核信息。
- [ ] 食材状态可追溯。
- [ ] 未知信息允许为空。

### 17.2 食谱数据

- [ ] 食谱具有唯一业务编码。
- [ ] 食谱能够区分孕期和幼儿业务域。
- [ ] 食谱能够配置适用阶段。
- [ ] 食谱能够关联多个食材。
- [ ] 食材用量及单位采用结构化字段。
- [ ] 食谱能够维护制作步骤。
- [ ] 食谱能够维护质地及场景标签。
- [ ] 营养数据支持为空。
- [ ] 食谱能够记录过敏原信息。
- [ ] 食谱能够关联内容版本。

### 17.3 孕期内容

- [ ] 一期食谱适用于已确认的孕晚期目标阶段。
- [ ] 食谱适用性经过相应审核。
- [ ] 特殊场景内容有明确专业依据。
- [ ] 未经审核的特殊状况内容不能进入生产推荐池。

### 17.4 幼儿内容

- [ ] 一期食谱适用于已确认的幼儿目标阶段。
- [ ] 食谱具备必要的质地信息。
- [ ] 食材及制作信息能够支持安全审核。
- [ ] 食谱能够关联过敏原信息。
- [ ] 观察中的食物不会仅因内容标签而自动进入推荐。

### 17.5 审核及发布

- [ ] 内容能够从草稿进入审核流程。
- [ ] 审核结果能够记录。
- [ ] 专业审核状态可追溯。
- [ ] 未审核内容不能发布。
- [ ] 已发布内容不能直接覆盖。
- [ ] 内容撤回能够影响未来候选筛选。
- [ ] AI 生成内容默认处于草稿状态。

### 17.6 版本及追溯

- [ ] 已发布内容具有唯一版本。
- [ ] 日程任务能够引用具体内容版本。
- [ ] 历史版本能够查询。
- [ ] 内容撤回能够追踪影响范围。
- [ ] 重要内容变更能够重新审核。
