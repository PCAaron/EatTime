# 食刻 — 一期日程生成与调度规则 Spec

- **文档路径**：`specs/04-schedule-rules.md`
- **版本**：V1.0
- **状态**：Draft
- **适用产品**：食刻——孕期与婴幼儿喂养日程助手
- **对应 PRD**：V1.2
- **关联文档**：
  - `specs/01-business-flow.md`
  - `specs/02-data-model.md`
  - `specs/03-content-spec.md`
- **一期目标场景**：
  - 孕 30 周左右的孕晚期用户
  - 2 岁左右幼儿的主要照护者

---

## 1. 文档目标

本文档定义食刻一期日程引擎的业务规则、生成流程、调度策略、状态流转及异常处理机制。

日程引擎需要将用户档案、阶段信息、审核通过的食谱内容、安全约束及用户偏好，转换为未来可执行的餐食与喂养任务。

核心目标：

1. 根据用户档案识别当前适用阶段。
2. 提前生成未来 7 天日程。
3. 按阶段、营养结构和安全约束筛选食谱。
4. 支持食谱替换、任务跳过、顺延及重新生成。
5. 确保已知过敏食物等安全约束无法被普通操作绕过。
6. 保证日程生成幂等，避免重复生成任务。
7. 保留日程生成时的内容版本、规则版本和来源依据。
8. 在候选不足时进行安全降级，而不是降低安全要求强行填满日程。

本文档描述的是产品规则和工程实现约束，不是医学诊疗指南，也不直接定义具体营养处方。

## 2. 一期范围

### 2.1 纳入范围

| 模块     | 一期要求                                          |
| -------- | ------------------------------------------------- |
| 用户档案 | 支持多个孕期/婴幼儿档案，日程生成必须绑定具体档案 |
| 阶段识别 | 孕晚期及 2 岁左右幼儿                             |
| 日程周期 | 每日执行，提前生成未来 7 天                       |
| 食谱筛选 | 根据阶段、内容状态、安全条件筛选                  |
| 营养结构 | 根据专业审核后的阶段营养配置进行匹配              |
| 个性化   | 支持口味、场景、制作难度等非安全偏好              |
| 食谱替换 | 支持主动替换，必须重新执行安全过滤                |
| 任务跳过 | 支持跳过，不产生负向惩罚                          |
| 任务顺延 | 支持调整到后续日期，并校验目标日期适用性          |
| 重新生成 | 支持档案、阶段、内容及规则变化后的重新校验        |
| 版本管理 | 记录内容版本、规则版本及生成快照                  |
| 数据分析 | 记录生成、查看、完成、跳过、替换等事件            |

### 2.2 暂不纳入

- 孕早期、孕中期完整日程覆盖。
- 其他孕周的完整营养方案。
- 0～12 月龄婴儿喂养日程。
- 13～23 月龄、25～36 月龄完整内容覆盖。
- 基于疾病诊断的自动膳食处方。
- 自动判断食物过敏及自动解除过敏禁忌。
- 根据用户身体指标自动调整医学营养治疗方案。
- AI 直接生成并发布生产日程。
- 复杂家庭协作及多照护者任务分配。

后续扩展时应复用日程引擎，不应将一期的阶段规则写死在生成流程中。

## 3. 日程核心概念

### 3.1 日程层级

日程采用以下层级：

```text
Profile
  └── SchedulePlan
        └── ScheduleDay
              └── ScheduleSlot
                    └── ScheduleTask
                          └── Recipe / ContentVersion
```

概念说明：

| 概念           | 定义                         |
| -------------- | ---------------------------- |
| Profile        | 孕期或幼儿档案               |
| SchedulePlan   | 某档案在某一周期内的日程计划 |
| ScheduleDay    | 某个自然日的日程容器         |
| ScheduleSlot   | 某日的餐次或任务槽位         |
| ScheduleTask   | 用户实际执行的任务实例       |
| Recipe         | 食谱内容实体                 |
| ContentVersion | 食谱内容版本                 |
| RuleVersion    | 日程规则版本                 |

实际字段应与 `02-data-model.md` 统一。如果现有数据模型中的实体名称不同，应优先沿用已确定的数据模型，不要在本 Spec 中重复创建同义实体。

### 3.1.1 逻辑实体与持久化映射

完整字段定义以 `02-data-model.md` §6.0 为准；数据库集合命名以 `06-technical-architecture.md` §10 为准。

| 逻辑实体 | 业务职责 | 是否持久化 | 持久化实体 | 数据库集合 |
| --- | --- | --- | --- | --- |
| `SchedulePlan` | 某档案一次未来 7 天生成规划（`generationId`、日期范围、版本上下文） | 否 | 同一 `generationId` 下多条 `ScheduleInstance` | — |
| `ScheduleDay` | 单日日程容器 | 否 | `ScheduleInstance`（`profileId` + `scheduleDate`） | `schedule_instances` / `schedules` |
| `ScheduleSlot` | 模板槽位在某日的展开 | 否 | `ScheduleTask.slotCode`、`mealType` 等 | — |
| `ScheduleInstance` | 档案在某自然日的日程实例 | 是 | `ScheduleInstance` | `schedule_instances` |
| `ScheduleTask` | 用户执行任务 | 是 | `ScheduleTask`（`scheduleId` + `slotCode` 追溯实例与槽位） | `schedule_tasks` |

一期生成未来 7 天：写入/补齐 7 个日期的 `ScheduleInstance` 及各槽位 `ScheduleTask`；幂等与不可覆盖规则见 §6.1、§19。

### 3.2 两个业务域

日程引擎共享基础能力，但孕期与幼儿喂养必须保持独立的业务规则。

| 对比项   | 孕期业务域                 | 幼儿业务域                     |
| -------- | -------------------------- | ------------------------------ |
| 阶段依据 | 孕周、预产期等档案信息     | 出生日期、月龄及适用阶段       |
| 内容依据 | 孕期膳食指南及专业审核内容 | 婴幼儿喂养指南及专业审核内容   |
| 食谱适配 | 孕期阶段适用性             | 年龄、咀嚼吞咽能力及质地适用性 |
| 安全约束 | 孕期饮食安全及用户特殊限制 | 已知过敏、食物安全及进食能力   |
| 个性化   | 口味、制作时间、食材偏好   | 口味、家庭餐场景、制作时间     |
| 任务形式 | 餐食及相关饮食任务         | 家庭餐、加餐及喂养任务         |

不得因为两类用户都存在“早餐、午餐、晚餐”，就将两个业务域的营养规则合并为一套通用规则。

## 4. 中国标准与专业依据管理

本项目涉及孕期营养、幼儿喂养、食物质地和食物过敏。具体营养数值、质地标准及过敏判断规则必须建立来源登记机制。

### 4.1 一期优先参考依据

| 编号    | 标准或指南                                               | 发布机构/来源                        | 适用范围                   | 在系统中的用途               |
| ------- | -------------------------------------------------------- | ------------------------------------ | -------------------------- | ---------------------------- |
| STD-001 | 《中国孕妇、乳母膳食指南（2022）》                       | 中国营养学会                         | 孕期、乳母                 | 孕期膳食结构与食物选择依据   |
| STD-002 | 《中国居民膳食指南（2022）》及孕期妇女平衡膳食宝塔       | 中国营养学会                         | 居民及孕期妇女             | 膳食结构和食物类别参考       |
| STD-003 | 《中国居民膳食营养素参考摄入量》适用版本                 | 中国营养学会                         | 不同年龄和生理阶段         | 营养素参考值和营养目标依据   |
| STD-004 | 《婴幼儿喂养健康教育核心信息》                           | 国家卫生健康委                       | 0～2 岁婴幼儿              | 喂养方式、质地逐步过渡等原则 |
| STD-005 | WS/T 678—2020《婴幼儿辅食添加营养指南》                  | 国家卫生健康相关标准                 | 婴幼儿辅食阶段             | 食物性状、质地及辅食安排参考 |
| STD-006 | 《婴幼儿营养喂养评估服务指南（试行）》                   | 国家卫生健康委                       | 0～3 岁婴幼儿              | 喂养评估与营养管理参考       |
| STD-007 | GB 7718—2025《食品安全国家标准 预包装食品标签通则》      | 国家卫生健康委、国家市场监督管理总局 | 预包装食品标签             | 致敏物质标示信息来源         |
| STD-008 | GB 28050—2025《食品安全国家标准 预包装食品营养标签通则》 | 国家卫生健康委、国家市场监督管理总局 | 预包装食品营养标签         | 食品营养标签数据读取与校验   |
| STD-009 | 《儿童IgE介导食物过敏诊断和管理专家共识》                | 国内相关医学专业组织                 | 儿童食物过敏临床诊断和管理 | 过敏诊断边界与专业审核依据   |

上述依据的定位并不相同：

- 膳食指南用于指导膳食结构和食物选择。
- 营养素参考摄入量用于建立阶段营养目标。
- WS/T 等标准用于提供对应范围内的技术参考。
- GB 食品安全国家标准用于其规定的食品生产、标签等适用范围。
- 临床指南和专家共识用于明确医学诊断及管理边界。

**不得将食品标签标准直接当作人体营养需求标准，也不得将食品致敏物质标签直接当作临床过敏诊断规则。**

### 4.2 标准实施状态管理

标准需要记录发布、实施、修订和废止状态。

特别注意：

- GB 7718—2025 和 GB 28050—2025 已发布，但实施日期为 2027 年 3 月 16 日。
- 在正式实施前，应按当时有效的法规标准执行。
- 不得提前将尚未生效的标准作为已经生效的强制要求。
- 标准更新后，应由专业审核人员判断对食谱、营养数据及规则配置的影响。

### 4.3 来源登记结构

建议建立 `RuleSourceReference`，或复用内容系统中已有的来源实体。

建议字段：

| 字段             | 说明                                                   |
| ---------------- | ------------------------------------------------------ |
| sourceId         | 来源唯一标识                                           |
| title            | 标准/指南名称                                          |
| sourceType       | 国家标准、行业标准、团体标准、指南、专家共识、研究文献 |
| issuer           | 发布机构                                               |
| standardCode     | 标准编号，若有                                         |
| version          | 版本                                                   |
| publishDate      | 发布日期                                               |
| effectiveDate    | 实施日期                                               |
| expiryDate       | 失效日期，若有                                         |
| sourceUrl        | 官方或权威来源                                         |
| applicableDomain | 适用业务域                                             |
| applicableStage  | 适用阶段                                               |
| reviewStatus     | 待审核、已审核、已失效                                 |
| reviewedBy       | 审核人员                                               |
| reviewedAt       | 审核时间                                               |

具体营养数值、质地要求及过敏医学规则，必须能够追溯到对应来源和审核记录。

### 4.4 专业数值配置原则

具体数值不直接写入业务代码。

建议通过版本化配置管理：

```text
NutritionTargetConfig
  - configId
  - domain
  - stage
  - nutrientCode
  - targetValue
  - minValue
  - maxValue
  - unit
  - referenceSourceId
  - referenceVersion
  - reviewStatus
  - effectiveAt
  - expiresAt
```

以上为建议结构，实际字段需与 `02-data-model.md` 统一。

配置要求：

1. 每项数值必须有来源。
2. 每项数值必须有适用阶段。
3. 必须记录单位及计算口径。
4. 必须经过具备相应专业能力的人员审核。
5. 无可靠数值时允许为空。
6. 未审核数据不得参与自动营养匹配。
7. 不得将群体推荐值直接解释为用户个体诊疗建议。

## 5. 阶段识别规则

### 5.1 孕期阶段

一期仅开放孕晚期场景。

阶段识别原则：

- 根据档案中可靠的孕周信息计算当前阶段。
- 孕晚期通常以妊娠 28 周起作为阶段划分依据，最终应与项目采用的专业指南口径保持一致。
- 孕周信息缺失、明显异常或相互矛盾时，不允许自动推断。
- 预产期或孕周发生变化时，应重新计算阶段并校验未来日程。
- 已完成的历史任务保留原始阶段和内容版本。

一期不能因为用户进入孕晚期，就默认其所有特殊饮食需求均已知。

### 5.2 幼儿阶段

一期针对 2 岁左右幼儿。

必须区分：

- 日历年龄/月龄。
- 产品配置的适用阶段。
- 实际咀嚼与吞咽能力。
- 监护人记录的特殊饮食限制。

“2 岁左右”是一期目标用户描述，不应直接将其定义成固定的 24 个月 ± 某个区间。

具体适用月龄范围由专业内容审核人员确定，并在阶段配置中维护。

### 5.3 阶段变化处理

阶段变化后：

1. 计算新阶段。
2. 检查未来未执行任务是否仍适用。
3. 不适用的任务进入待重新校验状态。
4. 重新筛选符合新阶段的食谱。
5. 不修改已经完成的历史任务。
6. 保留原日程与新日程之间的关联关系。

## 6. 日程生成总体流程

### 6.1 生成时机

一期采用：

- 用户完成档案后，首次生成未来 7 天日程。
- 用户首次进入日程页时，如果日程不存在，触发生成。
- 每日定时补齐未来 7 天的日程。
- 用户修改关键档案、安全信息或阶段信息后，触发重新校验。
- 内容或规则发布、撤回时，按影响范围检查未来未执行任务。

所有生成操作都必须支持幂等。

### 6.2 生成流程

```text
开始
  ↓
读取 Profile
  ↓
校验档案完整性
  ↓
识别业务域与当前阶段
  ↓
读取阶段日程模板
  ↓
生成未来 7 天 ScheduleSlot
  ↓
查询审核通过的食谱候选
  ↓
L0 安全规则过滤
  ↓
L1 阶段适用性过滤
  ↓
L2 营养结构匹配
  ↓
L3 个性化排序
  ↓
候选结果校验
  ↓
生成 ScheduleTask
  ↓
保存内容版本与规则版本
  ↓
返回日程
```

### 6.3 规则优先级

| 优先级 | 规则层       | 处理方式                       |
| ------ | ------------ | ------------------------------ |
| L0     | 安全规则     | 硬拦截，不允许普通操作覆盖     |
| L1     | 阶段规则     | 不适用内容不得进入候选池       |
| L2     | 营养结构规则 | 优先匹配专业审核后的营养配置   |
| L3     | 个性化规则   | 只影响候选排序，不改变安全约束 |

执行顺序必须固定。

任何低优先级规则都不能覆盖高优先级规则。

## 7. 日程槽位生成

### 7.1 槽位定义

日程槽位由阶段模板决定，不直接写死在代码中。

建议配置：

```text
ScheduleTemplate
  - templateId
  - domain
  - stage
  - version
  - slots[]
  - effectiveAt
  - reviewStatus
```

槽位建议包含：

```text
ScheduleSlotTemplate
  - slotCode
  - slotName
  - mealType
  - timeRange
  - required
  - candidateCount
  - contentType
  - applicableDomain
```

上述结构为逻辑示意，具体字段以 `02-data-model.md` 为准。

### 7.2 餐次规则

孕期与幼儿业务域分别配置餐次模板。

不在本 Spec 中直接指定：

- 一日必须安排几餐。
- 每餐必须包含多少食材。
- 每餐必须提供多少能量。
- 每日各餐次能量占比。
- 每日具体营养素摄入量。

这些内容应由专业人员根据适用指南、年龄阶段和业务目标审核后形成配置。

### 7.3 槽位生成约束

1. 每个槽位必须绑定一个明确日期。
2. 每个槽位必须绑定业务域及阶段。
3. 必须有明确的内容类型。
4. 必须能追溯到日程模板版本。
5. 不允许将不适用业务域的槽位混入日程。
6. 槽位数量由配置决定，不能通过代码临时补齐。

## 8. 食谱候选筛选规则

### 8.1 候选池基础条件

食谱必须满足：

- 内容状态为已发布。
- 内容审核状态为通过。
- 当前时间位于内容有效期内。
- 食谱适用于当前业务域。
- 食谱适用于当前阶段。
- 食材、制作方式、营养信息等必需字段满足该食谱的审核要求。
- 具备可追溯的内容版本。
- 未被撤回或禁用。

不符合条件的食谱不得进入生产候选池。

### 8.2 筛选顺序

```text
获取已发布食谱
  ↓
内容状态过滤
  ↓
业务域过滤
  ↓
阶段适用性过滤
  ↓
安全约束过滤
  ↓
质地与制作条件过滤
  ↓
营养结构匹配
  ↓
用户偏好过滤/排序
  ↓
生成候选集
```

安全过滤必须在最终候选确定前执行，且替换操作必须重新执行。

### 8.3 候选结果分组

建议将候选分为：

| 类型         | 说明                         |
| ------------ | ---------------------------- |
| Primary      | 满足全部要求的优先候选       |
| Alternative  | 满足安全与阶段要求的替代候选 |
| Insufficient | 候选不足，无法满足完整槽位   |
| Blocked      | 被安全规则或阶段规则拦截     |

不得将 `Blocked` 食谱作为替换候选展示给用户。

## 9. L0 安全规则

### 9.1 安全规则原则

L0 是不可被覆盖的硬约束。

以下操作均不得绕过 L0：

- 自动生成日程。
- 用户主动替换食谱。
- 用户手动选择食谱。
- 日程顺延。
- 日程重新生成。
- 用户偏好调整。
- AI 推荐或内容辅助。

### 9.2 过敏状态处理

沿用产品已确认的四种过敏状态：

| 状态                | 业务含义                     | 日程行为                             |
| ------------------- | ---------------------------- | ------------------------------------ |
| `none_known`        | 用户声明目前没有已知食物过敏 | 按正常流程生成，不代表医学排除过敏   |
| `confirmed_allergy` | 用户声明存在已知过敏食物     | 建立禁忌清单，强制过滤               |
| `observing`         | 正在观察或尝试新食物         | 执行观察流程，避免未经安排的重复尝试 |
| `skipped`           | 暂时跳过过敏信息设置         | 基础日程正常使用，不启动观察流程     |

`none_known` 与 `skipped` 必须区分。

不得将用户跳过过敏信息设置理解为用户确认没有过敏。

### 9.3 已知过敏食物过滤

当状态为 `confirmed_allergy` 时：

1. 读取已知过敏食物清单。
2. 检查食谱主料、辅料及复合食材。
3. 检查食材的过敏原关联标签。
4. 检查已知的交叉接触风险信息。
5. 命中禁忌条件时，直接排除该食谱。
6. 记录命中的安全规则和拦截原因。

**手动替换也必须执行同样的安全检查。**

如果复合食品的配料信息不完整，无法判断是否包含已知禁忌成分，应进入风险待审核或排除流程，不得默认安全。

### 9.4 过敏观察流程

当状态为 `observing`：

- 允许记录新食物尝试。
- 记录食物名称、尝试时间、食用情况、观察反应及反应时间。
- 观察记录必须关联具体食物。
- 出现疑似反应时，停止该食物的自动安排。
- 不自动安排未来重新试吃。
- 不将无反应记录解释为医学上排除过敏。
- 不将产品观察完成解释为医学确认不过敏。

出现严重或可能危及生命的反应时，产品应提示立即寻求紧急医疗帮助。

产品不得通过自动算法判断是否确诊食物过敏，也不得自动解除已记录的过敏禁忌。

### 9.5 安全信息变化

当用户更新过敏信息：

1. 保存新的用户声明及来源。
2. 生成安全信息版本。
3. 重新检查未来未执行任务。
4. 命中禁忌的任务立即标记为待替换或已阻止。
5. 不再允许执行原任务。
6. 为受影响任务生成替换候选。
7. 记录规则触发及任务处理结果。

已经完成的历史任务不应被删除，但可保留新的安全信息及历史记录之间的关系。

## 10. L1 阶段规则

### 10.1 孕期食谱适用性

必须满足：

- 食谱明确标注适用孕期业务域。
- 食谱适用孕晚期阶段。
- 关键食材及制作方式经过孕期适用性审核。
- 特殊饮食限制已经明确。
- 食谱来源及内容版本有效。

### 10.2 幼儿食谱适用性

必须满足：

- 食谱明确标注适用幼儿业务域。
- 食谱适用配置中的目标月龄范围。
- 食谱质地与已审核的年龄/能力适用条件相符。
- 制作方法、食材处理方式及进食安全信息完整。
- 已知过敏食物已排除。

### 10.3 质地匹配

幼儿食谱的质地不能仅由月龄推断。

建议建立受控质地字典，例如：

- 泥糊状
- 细碎状
- 软烂块状
- 可抓握形态
- 家庭膳食适配形态

以上是内容标签示例，不代表官方质地等级，也不能替代专业人员制定的具体标准。

质地匹配需要考虑：

1. 年龄阶段。
2. 咀嚼能力。
3. 吞咽能力。
4. 食材硬度与形态。
5. 是否存在明确的进食安全限制。
6. 食谱制作方式。

对于存在吞咽障碍、特殊疾病或其他特殊进食需求的儿童，普通自动日程不应代替专业评估。

## 11. L2 营养结构匹配

### 11.1 基本原则

营养结构匹配的目标是让日程在整体上符合对应阶段的膳食结构要求，而不是简单地为每一道食谱打营养分数。

营养匹配应基于：

- 阶段营养目标。
- 食物类别分布。
- 食谱营养数据。
- 食材及用量。
- 餐次配置。
- 已审核的专业规则。

### 11.2 营养数据可信度

建议区分：

| 数据状态    | 含义                 | 是否参与自动匹配     |
| ----------- | -------------------- | -------------------- |
| `verified`  | 来源明确且已审核     | 可以                 |
| `estimated` | 估算数据，方法已记录 | 仅按审核规则有限使用 |
| `unknown`   | 缺少可靠数据         | 不参与精确数值匹配   |
| `rejected`  | 数据不可信或已废弃   | 不可以               |

如果关键营养数据为 `unknown`，不得通过估算补齐并宣称满足营养目标。

### 11.3 营养匹配策略

建议分为三个层次：

**第一层：食物结构匹配**

检查食物类别及多样性是否符合当前阶段的审核配置。

**第二层：营养素匹配**

根据可靠的营养数据，检查能量、蛋白质、脂肪、碳水化合物及其他专业审核确定的营养指标。

**第三层：周期平衡**

检查多日食谱的重复程度、食物类别分布及营养结构。

不能只凭单餐数据判断一日或一周膳食是否合理。

### 11.4 营养规则配置

建议使用配置驱动：

```text
NutritionRule
  - ruleId
  - domain
  - stage
  - nutrientCode
  - targetRange
  - calculationScope
  - priority
  - sourceReferenceId
  - sourceVersion
  - reviewer
  - reviewStatus
  - effectiveAt
```

`targetRange` 仅为结构示例。实际数值必须由专业审核人员依据适用指南和参考摄入量确定。

### 11.5 营养匹配失败

如果候选食谱不能满足营养结构：

- 优先尝试其他已审核食谱。
- 尝试调整非安全类偏好。
- 尝试重新组合符合规则的食谱。
- 仍无法满足时，标记候选不足。

不得通过放宽 L0 安全规则或使用未审核食谱来完成营养匹配。

## 12. L3 个性化排序

### 12.1 可参与排序的条件

在满足 L0、L1 和 L2 后，可以考虑：

- 用户口味偏好。
- 不喜欢的食材。
- 制作时间。
- 制作难度。
- 家庭餐适配性。
- 历史替换记录。
- 历史完成情况。
- 食材可获得性（若产品已具备可靠数据）。

### 12.2 个性化规则限制

- 用户偏好不能覆盖已知过敏禁忌。
- 用户偏好不能覆盖阶段限制。
- 用户偏好不能覆盖专业审核的质地要求。
- 历史完成情况不能作为医学适用性判断依据。
- 用户频繁跳过某种食谱，只能用于排序或产品体验优化，不应自动推断医学禁忌。

### 12.3 排序建议

采用可解释的规则评分，而非一期引入复杂机器学习。

例如：

```text
score =
  preferenceScore
  + preparationConvenienceScore
  + varietyScore
  + historyAdjustmentScore
```

所有参与评分的维度必须可解释、可追踪。

安全规则不参与打分，而是先行硬过滤。

## 13. 候选不足与降级处理

### 13.1 候选不足原则

候选不足时，允许返回不完整日程。

禁止：

- 使用未审核食谱。
- 放宽已知过敏禁忌。
- 忽略阶段限制。
- 忽略质地限制。
- 使用未知营养数据伪造营养匹配结果。
- 自动安排存在疑似反应的食物。

### 13.2 降级策略

| 情况                   | 处理方式                         |
| ---------------------- | -------------------------------- |
| 个性化偏好导致候选不足 | 允许放宽非安全偏好               |
| 制作难度导致候选不足   | 允许推荐其他已审核难度的食谱     |
| 同类食谱重复过多       | 尝试其他已审核食物类别           |
| 营养数据不足           | 标记营养匹配不完整，不伪造数值   |
| 阶段候选不足           | 返回待补充内容状态               |
| 安全过滤后无候选       | 保持空缺，提示暂时没有适合的推荐 |
| 质地适用性无法确认     | 不推荐该食谱，进入内容审核       |

### 13.3 用户提示

提示应明确表达：

- 当前槽位暂时没有合适的食谱。
- 不会因为候选不足而降低安全要求。
- 用户可以保留空缺或稍后查看更新。

不应让用户感觉自己没有完成任务，也不应通过惩罚性游戏化机制制造压力。

## 14. 食谱替换规则

### 14.1 替换入口

用户可以从具体日程任务进入替换流程。

替换候选必须来自当前任务对应槽位的有效候选池。

### 14.2 替换流程

```text
用户选择替换
  ↓
读取原任务
  ↓
读取当前档案与阶段
  ↓
读取最新安全信息
  ↓
获取候选食谱
  ↓
执行 L0 安全过滤
  ↓
执行 L1 阶段过滤
  ↓
执行 L2 营养匹配
  ↓
执行 L3 个性化排序
  ↓
用户确认
  ↓
保存新任务关联
  ↓
保留替换记录
```

### 14.3 替换限制

1. 不允许替换成未审核食谱。
2. 不允许替换成不适用当前阶段的食谱。
3. 不允许绕过过敏禁忌。
4. 不允许绕过质地限制。
5. 替换后重新校验该日营养结构。
6. 保留原食谱与新食谱的关联。
7. 历史替换记录不可覆盖删除。

### 14.4 替换数据记录

建议记录：

- originalTaskId
- originalRecipeId
- originalContentVersionId
- replacementRecipeId
- replacementContentVersionId
- replacedAt
- replacedBy
- replacementReason
- ruleVersion
- safetyCheckResult

实际字段与 `02-data-model.md` 统一。

## 15. 任务跳过规则

### 15.1 跳过定义

跳过表示用户主动选择不执行当前任务。

跳过不是失败，不应影响用户的整体进度评价。

### 15.2 跳过行为

- 任务状态更新为 `skipped`。
- 保留原任务和原食谱关联。
- 记录跳过时间。
- 跳过原因可以选填。
- 不自动生成替代任务。
- 不自动扣减游戏化积分。
- 不将跳过行为解释为营养摄入不足的医学结论。

### 15.3 跳过后重新安排

如果用户希望重新安排，应通过顺延或重新生成流程完成，不直接将已跳过任务改成其他日期。

历史跳过记录必须保留。

## 16. 任务顺延规则

### 16.1 顺延定义

顺延表示用户将未执行任务调整到其他日期。

### 16.2 顺延流程

1. 读取原任务。
2. 校验任务当前状态。
3. 确认目标日期。
4. 重新识别目标日期对应的阶段。
5. 重新执行安全过滤。
6. 重新执行内容有效性检查。
7. 重新检查目标日期槽位。
8. 检查营养结构及重复安排。
9. 创建新的任务安排。
10. 保留原任务与新任务的关联。

### 16.3 顺延限制

- 已完成任务不能顺延。
- 已跳过任务不能直接顺延，需先通过明确的重新安排操作。
- 已撤回内容不能顺延。
- 目标日期不适用的食谱不能顺延。
- 顺延后必须重新校验安全条件。
- 不得因为原任务已经生成就跳过目标日期的阶段判断。

### 16.4 顺延与未来 7 天窗口

如果目标日期超出当前 7 天窗口：

- 不立即生成窗口外的正式日程。
- 可以记录用户的顺延意图。
- 到目标日期进入生成窗口时，重新执行完整规则校验。
- 如果届时内容或阶段已变化，应重新匹配。

## 17. 未来 7 天日程生成策略

### 17.1 生成窗口

一期采用滚动窗口：

```text
生成日期：D
日程范围：D 至 D+6
```

以用户档案所在时区的自然日为准。

不得直接使用服务器时区决定用户的日程日期。

### 17.2 每日补齐

每日定时任务检查：

- 当前档案是否有效。
- 当前阶段是否发生变化。
- 未来 7 天是否完整。
- 是否存在未处理的安全规则变化。
- 是否存在已撤回内容。
- 是否需要重新校验未执行任务。

### 17.3 已存在日程处理

生成前检查同一档案、同一日期、同一槽位是否已经存在有效任务。

处理原则：

| 原任务状态 | 生成策略                           |
| ---------- | ---------------------------------- |
| pending    | 根据规则版本和内容状态重新校验     |
| completed  | 保留，不重复生成                   |
| skipped    | 保留，不自动覆盖                   |
| deferred   | 保留顺延关系，按目标日期重新校验   |
| replaced   | 保留替换结果，必要时重新校验       |
| blocked    | 重新寻找安全候选，不直接恢复原任务 |

### 17.4 日程覆盖范围

未来 7 天是默认生成窗口，不代表用户每天必须完成所有槽位。

日程允许存在空缺、跳过和未完成状态。

## 18. 日程重新生成规则

### 18.1 触发条件

以下变化需要重新校验未来未执行任务：

- 用户档案关键字段发生变化。
- 孕周或幼儿阶段发生变化。
- 用户更新过敏信息。
- 用户更新特殊饮食限制。
- 食谱内容被撤回。
- 食谱适用阶段发生变化。
- 安全规则更新。
- 日程模板更新。
- 营养目标配置更新。

### 18.2 重新生成策略

不允许简单删除旧日程并重新创建全部任务。

采用差异化更新：

1. 读取现有日程。
2. 标记已经完成的任务。
3. 保留已经跳过的任务。
4. 保留有效的用户替换记录。
5. 检查未执行任务是否仍然有效。
6. 对无效任务进行阻止或待替换处理。
7. 对缺失槽位生成新任务。
8. 保留原任务与新任务的关联关系。

### 18.3 历史任务

已经完成的任务必须保留：

- 当时的内容版本。
- 当时的规则版本。
- 当时的阶段信息。
- 当时的生成时间。
- 当时的任务状态。

不能因为规则升级而修改历史任务的内容依据。

## 19. 幂等与并发控制

### 19.1 幂等原则

同一个档案、日期、槽位，在同一个有效生成周期内只能存在一个有效任务实例。

建议幂等键：

```text
profileId + scheduleDate + slotCode + generationVersion
```

如果实际数据模型采用其他主键或唯一索引策略，应统一采用数据模型中的实现方式。

### 19.2 幂等要求

- 重复触发生成不能产生重复任务。
- 定时任务与用户主动触发并发时不能重复创建。
- 生成失败后重试不能重复创建已成功的任务。
- 替换操作重复提交不能产生多个有效替换结果。
- 顺延操作重复提交不能生成多个目标任务。

### 19.3 并发处理

建议在云函数中实现：

- 生成请求唯一标识。
- 任务唯一性校验。
- 数据库事务或等效原子操作。
- 并发冲突重试。
- 失败任务补偿机制。

具体实现以微信云开发当前支持的数据库事务能力为准。

## 20. 规则与内容版本管理

### 20.1 版本绑定

每个 ScheduleTask 至少需要能够追溯：

- recipeId
- contentVersionId
- scheduleTemplateVersion
- ruleVersion
- safetyRuleVersion
- nutritionConfigVersion
- generatedAt

若某些版本信息由关联快照统一管理，可以避免在多个字段重复保存，但必须保证历史可追溯。

### 20.2 规则更新

规则更新后：

- 新生成日程使用新版本。
- 未来未执行任务根据影响范围重新校验。
- 已完成历史任务保留旧版本。
- 不得直接覆盖历史规则快照。
- 规则发布必须经过审核和发布审批。

### 20.3 食谱撤回

食谱撤回后：

1. 从新日程候选池移除。
2. 查询未来未执行任务。
3. 对关联任务进行阻止或待替换处理。
4. 不删除历史已完成任务。
5. 记录撤回原因、操作人员和时间。
6. 必要时触发用户通知。

## 21. 异常处理

| 异常场景               | 处理方式                                           |
| ---------------------- | -------------------------------------------------- |
| 档案不存在             | 停止生成并提示创建/选择档案                        |
| 档案信息不完整         | 返回缺失字段，不进行猜测                           |
| 阶段无法识别           | 停止对应业务域自动生成                             |
| 日程模板不存在         | 返回配置缺失并记录错误                             |
| 没有可用食谱           | 返回候选不足                                       |
| 所有食谱被安全规则拦截 | 保持空缺并记录安全拦截                             |
| 内容版本失效           | 不再进入新候选池                                   |
| 安全规则服务异常       | 不得跳过安全检查，应停止生成                       |
| 营养配置缺失           | 不执行精确营养匹配，按审核过的降级策略处理         |
| 数据库写入失败         | 记录失败并支持幂等重试                             |
| 并发生成               | 通过唯一性约束避免重复任务                         |
| 用户重复操作           | 返回当前有效结果                                   |
| 时区信息缺失           | 使用明确的产品默认时区策略或要求补充，不得随意切换 |

安全规则服务不可用时，必须采用 Fail Closed（失败关闭）原则，不能以“先生成日程”为理由跳过安全校验。

## 22. 日程状态机

> **持久化权威**：`ScheduleTask.status` 及 `statusReason` 以 `02-data-model.md` §6.2、§6.2.1 为准。本章 `blocked`、`expired` 为**流程/UI 语义**，落库时映射为 `invalidated`（或 `cancelled`）并写入 `statusReason`。

### 22.1 任务状态（持久化枚举）

与 02 一致：

| 状态 | 含义 |
| --- | --- |
| `pending` | 待执行 |
| `completed` | 已完成 |
| `skipped` | 已跳过 |
| `deferred` | 已顺延 |
| `replaced` | 已替换（原任务保留，新推荐另记） |
| `cancelled` | 已取消，不再执行 |
| `invalidated` | 因安全、内容、规则或计划窗口等原因失效 |

### 22.1.1 流程语义映射（非持久化 status 值）

| 流程称呼 | 落库 `status` | `statusReason` |
| --- | --- | --- |
| `blocked` | `invalidated` | `safety_blocked` |
| `expired` | `invalidated` 或 `cancelled` | `schedule_expired` |

### 22.2 状态流转

```text
pending
  ├── completed
  ├── skipped
  ├── deferred
  ├── replaced
  └── invalidated（流程中称 blocked：安全/内容阻断）

deferred
  ├── pending（目标日期重新生成并通过校验）
  ├── invalidated
  └── invalidated（流程中称 expired：schedule_expired）

replaced
  └── 保留替换关系，不覆盖原始记录

completed
  └── 终态

skipped
  └── 保留历史状态，通过新操作创建新的安排

invalidated
  └── 重新通过安全与阶段校验后创建新的有效任务（原任务保留审计）
```

持久化不得再使用 `blocked`、`expired` 作为 `ScheduleTask.status` 字段值。

实际状态机以 `02-data-model.md` §6.2.1 为准。

## 23. 日程引擎接口边界

### 23.1 输入

- 档案信息
- 阶段信息

- 特殊饮食限制
- 用户偏好
- 日程模板版本
- 内容版本集合
- 安全规则版本
- 营养配置版本

### 23.2 输出

```text
ScheduleGenerationResult

  - domain
  - scheduleRange
  - ruleVersion
  - templateVersion
  - generatedAt
  - status
  - days[]
  - warnings[]
  - blockedItems[]
  - insufficientSlots[]
```

实际字段需与现有数据模型及接口规范统一。

### 23.3 模块职责

| 模块                    | 职责                       |
| ----------------------- | -------------------------- |
| ProfileService          | 档案读取与完整性检查       |

## 24. 数据埋点

一期至少记录以下事件：

| 事件                            | 触发时机         | 关键属性                               |
| ------------------------------- | ---------------- | -------------------------------------- |
| schedule_generated              | 日程生成成功     | profileId、domain、stage、generationId |
| schedule_generation_failed      | 日程生成失败     | errorCode、failureReason               |
| schedule_viewed                 | 用户查看日程     | profileId、scheduleDate                |
| task_completed                  | 任务完成         | taskId、recipeId                       |
| task_skipped                    | 任务跳过         | taskId、reason                         |
| recipe_replaced                 | 食谱替换         | originalRecipeId、replacementRecipeId  |
| schedule_deferred               | 任务顺延         | taskId、targetDate                     |
| schedule_regenerated            | 日程重新生成     | triggerType、ruleVersion               |
| safety_rule_triggered           | 安全规则触发     | ruleId、action、domain                 |
| schedule_candidate_insufficient | 候选不足         | slotCode、reason                       |
| stage_changed                   | 阶段变化         | oldStage、newStage                     |
| content_withdrawn               | 内容撤回影响任务 | recipeId、affectedTaskCount            |

埋点应遵循数据最小化原则。

过敏信息及其他健康相关数据属于敏感信息，应严格限制采集、访问和使用范围，不得默认用于广告画像或无关商业分析。

## 25. 日程生成验收标准

### 25.1 基础生成

- [ ] 孕晚期档案可以生成对应日程。
- [ ] 2 岁左右幼儿档案可以生成对应日程。
- [ ] 不同档案之间的日程相互隔离。
- [ ] 首次建档后能够生成未来 7 天日程。
- [ ] 每日定时任务可以补齐未来 7 天。
- [ ] 用户时区与自然日计算正确。

### 25.2 安全规则

- [ ] `none_known` 与 `skipped` 能正确区分。
- [ ] `confirmed_allergy` 能建立禁忌清单。
- [ ] 已知过敏食物不能进入自动候选池。
- [ ] 手动替换不能绕过过敏过滤。
- [ ] 过敏信息修改后能重新校验未来任务。
- [ ] 疑似反应食物停止自动安排。
- [ ] 不会因观察记录无反应而自动解除禁忌。
- [ ] 安全规则服务异常时停止生成。

### 25.3 阶段与营养

- [ ] 阶段不适用的食谱不能进入候选池。
- [ ] 幼儿食谱质地与已审核的适用条件匹配。
- [ ] 未审核食谱不能进入生产候选池。
- [ ] 未核验营养数据不会被伪装成精确营养数据。
- [ ] 营养目标能追溯来源及配置版本。
- [ ] 候选不足时不降低安全规则。

### 25.4 任务操作

- [ ] 用户可以替换食谱。
- [ ] 用户可以跳过任务。
- [ ] 用户可以顺延任务。
- [ ] 顺延时重新执行阶段及安全校验。
- [ ] 已完成任务不能被普通操作覆盖。
- [ ] 历史操作记录可追溯。

### 25.5 幂等与版本

- [ ] 重复生成不会产生重复任务。
- [ ] 并发生成不会产生重复任务。
- [ ] 内容撤回后不会进入新候选池。
- [ ] 历史任务保留原内容版本。
- [ ] 新规则版本只影响新生成及需要重新校验的任务。
