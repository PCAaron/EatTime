## 1. 文档目标

本文档定义食刻一期安全规则中心的业务边界、数据结构、规则分类、判断流程、审核机制及其与日程引擎的接口约束。

安全规则中心负责回答以下问题：

1. 某项食材或食谱是否存在已知安全限制？
2. 当前用户是否记录了相关过敏或特殊饮食限制？
3. 食谱是否适用于当前孕期或幼儿阶段？
4. 食材的处理方式、质地及进食形式是否满足已审核的安全要求？
5. 是否存在复合食材、标签缺失或交叉接触等不确定风险？
6. 用户更新安全信息后，哪些未来任务需要阻止或重新生成？
7. 哪些情况必须停止自动推荐并提示用户寻求专业帮助？

核心原则：

**安全规则优先于营养匹配、个性化排序、用户偏好及游戏化机制。**

任何低优先级业务逻辑都不能覆盖安全规则。

本文档属于产品与工程规则规范，不是医学诊断指南、临床治疗方案或营养处方。

## 2. 一期安全范围

### 2.1 纳入范围

| 安全领域     | 一期要求                                     |
| ------------ | -------------------------------------------- |
| 孕期饮食安全 | 对经过审核的孕期饮食风险进行规则过滤         |
| 幼儿进食安全 | 管理年龄适用性、食物形态、质地和进食照护要求 |
| 食物过敏     | 记录用户声明、禁忌食物及观察状态             |
| 过敏原映射   | 建立食材、复合食材与过敏原之间的关系         |
| 交叉接触     | 记录已知生产加工或厨房交叉接触风险           |
| 特殊饮食限制 | 支持专业审核的特殊限制配置                   |
| 内容审核     | 安全信息必须经过专业审核                     |
| 日程阻断     | 不安全内容不得进入候选池或继续执行           |
| 安全审计     | 记录规则命中、阻断原因及处理过程             |
| 版本管理     | 安全规则和安全信息均可追溯版本               |

### 2.2 暂不纳入

- 自动诊断食物过敏。
- 自动解读过敏原检测报告并作出临床诊断。
- 自动判断儿童是否已经脱敏。
- 自动制定食物激发试验或再次尝试方案。
- 自动判断严重过敏反应的医学分级。
- 自动替代医生处理特殊疾病或特殊医学营养需求。
- 自动制定妊娠期疾病的治疗性膳食。
- 通过 AI 判断某种食物对某个用户是否绝对安全。
- 对食物安全性作出超出内容来源证据的承诺。

## 3. 安全规则设计原则

### 3.1 安全规则独立于日程引擎

日程引擎负责安排什么内容，安全规则中心负责判断哪些内容允许进入候选池。

两者职责必须分离：

| 模块         | 主要职责                     |
| ------------ | ---------------------------- |
| 内容中心     | 管理食材、食谱及其安全属性   |
| 用户安全档案 | 管理用户声明的过敏及特殊限制 |
| 安全规则中心 | 判断内容是否符合安全条件     |
| 日程引擎     | 根据安全校验结果生成日程     |
| 审计中心     | 记录规则命中、拦截及操作行为 |

不得在多个页面或云函数中分别实现一套不一致的过敏判断逻辑。

### 3.2 规则优先级

| 优先级 | 规则类型                     | 处理方式                   |
| ------ | ---------------------------- | -------------------------- |
| S0     | 紧急风险及明确禁止条件       | 立即阻断相关自动安排       |
| S1     | 用户已声明的过敏禁忌         | 硬过滤                     |
| S2     | 已审核的阶段性安全限制       | 硬过滤或按规则限制         |
| S3     | 食材、加工及交叉接触不确定性 | 按风险配置阻断或人工审核   |
| S4     | 普通饮食偏好                 | 仅用于排序，不属于安全规则 |

S0～S3 均不能被普通用户偏好覆盖。

特别注意：上述 S0～S4 是食刻内部产品规则优先级，不是国家标准或临床风险分级。

### 3.3 安全判断结果

统一使用明确的判断结果：

| 结果              | 含义                     | 日程行为               |
| ----------------- | ------------------------ | ---------------------- |
| `allow`           | 满足当前已配置的安全条件 | 可以进入后续筛选       |
| `block`           | 命中明确禁止条件         | 不允许推荐或安排       |
| `review_required` | 信息不足，需要专业审核   | 不进入自动推荐池       |
| `restricted`      | 满足受限使用条件         | 仅在规则允许的场景使用 |
| `not_applicable`  | 当前规则不适用于该业务域 | 继续其他适用规则判断   |

`allow` 只表示通过当前产品规则校验，不代表医学上绝对安全。

### 3.4 安全信息不完整时的处理

以下情况不能默认安全：

- 食谱缺少关键食材。
- 复合食材配料信息不完整。
- 食材过敏原映射缺失。
- 食谱质地适用性未审核。
- 食谱存在已知交叉接触风险但信息不完整。
- 规则版本失效。
- 安全规则服务异常。

处理方式应根据具体风险类型决定：

- 对已知禁忌相关的未知信息，阻断该候选。
- 对幼儿进食安全关键字段缺失的食谱，阻断该候选。
- 对专业审核尚未完成的特殊内容，进入待审核状态。
- 对安全规则服务整体异常，停止本次自动生成。

不得用“没有发现风险”替代“已经完成安全校验”。

## 4. 中国标准与专业依据

安全规则必须有可追溯的来源。

不同来源适用于不同业务问题，不能将食品标签、食品卫生标准和医学诊断指南混为一谈。

| ------------ | --------------------------------------------------- | ------------------------------------ | --------------------- | -------------------------------- |

### 4.2 特别说明：GB 7718—2025 的使用边界

GB 7718—2025 规定了预包装食品的标签要求，其中包括致敏物质标示要求。

标准列出的八大类致敏物质为：

1. 含有麸质的谷物及其制品。
2. 甲壳纲类动物及其制品。
3. 鱼类及其制品。
4. 蛋类及其制品。
5. 花生及其制品。
6. 大豆及其制品。
7. 乳及乳制品（包括乳糖）。
8. 坚果及其果仁类制品。

标准还涉及生产加工过程中可能带入致敏物质时的预防性提示信息。

系统使用时必须遵守以下边界：

- 八大类是该标准规定的预包装食品标签致敏物质标示范围，不是完整的医学过敏原清单。
- 其他食物也可能引起个体过敏反应。
- 不能因为某项食材未出现在八大类中，就判断其不会引起过敏。
- 不能因为包装没有标注“可能含有”，就判断不存在交叉接触风险。
- 不能仅凭包装标签判断用户是否存在临床食物过敏。
- 对用户已明确声明的其他过敏食物，仍应建立独立禁忌记录。

GB 7718—2025 应作为预包装食品信息读取与标示规则的依据，不得直接转化为产品唯一的过敏原判断字典。

### 4.3 医学诊断依据的使用边界

儿童食物过敏的医学诊断需要结合临床病史、症状表现及专业检查。

《儿童IgE介导食物过敏诊断和管理专家共识》特别强调，不能脱离临床病史过度解读过敏原检测结果。

因此：

- 产品不能仅凭用户上传的检测结果自动判定过敏。
- 产品不能仅凭某次食用后无明显反应判定不过敏。
- 产品不能自行判断某个孩子是否已经耐受某种食物。
- 产品不能根据 AI 分析结果解除已记录的禁忌。
- 食物重新引入、激发试验及脱敏相关安排必须由专业医疗人员决定。

### 4.4 来源版本管理

每条安全规则必须绑定依据：

- sourceId
- sourceVersion
- sourceType
- applicableDomain
- applicableStage
- applicableCondition
- reviewer
- reviewedAt
- effectiveAt
- expiryDate

标准或指南发生更新后，应重新评估受影响的规则和食谱。

不能仅更新来源名称，而不检查原规则是否仍然适用。

## 5. 安全规则数据模型

> **持久化权威**：`specs/02-data-model.md` §7.0。本节为规则执行视角的逻辑模型；`AllergyRestriction` 等名称若与 02 实体不同，按 §7.0 映射表转换为持久化读写。

以下是建议的逻辑模型。实际字段需要与 `02-data-model.md` 和 `03-content-spec.md` 合并，避免重复建设。

### 5.1 SafetyRule

安全规则主表。

| 字段             | 类型建议 | 说明             |
| ---------------- | -------- | ---------------- |
| ruleId           | string   | 规则唯一标识     |
| ruleCode         | string   | 规则编码         |
| ruleName         | string   | 规则名称         |
| ruleType         | enum     | 规则类型         |
| severity         | enum     | 内部规则严重程度 |
| priority         | number   | 执行优先级       |
| applicableDomain | array    | 适用业务域       |
| applicableStage  | array    | 适用阶段         |
| condition        | object   | 规则条件         |
| action           | enum     | 规则执行动作     |
| messageCode      | string   | 用户提示编码     |
| sourceReferences | array    | 依据来源         |
| reviewStatus     | enum     | 审核状态         |
| version          | string   | 规则版本         |
| effectiveAt      | datetime | 生效时间         |
| expiresAt        | datetime | 失效时间         |
| createdBy        | string   | 创建人           |
| reviewedBy       | string   | 审核人           |
| publishedAt      | datetime | 发布时间         |

### 5.2 UserSafetyProfile

用户安全档案（**持久化字段以 `specs/02-data-model.md` §7.0.1 为唯一权威**；集合 `user_safety_profiles`）。

一个 `Profile` 对应一条 `UserSafetyProfile`，不允许将不同孕期或幼儿档案的过敏信息混用。

**规范持久化字段**（与 02 §7.0.1 一致，不得另起字段名）：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `_id` | string | 安全档案 ID |
| `profileId` | string | 对应业务档案 |
| `profileType` | enum | `pregnancy` / `child`（02 规范名；勿使用 `domain` 作为持久化字段名） |
| `allergyStatus` | enum | 四种过敏状态，**唯一存储归属** |
| `declaredRestrictions` | array | 用户声明的额外限制，元素结构见 02 §7.0.3 |
| `informationSource` | string | 信息来源（02 规范名；勿使用 `source` 作为档案级字段名） |
| `declaredAt` | datetime | 可选，首次完成过敏信息声明时间 |
| `version` | number | 安全档案版本 |
| `updatedAt` | datetime | 最近更新时间 |
| `updatedBy` | string | 修改来源 |

**只读查询投影**（`derived / read-only projection`，**不得**与 `AllergyItem` / `FoodObservation` 双写）：

| 投影名 | 来源实体 | 说明 |
| --- | --- | --- |
| `knownAllergies` | `AllergyItem`（`profileId` + `status=active`） | 列表/详情展示用；S1 硬过滤与写入以 `allergy_items` 为准；`reviewStatus` 不改变是否过滤 |
| `observations` | `FoodObservation`（`profileId`） | 列表/详情展示用；写入以 `food_observations` 为准 |

过敏状态沿用：

- `none_known`
- `confirmed_allergy`
- `observing`
- `skipped`

其中 `confirmed_allergy` 是产品中的业务状态名称，表示存在需要按禁忌处理的用户声明，不代表食刻已经完成医学诊断。

### 5.3 AllergyRestriction

过敏禁忌记录（**逻辑命名**；**持久化实体为 `AllergyItem`**，集合 `allergy_items`，字段与逐字段映射见 **02 §7.2**）。

| 字段              | 说明                               |
| ----------------- | ---------------------------------- |
| restrictionId     | 禁忌记录 ID（→ `AllergyItem._id`） |
| profileId         | 对应业务档案（→ `AllergyItem.profileId`） |
| foodItemId        | 对应食材（→ `AllergyItem.foodItemId`，条件必填） |
| foodName          | 食物名称（→ `AllergyItem.foodName`；无 `foodItemId` 时必填，见 §5.3.1） |
| allergenId        | 对应过敏原（→ `AllergyItem.allergenId`，可选） |
| restrictionType   | 食物、食材类别或其他限制（→ **V1 无独立持久化字段**；食物级以 `foodItemId`/`allergenId`/`foodName` 表达；类别级 `DECISION_REQUIRED`，见 02 §7.2） |
| declarationType   | 声明/确认性质（→ `AllergyItem.declarationType`：`user_reported` / `professionally_confirmed`） |
| declarationSource | 信息来源（→ `AllergyItem.source`；**不得**与 `declarationType` 合并） |
| evidenceReference | 可选的依据引用（→ `AllergyItem.evidenceReference`） |
| status            | 限制是否生效（→ `AllergyItem.status`：`active` / `inactive`） |
| reviewStatus      | 专业复核进度（→ `AllergyItem.reviewStatus`；**不**决定 S1 是否硬过滤） |
| declaredAt        | 声明时间（→ `AllergyItem.createdAt`） |
| updatedAt         | 更新时间（→ `AllergyItem.updatedAt`） |
| notes             | 用户补充信息（→ `AllergyItem.notes`） |

**逐字段处理结论**（与 02 §7.2 映射表一致）：除 `restrictionType` 类别级能力为 `DECISION_REQUIRED` 外，上表字段均为 `MAPPED` 或 `RETAINED`（`profileId`、`foodItemId`、`allergenId` 为规范持久化字段 `RETAINED`）。

要求：

1. 用户声明必须保留原始含义。
2. 不允许自动把用户声明升级为医学确诊（`declarationType` 不得自动变为 `professionally_confirmed`）。
3. 不允许 AI 自动解除禁忌。
4. 解除禁忌必须经过明确用户操作（`status=inactive`），并按产品定义的专业安全流程处理。
5. 已失效记录（`status=inactive`）仍应保留历史审计信息。
6. 用户新增已知过敏项时默认 `status=active`；不得因等待专业复核而暂时放开硬过滤。

### 5.3.1 S1 用户过敏禁忌硬过滤

与 §3.2 S1 及 02 §7.2 一致；日程引擎与安全规则中心**必须**共用下列规则，不得在 UI 或云函数中另写一套。

**有效禁忌集合**：

- 查询条件：`AllergyItem.profileId` = 当前档案且 `AllergyItem.status` = `active`。
- **不**使用 `reviewStatus`、`declarationType` 或 `source` 作为是否进入 S1 的判断条件。

**候选食谱/食材命中**（满足任一即 `block`）：

1. 食谱（含配料展开）关联的 `foodItemId` 与禁忌项 `foodItemId` 相同。
2. 食谱关联食材经已审核 `FoodAllergen` 映射，与禁忌项 `allergenId` 相同。
3. 禁忌项仅有 `foodName`（或映射待复核）：按产品定义的保守文本/别名匹配规则命中该食物或其已审核别名；**不得**因 `reviewStatus=pending_review` 跳过。
4. V1 **不支持**类别级 `restrictionType` 的自动硬过滤；若未来扩展须单独产品决议并更新 02/05。

**明确问答**：

| 问题 | 结论 |
| --- | --- |
| 用户声明已知过敏后是否立即硬过滤？ | **是**（创建时 `status=active`） |
| `reviewStatus=pending_review` 时是否仍硬过滤？ | **是**（当 `status=active`） |
| `user_reported` 与 `professionally_confirmed` 是否影响生效？ | **否**（仅标注与流程） |
| 如何解除限制？ | 用户明确操作置 `status=inactive`（及 SAF-10 等专业流程）；禁止 AI 自动解除 |
| 限制变更后是否重新校验未执行日程？ | **是**（§14、02 §7.0.1） |

**变更触发**：`AllergyItem` 的 `status`、`foodItemId`、`allergenId`、`foodName` 或关联 `UserSafetyProfile.allergyStatus` 变更后，须重新校验未来未执行 `ScheduleTask`。

### 5.4 FoodAllergen

过敏原字典（**持久化**：`FoodAllergen`，集合 `food_allergens`，见 02 §7.0.2）。

| 字段             | 说明              |
| ---------------- | ----------------- |
| allergenId       | 过敏原 ID         |

| allergenName     | 标准名称          |

注意：

- 过敏原字典与 GB 7718 标签分类不是同一个概念。
- 过敏原字典应支持扩展。
- 食材、食材类别、复合食品之间应建立关联。
- 不得仅根据名称相似度自动建立生产级过敏原映射。

## 6. 食材与过敏原管理

### 6.1 受控字典原则

食材名称不能直接作为安全判断的唯一依据。

例如：

- 牛奶、乳粉、乳清粉等可能属于不同食材记录，但需要关联到相应乳类信息。
- 花生油、花生酱等需要根据具体成分和加工信息维护关系。
- 含有多种原料的复合食品需要展开配料信息。
- 食材别名、地方名称和商品名称需要建立标准映射。

以上仅为数据建模示例，具体映射需要专业审核。

### 6.2 食材关系

建议支持以下关系：

```text
FoodItem
  ├── hasAllergen
  ├── derivedFrom
  ├── containsIngredient
  ├── belongsToCategory
  └── hasCrossContactRisk
```

例如，某个复合食材可以关联多个基础食材和过敏原。

关系需要具备：

- 关系类型。
- 关联来源。
- 可信状态。
- 审核人员。
- 版本信息。

### 6.3 复合食材处理

复合食材是安全过滤的重要风险点。

处理原则：

1. 能获取完整配料时，展开所有可识别成分。
2. 将成分映射到标准食材字典。
3. 关联已知过敏原。
4. 记录标签中明确提示的致敏物质。
5. 记录已知的交叉接触提示。
6. 缺少关键配料信息时，不能默认不含相关过敏原。
7. 无法判断是否满足用户禁忌时，阻断相关候选并进入审核流程。

### 6.4 信息可信度

建议使用：

| 状态            | 含义               | 处理方式                   |
| --------------- | ------------------ | -------------------------- |
| `verified`      | 来源明确并经过审核 | 可用于规则判断             |
| `declared`      | 用户主动声明       | 按用户声明的安全约束处理   |
| `label_derived` | 从食品标签读取     | 作为配料和标签信息来源     |
| `inferred`      | 根据名称或关系推测 | 不得单独作为安全放行依据   |
| `unknown`       | 未知               | 按对应风险规则阻断或待审核 |
| `rejected`      | 已被审核否定       | 不参与规则判断             |

不能把 `inferred` 当成 `verified`。

## 7. 过敏状态与业务规则

### 7.1 四种状态定义

| 状态                | 用户含义                     | 系统行为         |
| ------------------- | ---------------------------- | ---------------- |
| `none_known`        | 用户声明目前没有已知食物过敏 | 正常生成基础日程 |
| `confirmed_allergy` | 用户声明存在需要回避的食物   | 启用禁忌过滤     |
| `observing`         | 用户正在观察或记录新食物     | 启用观察记录     |
| `skipped`           | 暂时不填写，之后再设置       | 基础功能正常使用 |

`none_known` 不代表医学上排除了所有食物过敏。

`skipped` 不代表用户确认没有过敏。

### 7.2 状态转换

```text
首次设置
  ├── none_known
  ├── confirmed_allergy
  ├── observing
  └── skipped

none_known
  ├── confirmed_allergy
  ├── observing
  └── skipped

skipped
  ├── none_known
  ├── confirmed_allergy
  └── observing

observing
  ├── none_known
  ├── confirmed_allergy
  └── skipped

confirmed_allergy
  ├── 保持禁忌
  └── 经过明确处理后更新状态
```

状态转换不能仅靠定时任务或 AI 自动执行。

### 7.3 用户声明处理

当用户选择 `confirmed_allergy`：

1. 选择已知过敏食物。
2. 支持补充其他食物名称。
3. 保存用户声明。
4. 映射到标准食材或过敏原字典。
5. 对无法映射的食物保留原始文本。
6. 无法准确映射时：`status` 仍为 `active` 并启用过滤；`reviewStatus=pending_review` 供专业人员后续复核映射。
7. 启用相关食谱过滤（S1，见 §5.3.1）。
8. 重新检查未来未执行任务。

不能因为某个用户声明的食物尚未匹配到字典，就忽略该声明。

### 7.4 未知过敏信息

当用户选择 `skipped`：

- 不阻断建档。
- 不阻断基础日程。
- 不启动食物观察任务。
- 不展示已确认无过敏的结论。
- 可以在后续设置入口中补充信息。

不应通过强制弹窗或惩罚机制要求用户完成过敏信息填写。

## 8. 新食物观察与疑似反应处理

### 8.1 观察记录

观察记录是用户记录行为，不是医学检测或临床观察试验。

建议字段：

| 字段                | 说明                           |
| ------------------- | ------------------------------ |
| observationId       | 观察记录 ID                    |
| profileId           | 对应幼儿档案                   |
| foodItemId          | 对应食物                       |
| attemptedAt         | 尝试时间                       |
| consumptionStatus   | 未食用、少量、已食用等用户记录 |
| reactionStatus      | 无明显反应、疑似反应、未记录   |
| reactionDescription | 用户描述                       |
| reactionTime        | 用户记录的反应时间             |
| createdAt           | 创建时间                       |

不得要求用户填写医学上无法自行判断的指标。

### 8.2 观察记录的限制

- 产品不能把观察过程设计成自动食物激发试验。
- 不应要求用户按照产品指定剂量或时间进行试吃。
- 不应要求用户在出现疑似反应后继续尝试。
- 不应将一次无明显反应记录解释为食物安全证明。
- 不应自动安排未来重复尝试。
- 不应通过积分奖励鼓励用户尝试未经专业建议的食物。

### 8.3 疑似反应处理

当用户记录疑似反应：

1. 保存用户原始描述。
2. 将对应食物标记为疑似风险。
3. 停止该食物的自动安排。
4. 检查未来未执行日程。
5. 将相关任务阻断或标记为待处理。
6. 提示用户联系专业医疗人员评估。
7. 不自动安排重新尝试。
8. 保留完整的记录及处理日志。

这里的“疑似风险”是产品保护机制，不代表医学确诊。

### 8.4 严重反应提示

当用户描述可能涉及严重或危及生命的症状时：

- 立即展示紧急求助提示。
- 提醒用户优先联系当地急救服务或立即寻求急诊医疗帮助。
- 不应继续展示普通食谱推荐作为当前页面的主要内容。
- 不应通过问答流程拖延用户寻求紧急帮助。
- 不由产品判断是否需要等待观察。

具体症状识别词典和提示内容应由专业医疗人员审核。

## 9. 幼儿进食安全规则

### 9.1 基本原则

幼儿食谱必须考虑食材营养之外的进食安全。

安全审核至少包含：

- 食材本身的风险。
- 食物大小和形态。
- 软硬程度。
- 是否容易造成噎食。
- 制作方式。
- 是否需要成人协助。
- 是否符合当前阶段的进食能力。

### 9.2 官方依据中的明确提示

国家卫生健康委《婴幼儿喂养健康教育核心信息》指出：

- 2 岁后幼儿可食用家庭膳食，但仍需注意少盐少糖等原则。
- 婴幼儿进食需要成人看护。
- 进食时不应逗笑、打闹。
- 整粒花生、坚果、果冻等存在吸入气管造成窒息的风险，应避免给婴幼儿食用。

该文件可作为一期幼儿安全内容的基础依据。

### 9.3 食谱质地规则

质地必须使用受控标签，不允许内容编辑人员随意创造新等级。

可建立的标签示例：

- 泥糊状。
- 细碎状。
- 软烂块状。
- 可抓握形态。
- 家庭膳食适配形态。

以上为系统标签示例，不是官方质地分级。

具体质地标准、适用年龄及食材形态要求，需要专业人员结合适用指南审核。

### 9.4 食材形态审核

食谱需要描述关键食材的处理方式，例如：

- 是否去除不适宜食用的部分。
- 是否需要充分煮熟。
- 是否需要切碎或改变形态。
- 是否存在整粒、坚硬、黏性或其他进食风险。
- 是否需要成人全程看护。

不能只记录食材名称，而忽略最终端上餐桌的实际形态。

### 9.5 进食照护提示

适用食谱可以关联照护提示：

- 进食时保持安静。
- 由成人看护。
- 不在跑跳、打闹时进食。
- 按照经过审核的食物形态和制作方式准备。

提示应根据食谱实际情况展示，不需要每道食谱重复展示所有通用提示。

### 9.6 特殊进食能力

当用户记录儿童存在吞咽困难、明显咀嚼障碍或其他特殊进食问题时：

- 不继续使用普通年龄匹配规则作为唯一依据。
- 暂停相关食谱自动推荐，或切换到经过专业审核的受限内容。
- 提示监护人寻求专业评估。
- 不由产品自动调整食物质地来替代专业建议。

## 10. 孕期饮食安全规则

### 10.1 基本原则

孕期安全规则需要区分：

1. 食材本身的安全属性。
2. 食材的储存和加工条件。
3. 食品污染及食源性风险。
4. 孕期特殊适用限制。
5. 用户已记录的个体饮食限制。

不能仅依据“孕晚期”标签，就认为所有孕妇都适用同一套特殊饮食规则。

### 10.2 食谱审核要求

孕期食谱至少需要审核：

- 食材来源是否明确。
- 是否存在已知食品安全风险。
- 是否涉及生食或未充分熟制食材。
- 是否存在未经审核的特殊食材。
- 储存、清洗及加工方式是否清晰。
- 是否存在用户已声明的特殊饮食限制。
- 是否符合孕期内容适用性要求。

具体哪些食材需要限制、限制条件和适用范围，应根据有效的中国标准、指南及专业审核结果建立规则。

不得由开发人员自行维护医学性质的孕期禁食清单。

### 10.3 加工与储存要求

食谱制作说明应包含必要的食品卫生信息：

- 食材清洁处理要求。
- 生熟食材分开处理要求。
- 必要的充分加热要求。
- 易腐食品的合理储存要求。
- 不适宜食用的变质食材识别与处理提示。

具体加工参数及储存时限必须引用适用的食品安全标准或经过专业审核的操作规范，不得自行填写未经验证的数值。

### 10.4 特殊孕期情况

以下情况不应由普通日程规则自行给出治疗性饮食方案：

- 妊娠期糖尿病。
- 妊娠期高血压相关特殊饮食管理。
- 肾脏疾病相关饮食管理。
- 明确的营养不良或特殊营养需求。
- 医生要求限制或增加特定营养素的情况。
- 其他需要临床营养干预的情况。

一期建议：

- 允许用户记录相关特殊情况。
- 将其作为安全档案中的特殊限制。
- 提示用户按照医生或临床营养师建议管理饮食。
- 对没有专业审核规则覆盖的场景，停止自动生成相关特殊饮食建议。
- 不使用普通食谱替代临床营养治疗方案。

## 11. 交叉接触与复合食品安全

### 11.1 交叉接触定义

交叉接触是指食物在生产、储存、运输或加工过程中，意外接触其他可能引起过敏的成分。

它与用户主动添加某种食材不是同一概念。

### 11.2 信息来源

可维护的信息包括：

- 预包装食品标签提示。
- 生产商提供的配料和生产信息。
- 食材供应商提供的信息。
- 内容审核人员确认的信息。
- 用户主动提供的信息。

不同来源必须保留来源类型，不能混为一谈。

### 11.3 风险状态

建议：

| 状态            | 说明                                                     | 处理方式                           |
| --------------- | -------------------------------------------------------- | ---------------------------------- |
| `known_clear`   | 有明确、可靠的信息支持当前检查范围内未发现相关成分或风险 | 按规则继续判断                     |
| `known_risk`    | 已知存在相关过敏原或交叉接触风险                         | 命中禁忌时阻断                     |
| `possible_risk` | 标签或生产信息提示可能存在                               | 根据用户禁忌及审核规则阻断或待审核 |
| `unknown`       | 无法获取必要信息                                         | 不得默认安全                       |

`known_clear` 不代表医学意义上的绝对无过敏风险。

### 11.4 标签信息处理

对于预包装食品：

1. 记录食品名称和配料表。
2. 记录标签中明确标示的致敏物质。
3. 记录预防性交叉接触提示。
4. 保存标签来源或图片。
5. 记录读取时间及审核状态。
6. 当产品配料或标签版本变化时重新审核。

不能因为标签没有预防性提示，就推断生产过程中不存在交叉接触。

## 12. 特殊饮食限制管理

除过敏外，还可能存在其他限制。

建议统一管理：

| 类型              | 示例                     | 管理方式                   |
| ----------------- | ------------------------ | -------------------------- |
| 用户偏好          | 不喜欢某种食物           | 个性化排序或排除           |
| 宗教/文化饮食限制 | 用户主动声明的禁食要求   | 按用户声明执行             |
| 医疗相关限制      | 医生要求限制某类食物     | 记录来源，按审核规则处理   |
| 食物不耐受        | 用户声明的特定食物不耐受 | 独立记录，不自动等同于过敏 |
| 食物安全限制      | 某食物在特定阶段不适用   | 安全规则过滤               |
| 特殊进食需求      | 咀嚼、吞咽或其他能力限制 | 专业审核后受限推荐         |

必须区分：

- 食物过敏。
- 食物不耐受。
- 用户不喜欢。
- 医疗人员要求的饮食限制。
- 产品依据指南设置的普遍安全限制。

不能把这些概念统一存成一个 `allergy` 字段。

## 13. 安全规则执行引擎

### 13.1 执行位置

安全校验必须在以下操作中执行：

1. 首次日程生成。
2. 每日未来 7 天日程补齐。
3. 用户手动替换食谱。
4. 用户顺延任务。
5. 用户更新过敏信息。
6. 用户更新特殊饮食限制。
7. 食谱内容更新。
8. 食谱撤回。
9. 安全规则更新。
10. 日程重新生成。

### 13.2 统一执行流程

```text
接收安全校验请求
  ↓
读取档案及业务域
  ↓
读取用户安全档案
  ↓
读取当前有效安全规则
  ↓
读取食材与食谱安全属性
  ↓
检查用户已声明的禁忌
  ↓
检查阶段安全限制
  ↓
检查幼儿进食安全/孕期饮食安全
  ↓
检查复合食材及交叉接触
  ↓
生成安全判断结果
  ↓
返回 allow / block / review_required / restricted
  ↓
记录规则命中与审计日志
```

### 13.3 规则执行顺序

建议固定为：

1. 当前规则和档案版本有效性检查。
2. 明确禁止条件检查。
3. 用户过敏禁忌检查。
4. 特殊饮食限制检查。
5. 阶段适用性检查。
6. 进食安全检查。
7. 复合食材及交叉接触检查。
8. 输出最终判断结果。

实际执行可根据性能优化，但不得跳过任何适用的硬约束。

### 13.4 统一结果结构

```text
SafetyCheckResult
  - checkId
  - profileId
  - recipeId
  - contentVersionId
  - result
  - matchedRules[]
  - blockedIngredients[]
  - warnings[]
  - reviewRequiredItems[]
  - safetyProfileVersion
  - safetyRuleVersion
  - checkedAt
```

建议返回结构化结果，避免业务页面自行解释原始规则。

### 13.5 多规则命中

同一食谱可能同时命中多个安全规则。

例如：

- 食谱包含已知过敏食物。
- 食谱适用阶段不匹配。
- 食谱质地未审核。
- 食谱复合食材信息不完整。

系统应记录所有相关命中结果，但最终状态以最高优先级的阻断条件为准。

不得只返回一个笼统的“不可推荐”，而丢失具体命中原因。

## 14. 安全规则与日程引擎接口

### 14.1 接口职责

日程引擎不自行解释安全规则，只调用统一安全校验能力。

建议接口：

```text
checkRecipeSafety({
  profileId,
  recipeId,
  contentVersionId,
  scheduleDate,
  operationType
})
```

`operationType` 示例：

- `generate`
- `replace`
- `defer`
- `regenerate`
- `revalidate`

### 14.2 返回结果

```text
{
  "result": "allow",
  "matchedRules": [],
  "blockedIngredients": [],
  "warnings": [],
  "reviewRequiredItems": [],
  "safetyProfileVersion": 1,
  "safetyRuleVersion": "1.0.0"
}
```

以上为接口结构示例，不代表生产规则的默认放行结果。

### 14.3 日程引擎处理

| 安全结果        | 日程引擎处理               |
| --------------- | -------------------------- |
| allow           | 进入下一步营养及个性化匹配 |
| block           | 从候选池排除               |
| review_required | 不进入自动推荐池           |
| restricted      | 按审核规则限制使用         |
| 服务异常        | 停止本次自动生成           |

### 14.4 手动操作不可绕过

以下操作都必须调用安全校验：

- 手动选择食谱。
- 手动替换食谱。
- 从历史食谱重新安排。
- 将任务顺延到其他日期。
- 从收藏内容添加到日程。

不能只在自动推荐入口调用安全校验。

## 15. 安全信息变更后的日程处理

### 15.1 触发事件

以下变化应触发未来日程重新校验：

- 新增过敏声明。
- 修改已知过敏食物。
- 更新观察记录并出现疑似反应。
- 新增特殊饮食限制。
- 幼儿进食能力信息发生变化。
- 孕期阶段变化。
- 食谱安全属性变化。
- 食谱被撤回。
- 安全规则版本升级。

### 15.2 处理流程

```text
安全信息发生变化
  ↓
保存新版本
  ↓
查找关联的未来任务
  ↓
筛选尚未执行的任务
  ↓
重新执行安全校验
  ↓
通过校验
  └── 保留原任务或更新校验信息

未通过校验
  └── 标记 blocked / pending_replacement
        ↓
      查询安全候选
        ↓
      用户确认或按产品策略重新安排
```

### 15.3 任务处理原则

| 原任务状态 | 处理方式                   |
| ---------- | -------------------------- |
| pending    | 重新校验                   |
| completed  | 保留历史记录               |
| skipped    | 保留跳过状态               |
| deferred   | 对目标日期重新校验         |
| replaced   | 对当前有效替换内容重新校验 |
| blocked    | 保持阻断，等待重新处理     |

已经完成的任务不能因为新规则发布而被修改成未完成状态。

### 15.4 自动替换限制

一期建议采用：

- 安全阻断可以自动执行。
- 自动寻找替代候选可以执行。
- 替代食谱是否直接写入正式日程，需要根据用户是否授权及产品交互规则确定。
- 对安全风险相关任务，优先提示用户确认替代安排。
- 不得在替换失败时恢复原来的不安全食谱。

## 16. 安全规则审核与发布

### 16.1 审核角色

| 角色         | 职责                         |
| ------------ | ---------------------------- |
| 内容编辑     | 创建和维护食材、食谱安全信息 |
| 专业审核人员 | 审核安全规则、适用范围和依据 |
| 产品负责人   | 确认产品行为及用户提示       |
| 技术管理员   | 管理规则配置、发布及回滚     |
| 审计人员     | 检查规则变更和发布记录       |

涉及医学判断的规则必须由具备相应专业能力的人员审核。

### 16.2 审核流程

```text
规则创建
  ↓
依据来源登记
  ↓
业务适用范围检查
  ↓
专业审核
  ↓
安全测试
  ↓
产品确认
  ↓
发布审批
  ↓
正式发布
  ↓
持续监控
```

### 16.3 发布条件

规则必须满足：

- 规则条件明确。
- 适用业务域明确。
- 适用阶段明确。
- 执行动作明确。
- 来源依据完整。
- 规则版本明确。
- 专业审核通过。
- 安全测试通过。
- 有回滚方案。

未经审核的规则只能保存为草稿，不能参与生产推荐。

### 16.4 规则撤回与回滚

规则出现问题时：

1. 停止新任务使用问题规则。
2. 恢复上一个有效版本或发布修正版。
3. 查询受影响的未来任务。
4. 重新执行安全校验。
5. 保留规则变更前后的记录。
6. 必要时通知受影响用户。

安全规则回滚不能自动恢复已经被用户声明为禁忌的食物。

## 17. 安全提示文案规范

### 17.1 提示原则

- 不制造恐慌。
- 不作医学诊断。
- 明确说明产品限制。
- 提供用户可以执行的下一步。
- 不通过模糊措辞弱化已知风险。
- 严重风险提示必须优先展示。

### 17.2 提示类型

| 场景               | 提示方向                                     |
| ------------------ | -------------------------------------------- |
| 命中已知过敏食物   | 说明该食谱包含用户已记录的禁忌食物，无法安排 |
| 复合食材信息不完整 | 说明暂时无法确认配料信息，需要核实           |
| 质地不适用或未审核 | 说明该食谱暂不适合当前进食条件               |
| 食物疑似引起反应   | 停止自动安排，建议联系专业医疗人员           |
| 可能出现严重反应   | 优先提示立即寻求紧急医疗帮助                 |
| 特殊孕期情况       | 提示按医生或临床营养师的建议管理饮食         |
| 安全规则服务异常   | 暂时无法完成安全校验，本次不生成相关推荐     |

### 17.3 禁止使用的表达

不得使用：

- “绝对安全”。
- “保证不过敏”。
- “医学确认无过敏”。
- “已经脱敏”。
- “系统判断可以放心食用”。
- “完成观察后自动解锁安全食物”。

可以使用：

- “目前没有记录已知过敏信息”。
- “该食谱通过当前产品安全规则校验”。
- “该食物暂时不进入自动推荐”。
- “建议联系专业医疗人员评估”。

## 18. AI 使用约束

AI 可以辅助：

- 识别食谱中的疑似食材名称。
- 提取食品标签中的配料信息。
- 生成待审核的过敏原映射建议。
- 检查食谱安全字段是否缺失。
- 汇总规则命中原因。
- 生成安全提示文案草稿。

AI 不可以：

- 自动诊断食物过敏。
- 自动判断过敏原检测结果是否代表临床过敏。
- 自动解除用户禁忌。
- 自动判断食物激发试验结果。
- 自动制定重新尝试食物的方案。
- 自动判定幼儿吞咽能力。
- 自动编造国家标准或医学指南内容。
- 自动批准或发布安全规则。

所有 AI 产生的安全相关内容都必须经过人工审核。

## 19. 审计与数据安全

### 19.1 审计事件

建议记录：

| 事件                          | 触发时机     |
| ----------------------------- | ------------ |
| safety_profile_created        | 创建安全档案 |
| allergy_status_updated        | 过敏状态变化 |
| allergy_restriction_added     | 新增禁忌     |
| allergy_restriction_updated   | 修改禁忌     |
| food_observation_created      | 创建观察记录 |
| suspected_reaction_recorded   | 记录疑似反应 |
| safety_rule_triggered         | 安全规则命中 |
| recipe_safety_blocked         | 食谱被阻断   |
| safety_revalidation_started   | 开始重新校验 |
| safety_revalidation_completed | 完成重新校验 |
| safety_rule_published         | 安全规则发布 |
| safety_rule_withdrawn         | 安全规则撤回 |

### 19.2 数据最小化

过敏及健康相关信息应严格控制：

- 只采集实现功能所需的信息。
- 明确告知用户采集目的。
- 按照适用法律法规处理敏感个人信息。
- 限制后台人员访问权限。
- 记录敏感数据访问和修改日志。
- 不默认用于广告画像。
- 不用于与产品核心功能无关的商业分析。
- 对分析数据尽可能采用去标识化处理。

### 19.3 数据删除与历史审计

用户要求删除相关信息时，应按照产品隐私政策及适用法律法规处理。

但删除用户当前有效的安全档案，不应导致系统在删除完成前继续使用已失效或不再授权的数据。

审计日志应采用合理的保留和访问控制策略，不应无限制复制敏感原始信息。

## 20. 测试与验收标准

### 20.1 过敏状态测试

- [ ] `none_known` 与 `skipped` 区分正确。
- [ ] `confirmed_allergy` 能建立独立禁忌清单。
- [ ] 用户声明的过敏食物能够映射到食材字典。
- [ ] 无法映射的过敏食物不会被忽略。
- [ ] 过敏信息更新后能够重新校验未来任务。
- [ ] 疑似反应后停止该食物自动安排。
- [ ] 无反应记录不会自动解除过敏禁忌。
- [ ] 用户跳过过敏流程不影响基础日程使用。

### 20.2 复合食材测试

- [ ] 复合食材能够展开已知配料。
- [ ] 能识别已知关联过敏原。
- [ ] 预包装食品标签来源能够追溯。
- [ ] 交叉接触提示能够记录。
- [ ] 关键配料未知时不能默认安全。
- [ ] 标签信息与临床过敏诊断逻辑没有混用。

### 20.3 幼儿进食安全测试

- [ ] 幼儿食谱具有经过审核的阶段适用信息。
- [ ] 质地信息使用受控字典。
- [ ] 食材处理方式明确。
- [ ] 整粒花生、坚果、果冻等已按适用规则处理。
- [ ] 进食照护提示可以正确展示。
- [ ] 特殊进食能力限制能够阻断普通不适用食谱。
- [ ] 年龄不能作为唯一的质地安全判断依据。

### 20.4 孕期安全测试

- [ ] 孕期食谱必须具有孕期适用性审核记录。
- [ ] 关键加工和储存信息完整。
- [ ] 已审核的特殊限制能够正确过滤。
- [ ] 未审核的医学性限制不会被擅自编造成规则。
- [ ] 特殊孕期情况不会错误进入普通营养建议流程。

### 20.5 日程引擎集成测试

- [ ] 自动生成调用安全校验。
- [ ] 手动替换调用安全校验。
- [ ] 顺延调用安全校验。
- [ ] 重新生成调用安全校验。
- [ ] 安全服务异常时停止自动生成。
- [ ] 安全信息变化后能够阻断不适用任务。
- [ ] 已完成历史任务不会被错误修改。
- [ ] 安全规则版本可以追溯。

### 20.6 权限与审核测试

- [ ] 未审核规则不能发布。
- [ ] 普通内容编辑人员不能直接发布医学性规则。
- [ ] 规则变更具有完整审计记录。
- [ ] 规则撤回后能够检查关联任务。
- [ ] AI 生成的安全内容不能绕过人工审核。

### 21.1 上线前必须完成的事项

以下事项属于生产上线前置条件：

1. 建立并审核一期过敏原及食材关联字典。
2. 完成一期孕期安全规则审核。
3. 完成一期幼儿进食安全及质地规则审核。
4. 完成复合食材及交叉接触处理规则。
5. 完成安全规则中心的硬过滤能力。
6. 完成安全信息变化后的未来任务重新校验。
7. 完成严重风险提示及相关交互审核。

未完成上述事项时，可以继续开发规则引擎框架、数据模型和测试环境，但不能把未经审核的安全规则作为生产推荐依据。
