## 1. 文档目标

本文档定义食刻一期的整体技术架构、模块职责、数据访问方式、云函数划分、日程引擎、安全规则中心、内容管理、任务调度、权限控制、部署及质量保障要求。

目标是将前五份 Spec 中确定的产品与业务规则转换为可实施的技术设计。

本架构需要解决：

1. 如何组织微信小程序前端代码。
2. 如何划分孕期与婴幼儿两个业务域。
3. 如何设计共享业务能力。
4. 如何实现统一日程生成引擎。
5. 如何实现独立安全规则中心。
6. 如何管理食谱、食材和内容版本。
7. 如何实现未来 7 天日程自动补齐。
8. 如何保证日程生成和任务操作的幂等性。
9. 如何处理安全档案、食谱和规则更新后的日程重新校验。
10. 如何实现轻量内容维护后台。
11. 如何保证敏感数据访问安全。
12. 如何支持后续扩展到完整孕期及 0—36 月龄。

## 2. 一期技术选型

### 2.1 技术栈

| 层级     | 技术方案                         | 一期用途                         |
| -------- | -------------------------------- | -------------------------------- |
| 用户端   | 微信小程序原生框架               | 用户交互、日程、食谱、任务管理   |
| 前端语言 | JavaScript 或 TypeScript         | 页面与业务逻辑                   |
| 前端样式 | WXSS                             | 小程序界面                       |
| 后端平台 | 微信云开发                       | 云端基础设施                     |
| 后端业务 | 微信云函数                       | 业务接口及规则执行               |
| 数据库   | 微信云数据库                     | 用户、档案、食谱、日程等数据     |
| 文件存储 | 微信云存储                       | 食谱图片、内容资料等非结构化文件 |
| 定时调度 | 云开发定时触发器                 | 未来 7 天日程补齐、定时检查      |
| 内容管理 | 轻量受控管理工具                 | 食谱、食材、规则和审核维护       |
| 规则引擎 | TypeScript/JavaScript 纯函数模块 | 阶段匹配、候选筛选、安全校验     |
| 数据分析 | 事件埋点与基础统计               | 核心行为和业务质量分析           |

### 2.2 技术选型原则

一期优先采用微信生态原生能力，降低基础设施和运维成本。

不建议一期引入：

- Kubernetes。
- 微服务拆分。
- 独立消息队列集群。
- Drools 等通用规则引擎平台。
- 独立推荐算法服务。
- 独立 AI 日程生成服务。
- 复杂 CMS。
- 多套数据库。
- 不必要的第三方用户身份体系。

当业务规模和实际性能需求出现明确证据后，再评估是否拆分。

### 2.3 技术版本约束

具体 SDK、云函数运行时、数据库 API 和构建工具版本应在项目初始化时确认。

实施前必须检查：

- 微信开发者工具当前支持的基础库版本。
- 微信小程序项目配置。
- 云开发环境配置。
- 云函数运行时支持情况。
- 当前云数据库 SDK 及事务能力。
- 云开发定时触发器支持情况。

不得在没有检查项目环境的情况下直接假定某个 SDK API 或运行时版本可用。

### 3.2 核心架构约束

1. 小程序端只负责交互和展示，不承担最终安全判断。
2. 用户身份由可信服务端上下文确定，不接受客户端传入的用户 ID 作为授权依据。
3. 业务写操作必须通过云函数完成。
4. 日程生成逻辑不能直接放在页面中。
5. 安全规则必须通过统一服务执行。
6. 内容审核和发布必须在受控后台完成。
7. 孕期与幼儿业务域保持独立。
8. 共享能力通过明确的服务接口提供。
9. 历史日程必须保留生成时使用的内容及规则版本。
10. 所有涉及安全状态变化的操作必须保留审计记录。

## 4. 业务域与模块边界

### 4.1 用户与档案域

职责：

- 用户身份识别。
- 用户基础信息管理。
- 多档案管理。
- 当前档案选择。
- 档案状态管理。
- 档案与用户之间的归属关系。

一期支持一个账号拥有多个孕期或幼儿档案。

虽然一期界面可以简化档案切换，但底层数据必须具备多档案隔离能力。

### 4.2 孕期业务域

职责：

- 孕期档案。
- 孕周计算。
- 孕期阶段识别。
- 孕期饮食约束。
- 孕期食谱适用性。
- 孕期特殊情况记录。

孕期业务域独立维护专业字段，不与幼儿业务字段强行合并。

### 4.3 幼儿业务域

职责：

- 幼儿档案。
- 年龄阶段识别。
- 喂养与进食相关信息。
- 食物过敏信息。
- 食物观察记录。
- 幼儿进食安全约束。
- 幼儿食谱适用性。

幼儿业务域应能够扩展到 0—36 月龄，但一期只启用 2 岁左右幼儿相关规则和内容。

### 4.4 共享业务域

| 模块              | 职责                     |
| ----------------- | ------------------------ |
| Schedule Service  | 日程生成和查询           |
| Task Service      | 微任务状态与操作         |
| Content Service   | 食材、食谱和内容版本读取 |
| Safety Service    | 统一安全校验             |
| Stage Resolver    | 当前阶段识别             |
| Audit Service     | 操作审计                 |
| Analytics Service | 行为事件记录             |

共享的是基础业务能力，不是所有业务实体。

### 4.5 模块依赖规则

```text
Pregnancy Domain ─────┐
                      ├── Schedule Service
Child Domain ─────────┘

Schedule Service
  ├── Stage Resolver
  ├── Content Service
  ├── Safety Service
  └── Task Service

Safety Service
  ├── User Safety Profile
  ├── Food Safety Profile
  ├── Recipe Safety Profile
  └── Published Safety Rules
```

约束：

- Schedule Service 不直接修改安全规则。
- Pregnancy Domain 不直接访问 Child Domain 内部数据。
- Child Domain 不直接访问 Pregnancy Domain 内部数据。
- 业务域之间通过明确的服务接口协作。
- Safety Service 不依赖页面组件。
- 内容服务不能自行绕过安全校验直接写入日程。

## 6. 核心服务设计

### 6.1 User Service

主要能力：

- 获取当前登录用户。
- 初始化用户记录。
- 获取用户档案列表。
- 更新用户基础信息。
- 校验档案归属。

关键约束：

- 使用可信的微信身份上下文。
- 用户 ID 由服务端获取。
- 不允许客户端传入其他用户 ID 后直接读取或修改其数据。

### 6.2 Profile Service

主要能力：

- 创建孕期档案。
- 创建幼儿档案。
- 查询档案详情。
- 修改档案。
- 切换当前档案。
- 获取档案版本。

档案修改涉及阶段、安全或日程适用性时，应触发后续校验流程。

### 6.3 Pregnancy Service

主要能力：

- 计算当前孕周。
- 解析孕期阶段。
- 查询孕期适用规则。
- 读取孕期特殊限制。

孕周计算和日期边界必须统一实现，不能在多个页面中分别计算。

### 6.4 Child Service

主要能力：

- 计算幼儿年龄。
- 解析适用阶段。
- 读取幼儿进食能力相关信息。
- 管理食物观察记录。
- 管理过敏相关状态。

年龄计算必须统一处理生日、时区及日期边界问题。

### 6.5 Content Service

主要能力：

- 查询食材。
- 查询食谱。
- 查询食谱版本。
- 获取内容适用阶段。
- 获取食材及食谱安全属性。
- 查询审核状态。
- 查询内容来源。

只允许读取已发布且在有效期内的内容作为生产候选。

### 6.6 Schedule Service

主要能力：

- 生成未来 7 天日程。
- 查询日程。
- 查询日程任务。
- 补齐缺失日程。
- 重新生成日程。
- 处理档案阶段变化。
- 处理内容和规则变化。

### 6.7 Task Service

主要能力：

- 完成任务。
- 跳过任务。
- 替换食谱。
- 顺延任务。
- 查询任务状态。
- 记录任务执行历史。

所有会改变当前有效食谱的操作必须重新执行安全校验。

### 6.8 Safety Service

主要能力：

- 查询用户安全档案。
- 查询有效安全规则。
- 校验食材。
- 校验食谱。
- 校验复合食材。
- 校验交叉接触信息。
- 输出统一安全判断。
- 记录规则命中。
- 触发未来任务重新校验。

Safety Service 必须是唯一的生产安全判断入口。

## 7. 日程引擎技术设计

### 7.1 设计原则

日程引擎是规则驱动的确定性业务模块，不是 AI 内容生成器。

核心流程：

```text
读取档案
  ↓
识别业务域和当前阶段
  ↓
获取日程槽位
  ↓
查询已发布内容候选
  ↓
阶段过滤
  ↓
安全规则硬过滤
  ↓
营养结构匹配
  ↓
个性化排序
  ↓
结果完整性校验
  ↓
写入日程和任务
  ↓
记录生成版本与审计信息
```

### 7.2 规则引擎结构

建议将规则实现为纯函数：

```text
resolveStage(profile, date)
  → StageResult

buildScheduleSlots(stage, dateRange)
  → ScheduleSlot[]

getRecipeCandidates(slot, contentSnapshot)
  → RecipeCandidate[]

filterByStage(candidates, stage)
  → RecipeCandidate[]

filterBySafety(candidates, safetyContext)
  → SafetyFilterResult

matchNutrition(candidates, nutritionProfile)
  → RecipeCandidate[]

rankCandidates(candidates, preferences)
  → RecipeCandidate[]

validateSchedule(scheduleDraft)
  → ValidationResult
```

纯函数要求：

- 输入明确。
- 输出确定。
- 不直接访问数据库。
- 不依赖页面状态。
- 不依赖系统当前时间的隐式值。
- 不在函数内部直接写入数据库。
- 规则测试可独立执行。

数据库读取、事务和任务写入由应用服务层处理。

### 7.3 日程生成上下文

一次日程生成应构建明确的上下文：

```text
ScheduleGenerationContext
  - userId
  - profileId
  - domain
  - targetDateRange
  - profileSnapshot
  - stageSnapshot
  - safetyProfileSnapshot
  - contentVersionSnapshot
  - safetyRuleVersion
  - scheduleRuleVersion
  - preferenceSnapshot
  - requestId
```

生成过程中不得混用不同版本的档案和规则。

### 7.4 未来 7 天日程

一期采用每日执行、提前生成未来 7 天日程。

技术要求：

- 使用统一业务时区和日期计算方式。
- 按档案分别生成。
- 检查已有日程。
- 只补齐缺失日期或缺失槽位。
- 不重复生成已经存在的有效任务。
- 不覆盖已完成任务。
- 不擅自覆盖用户已跳过或已替换的任务。
- 生成失败时保留已有有效日程。
- 日程不足时返回可解释的结果。

### 7.5 候选不足

候选不足时：

- 不放宽安全规则。
- 不使用未经审核的内容。
- 不使用阶段不适用的食谱。
- 不使用安全属性不完整且必须审核的内容。
- 可以返回不完整日程。
- 应记录缺少候选的原因。
- 必要时向用户展示合理的结构建议或待补充提示。

### 7.6 日程结果版本快照

每次生成应记录：

- profileVersion
- stageRuleVersion
- scheduleRuleVersion
- safetyRuleVersion
- contentVersionId
- generatedAt
- generationRequestId

每个 ScheduleTask 应关联具体的食谱内容版本。

历史任务不能只引用食谱当前版本，否则内容更新后无法还原当时的推荐依据。

## 8. 安全规则中心技术设计

### 8.1 模块独立性

安全规则中心应作为独立业务模块存在，但一期不需要独立部署成微服务。

逻辑结构：

```text
Safety Service
  ├── Safety Profile Repository
  ├── Safety Rule Repository
  ├── Food Safety Resolver
  ├── Recipe Safety Resolver
  ├── Allergen Matcher
  ├── Cross Contact Checker
  ├── Safety Rule Evaluator
  ├── Safety Audit Writer
  └── Safety Revalidation Handler
```

### 8.2 统一校验入口

```text
checkRecipeSafety({
  profileId,
  recipeId,
  contentVersionId,
  scheduleDate,
  operationType
})
```

返回：

```text
SafetyCheckResult
  - result
  - matchedRules[]
  - blockedIngredients[]
  - warnings[]
  - reviewRequiredItems[]
  - safetyProfileVersion
  - safetyRuleVersion
  - checkedAt
```

### 8.3 Fail Closed

安全校验失败时必须默认拒绝自动放行。

以下情况必须阻止本次候选进入生产日程：

- 安全规则服务不可用。
- 用户安全档案读取失败。
- 关键食材映射无法完成。
- 规则版本不可用。
- 安全数据结构不符合要求。
- 关键安全属性缺失。
- 校验结果不完整。

不能将异常捕获后转换成 `allow`。

### 8.4 安全档案更新

**过敏禁忌解除与审计（F-04.3-06 / F-04.3-07）**：

- `AllergyChangeLog` 写入集合 `allergy_change_logs`（02 §7.4）；分类：**用户安全数据审计**，与通用 `audit_logs` 并存、不重复建第二套禁忌审计集合。
- 仅 **`safety` / `profile` 云函数**（或等价应用服务）在业务校验通过后 **追加** 写入；小程序客户端 **只读** 或经云函数间接查询，**不得**直写。
- `allergy_item_deactivated` 须校验 `actorId`、`userConfirmationId`、`outcome=success` 后方能更新 `allergy_items.status`；失败须 `outcome=failed`/`rejected` 且不改 `status`。
- 成功解除后触发 §8.4 重新校验流程，并在日志中记录 `revalidationTriggered` / `revalidationReference`。

安全信息发生变化时：

1. 保存新版本（含 `AllergyChangeLog` 追加，适用时）。
2. 创建重新校验任务。
3. 查询未来未执行日程。
4. 对相关食谱重新执行安全校验。
5. 阻断不再满足条件的任务。
6. 记录重新校验结果。
7. 根据业务策略处理替换。

重新校验任务应具备幂等能力，避免重复执行导致状态混乱。

### 8.5 安全规则版本

每次发布安全规则都必须生成新版本。

规则执行结果应记录：

- 规则版本。
- 用户安全档案版本。
- 食谱安全版本。
- 命中规则。
- 执行结果。
- 执行时间。

不能只保存一个当前规则版本，导致历史结果失去依据。

## 9. 云函数设计

### 9.1 划分原则

云函数按照业务能力划分，而不是按照小程序页面数量划分。

一期建议模块：

| 云函数      | 主要职责                   |
| ----------- | -------------------------- |
| `user`      | 用户初始化和身份相关操作   |
| `profile`   | 档案创建、修改和查询       |
| `pregnancy` | 孕期信息与阶段计算         |
| `child`     | 幼儿信息与阶段计算         |
| `schedule`  | 日程生成和查询             |
| `task`      | 任务完成、跳过、替换、顺延 |
| `content`   | 食材和食谱读取             |
| `safety`    | 安全档案及统一安全校验     |
| `admin`     | 后台内容和规则管理         |
| `scheduler` | 定时补齐和重新校验任务     |

实际部署时可以根据调用频率和维护复杂度合并部分云函数，但不得合并业务职责导致边界模糊。

### 9.2 云函数调用结构

```text
miniprogram
  ↓
cloud.callFunction
  ↓
cloud function entry
  ↓
authentication / authorization
  ↓
input validation
  ↓
application service
  ↓
domain logic
  ↓
repository
  ↓
cloud database
```

### 9.3 云函数返回结构

建议统一：

```text
{
  success: true,
  data: {},
  error: null,
  requestId: "..."
}
```

失败：

```text
{
  success: false,
  data: null,
  error: {
    code: "SCHEDULE_GENERATION_FAILED",
    message: "日程生成失败",
    retryable: true
  },
  requestId: "..."
}
```

约束：

- 不将数据库内部错误直接返回客户端。
- 不返回敏感规则内部配置。
- 错误码保持稳定。
- 错误信息应适合前端处理。
- 服务端日志保留完整错误上下文。

### 9.4 云函数超时和任务拆分

日程生成和安全重新校验不能假设一定能在一次云函数执行时间内完成。

需要：

- 控制单次处理的数据范围。
- 支持分批处理。
- 支持失败重试。
- 支持任务状态查询。
- 避免长时间占用单个云函数。
- 对已经完成的批次不重复写入。

当业务量尚小时可以同步处理；出现执行时长或并发压力后，再切换为分批异步处理。

- 内容基础数据与内容版本分开管理。
- 安全规则与用户安全档案分开管理。

- 历史任务保留版本引用。
- 避免在一个集合中存储大量无边界嵌套数据。
- 不把所有业务数据集中存放在一个用户文档中。

### 10.4 索引设计

- 根据 profileId 查询安全档案。
- 根据 profileId 和日期范围查询日程。
- 根据 scheduleId 查询任务。
- 根据 profileId 和任务状态查询待执行任务。
- 根据 recipeId 和版本查询内容。
- 根据规则状态及生效时间查询有效规则。
- 根据任务状态和重试时间查询后台任务。

云数据库的索引限制、组合查询能力和实际执行计划必须在实施阶段验证。

不能只依据逻辑查询设计假定数据库一定支持对应查询。

## 11. 日程生成幂等与并发控制

### 11.1 幂等目标

同一个档案、同一个目标日期范围、同一版本上下文的重复请求，不应生成重复日程或重复任务。

### 11.2 幂等键

建议生成：

```text
generationKey =
  profileId
  + domain
  + targetStartDate
  + targetEndDate
  + generationVersion
```

具体实现可以使用稳定哈希。

幂等键必须包含能够影响生成结果的关键参数。

不能将请求时间戳作为唯一幂等依据。

### 11.3 并发控制

典型场景：

- 用户主动进入日程页面触发补齐。
- 定时任务同时触发补齐。
- 用户连续点击重新生成。
- 多个云函数同时操作同一档案。

建议：

1. 创建生成任务。
2. 检查相同幂等键是否已存在。
3. 使用事务或条件更新争取任务执行权。
4. 生成日程草稿。
5. 检查档案和规则版本是否发生变化。
6. 写入日程与任务。
7. 标记生成任务完成。
8. 失败时释放或过期处理执行锁。

具体锁机制必须结合云数据库实际支持能力设计。

不能假定数据库天然具备分布式锁。

### 11.4 生成失败处理

- 已经存在的有效任务不能被删除。
- 失败的生成任务需要保留错误信息。
- 可重试错误与不可重试错误必须区分。
- 重试不能创建重复日程。
- 安全校验失败不能通过重试绕过。
- 多次失败应进入可观察的异常状态。

## 12. 任务状态与事务设计

### 12.1 任务状态

建议沿用 `04-schedule-rules.md` 定义的任务状态。

实现前需要将任务状态统一成受控枚举，不能在页面和云函数中自行创造状态名称。

### 12.2 任务操作

以下操作必须由服务端完成：

- 完成。
- 跳过。
- 替换。
- 顺延。
- 阻断。
- 重新安排。

### 12.3 操作原子性

例如替换食谱：

```text
用户提交替换请求
  ↓
检查用户和档案归属
  ↓
检查当前任务状态
  ↓
读取目标食谱版本
  ↓
执行安全校验
  ↓
执行阶段和业务约束校验
  ↓
检查任务版本是否变化
  ↓
更新任务
  ↓
写入操作记录
```

任务更新和操作记录应尽可能通过事务保证一致性。

如果云数据库事务无法覆盖全部操作，应采用状态机和可恢复任务设计，不能出现任务已更新但审计完全丢失的静默失败。

### 12.4 并发操作

对于同一个任务：

- 同时完成和跳过时，只允许一个合法状态转换成功。
- 同时替换时，需要检测任务版本。
- 已完成任务不能被普通替换操作覆盖。
- 已阻断任务不能直接恢复原食谱。
- 顺延后必须重新校验目标日期适用性。

建议采用乐观锁字段，例如 `version`。

更新时要求：

```text
update where
  taskId = expectedTaskId
  and version = expectedVersion
```

只有一个并发请求能够成功更新。

具体查询和条件更新方式应按云数据库实际 API 验证。

## 13. 内容版本管理

### 13.1 内容基础信息与版本分离

建议：

```text
Recipe
  └── RecipeVersion
        ├── ingredients
        ├── instructions
        ├── nutrition
        ├── applicability
        ├── safetyProfile
        ├── sourceReferences
        ├── reviewStatus
        └── version
```

基础食谱用于稳定标识。

版本用于保存具体内容。

### 13.2 日程引用

每条任务必须关联：

- recipeId
- contentVersionId
- contentSnapshotVersion
- safetyRuleVersion

历史日程展示时应能还原当时的食谱内容。

### 13.3 内容更新

食谱发生变化时：

1. 创建新版本。
2. 完成内容审核。
3. 完成安全审核。
4. 发布新版本。
5. 新生成日程使用新版本。
6. 未来未执行任务重新检查是否受影响。
7. 历史完成任务保留原版本。

### 13.4 内容撤回

食谱撤回后：

- 不再进入新的候选池。
- 查询未来未执行任务。
- 对关联任务重新校验。
- 不直接删除历史任务。
- 不覆盖用户已经完成的记录。

## 14. 定时任务与后台任务

### 14.1 一期定时任务

| 任务              | 触发方式   | 目的               |
| ----------------- | ---------- | ------------------ |
| 未来 7 天日程补齐 | 定时触发器 | 检查需要补齐的日程 |
| 日程重新校验      | 后台任务   | 处理规则或档案变化 |
| 食谱撤回处理      | 后台任务   | 检查关联任务       |
| 过期规则检查      | 定时任务   | 检查失效规则       |
| 异常任务重试      | 定时任务   | 重试可恢复任务     |
| 数据质量检查      | 定时任务   | 发现缺失或异常数据 |

### 14.2 定时任务原则

- 定时任务必须幂等。
- 支持分批执行。
- 支持失败重试。
- 记录执行开始、结束及结果。
- 不能假设定时触发器绝对准时。
- 不依赖定时任务完成所有关键安全检查。

关键安全校验必须在实际业务操作时同步执行。

定时重新校验是补充机制，不是安全校验的唯一入口。

### 14.3 后台任务结构

建议：

```text
BackgroundJob
  - jobId
  - jobType
  - targetId
  - idempotencyKey
  - status
  - attempts
  - nextRetryAt
  - lastErrorCode
  - createdAt
  - updatedAt
  - completedAt
```

任务状态至少需要支持：

- pending
- processing
- succeeded
- failed
- retry_wait

具体字段需与实际任务执行方案保持一致。

## 15. 轻量内容管理后台

### 15.1 一期定位

一期需要轻量、受控的内容维护能力，不建设复杂 CMS。

后台主要服务于：

- 食材维护。
- 过敏原字典维护。
- 食谱维护。
- 食谱审核。
- 安全属性维护。
- 安全规则维护。
- 内容发布与撤回。
- 规则版本管理。
- 审计记录查看。

### 15.2 权限角色

建议：

| 角色       | 权限                 |
| ---------- | -------------------- |
| 内容编辑   | 创建和编辑草稿       |
| 内容审核   | 审核食谱和内容       |
| 专业审核   | 审核安全及专业适用性 |
| 发布管理员 | 发布审核通过的版本   |
| 系统管理员 | 管理角色和系统配置   |

普通用户不能访问管理接口。

### 15.3 后台技术形态

一期可以选择：

- 受控的简单 Web 管理页面。
- 微信生态支持的管理工具。
- 基于现有项目能力实现的内部维护页面。

选型原则：

- 不把后台权限暴露给普通小程序用户。
- 所有管理操作在云端重新鉴权。
- 敏感规则变更保留审计记录。
- 不允许前端直接修改已发布规则。
- 不允许未审核内容进入生产推荐池。

具体后台技术方案在实施前根据团队能力和部署条件确认。

## 16. 权限与数据安全

### 16.1 身份认证

用户端使用微信登录体系。

服务端应通过可信调用上下文识别当前用户。

不能相信客户端传入的：

- userId
- openId
- role
- isAdmin
- permission

这些字段如果存在，必须由服务端重新获取或校验。

### 16.2 数据访问控制

用户只能访问自己拥有或被明确授权访问的档案。

每次查询和写入都应校验：

1. 当前用户身份。
2. 档案归属。
3. 当前操作权限。
4. 目标数据归属。
5. 当前业务状态是否允许操作。

### 16.3 数据库权限

客户端不应直接拥有修改核心业务数据的权限。

尤其是：

- 过敏禁忌。
- 安全档案。
- 过敏变更审计（`allergy_change_logs`）。
- 日程任务。
- 内容发布状态。
- 安全规则。
- 管理员权限。

这些操作必须经过云函数的权限检查和业务校验。

数据库安全规则需要按实际集合逐一配置，并在测试环境验证越权访问。

### 16.4 敏感数据

过敏信息、孕期信息和幼儿信息应按照适用法律法规进行敏感个人信息管理。

要求：

- 最小必要采集。
- 明确处理目的。
- 提供必要告知。
- 按要求取得单独同意或履行其他适用法律要求。
- 严格限制后台访问。
- 敏感操作记录审计。
- 不默认用于广告画像。
- 不在普通日志中输出完整敏感信息。

具体法律合规要求应由项目法务或隐私负责人确认。

## 17. 日志、监控与埋点

### 17.1 技术日志

至少记录：

- requestId
- cloudFunction
- operation
- executionStatus
- duration
- errorCode
- retryCount
- createdAt

禁止在普通日志中记录完整过敏信息、医疗资料及其他不必要的敏感数据。

### 17.2 业务日志

建议关注：

- 日程生成成功率。
- 日程生成失败原因。
- 候选食谱不足情况。
- 食谱安全拦截数量。
- 手动替换成功率。
- 任务操作失败率。
- 日程重新校验结果。
- 内容审核及发布状态。

### 17.3 行为埋点

沿用 PRD 和前序 Spec 已定义的事件：

- profile_created
- schedule_generated
- schedule_viewed
- task_completed
- task_skipped
- recipe_replaced
- recipe_viewed
- schedule_deferred
- stage_changed
- allergy_status_updated
- food_observation_created
- safety_rule_triggered

埋点不得默认收集不必要的医疗敏感详情。

## 18. 异常处理

### 18.1 异常分类

| 异常           | 处理方式                   |
| -------------- | -------------------------- |
| 用户未登录     | 引导登录                   |
| 档案不存在     | 提示创建或重新选择档案     |
| 档案无权限     | 拒绝访问                   |
| 食谱不存在     | 返回内容不可用             |
| 食谱未发布     | 不进入候选池               |
| 安全校验失败   | 阻断候选                   |
| 安全服务不可用 | 停止本次生成               |
| 日程重复生成   | 返回已有有效结果或任务状态 |
| 任务状态冲突   | 返回冲突错误，要求刷新     |
| 定时任务失败   | 记录并按策略重试           |
| 数据库写入失败 | 不返回成功，保留恢复依据   |
| 内容版本失效   | 重新读取有效版本并校验     |

### 18.2 错误码建议

| 错误码                       | 说明             |
| ---------------------------- | ---------------- |
| `UNAUTHORIZED`               | 未授权           |
| `FORBIDDEN`                  | 无操作权限       |
| `PROFILE_NOT_FOUND`          | 档案不存在       |
| `PROFILE_VERSION_CONFLICT`   | 档案版本冲突     |
| `CONTENT_NOT_AVAILABLE`      | 内容不可用       |
| `SAFETY_CHECK_BLOCKED`       | 安全规则阻断     |
| `SAFETY_CHECK_UNAVAILABLE`   | 安全服务不可用   |
| `SCHEDULE_GENERATION_FAILED` | 日程生成失败     |
| `SCHEDULE_CONFLICT`          | 日程冲突         |
| `TASK_VERSION_CONFLICT`      | 任务版本冲突     |
| `TASK_INVALID_TRANSITION`    | 非法任务状态转换 |
| `IDEMPOTENCY_CONFLICT`       | 幂等请求冲突     |
| `VALIDATION_FAILED`          | 参数校验失败     |
| `INTERNAL_ERROR`             | 内部错误         |

错误码属于技术接口定义，不应直接作为用户可见文案。

## 19. 测试策略

### 19.1 单元测试

重点测试：

- 孕周计算。
- 幼儿年龄计算。
- 阶段解析。
- 日程槽位生成。
- 食谱候选筛选。
- 营养结构匹配。
- 安全规则判断。
- 过敏原映射。
- 任务状态转换。
- 幂等键生成。

### 19.2 集成测试

重点测试：

- 用户建档。
- 档案读取和权限隔离。
- 日程生成。
- 食谱替换。
- 任务跳过。
- 任务顺延。
- 安全档案更新。
- 未来日程重新校验。
- 食谱版本发布。
- 食谱撤回。
- 定时任务补齐。

### 19.3 安全测试

必须覆盖：

- 用户 A 不能访问用户 B 的档案。
- 用户不能通过传入其他 profileId 修改他人数据。
- 手动替换不能绕过过敏禁忌。
- 顺延不能绕过安全校验。
- 安全服务异常不能默认放行。
- 未审核食谱不能进入候选池。
- 未审核安全规则不能发布。
- 普通用户不能调用管理接口。
- 规则版本更新后未来任务能够重新校验。

### 19.4 并发测试

至少覆盖：

- 同一档案并发生成日程。
- 同一任务并发替换。
- 完成和跳过同时发生。
- 用户操作与定时任务同时发生。
- 安全档案更新与日程生成同时发生。
- 内容撤回与任务补齐同时发生。

### 19.5 质量门禁

每次代码提交应执行：

- 静态检查。
- 业务逻辑单元测试。
- 安全规则测试。
- 关键云函数集成测试。
- 构建或微信开发者工具编译检查。

具体脚本名称以项目实际 package 配置为准，不得假定项目一定使用某个测试框架。

### 20.1 环境划分

- Development
- Production

本地检查
  ↓
单元测试
  ↓
云开发测试环境部署
  ↓

不要通过直接修改生产数据库的方式替代正常发布流程。

- 影响范围。
- 操作前后数据。
- 回滚或恢复方案。
- 执行人及审批人。

## 22. 一期架构验收标准

### 22.1 架构边界

- [ ] 孕期与幼儿业务域独立。
- [ ] 共享能力通过明确接口调用。
- [ ] 页面不直接实现核心业务规则。
- [ ] 日程生成逻辑独立于页面。
- [ ] 安全规则统一执行。
- [ ] 内容、规则和日程版本可追溯。

### 22.2 数据与权限

- [ ] 支持一个用户多个档案。
- [ ] 用户数据按档案隔离。
- [ ] 服务端鉴权有效。
- [ ] 普通用户无法修改内容和规则。
- [ ] 敏感信息访问受控。
- [ ] 关键操作有审计记录。

### 22.3 日程与任务

- [ ] 支持未来 7 天日程。
- [ ] 重复请求不产生重复任务。
- [ ] 日程候选不足时不放宽安全约束。
- [ ] 替换、跳过、顺延符合状态机。
- [ ] 并发操作有冲突检测。
- [ ] 失败任务能够恢复或重试。

### 22.4 安全规则

- [ ] 安全规则中心独立。
- [ ] 安全校验覆盖自动生成和所有用户操作入口。
- [ ] 安全服务异常时停止自动放行。
- [ ] 过敏禁忌能够硬过滤。
- [ ] 食材与食谱安全属性可追溯。
- [ ] 安全档案变化能够触发未来任务重新校验。
- [ ] 未审核规则不能发布。

### 22.5 可维护性

- [ ] 业务规则可独立测试。
- [ ] 规则版本可管理。
- [ ] 内容版本可管理。
- [ ] 云函数职责清晰。
- [ ] 错误码统一。
- [ ] 日志和埋点可追踪。
- [ ] 定时任务可监控。
- [ ] 项目具备基本部署和回滚流程。

## 24. 架构决策记录（ADR）

### ADR-001：采用微信云开发

**决策**：一期采用微信小程序原生框架与微信云开发。

**原因**：

- 降低后端基础设施维护成本。
- 充分利用微信生态能力。
- 适合一期轻量业务规模。
- 减少额外部署和运维复杂度。

### ADR-002：采用模块化单体

**决策**：业务模块在同一后端工程内保持清晰边界，不提前拆分微服务。

**原因**：

- 一期团队规模和业务复杂度尚不足以支撑微服务运维成本。
- 模块化边界能够为后续拆分提供基础。
- 更容易保持业务规则一致性。

### ADR-003：规则引擎采用纯函数模块

**决策**：使用 TypeScript/JavaScript 实现可测试的确定性规则模块。

**原因**：

- 规则行为透明。
- 易于单元测试。
- 不需要额外规则引擎基础设施。
- 适合一期阶段和内容规模。

### ADR-004：安全规则独立

**决策**：Safety Service 是独立业务模块，统一提供安全校验。

**原因**：

- 安全逻辑不能散落在页面和各业务入口。
- 自动生成、替换、顺延和重新生成必须遵循同一套规则。
- 便于审计、测试、版本管理及后续扩展。

### ADR-005：内容与业务规则分离

**决策**：食材和食谱作为内容数据维护，业务约束通过规则配置执行。

**原因**：

- 内容可以独立维护和审核。
- 规则可以独立升级。
- 避免修改一个食谱就需要修改程序逻辑。
- 支持未来增加其他孕期和幼儿阶段。

### ADR-006：历史任务保留版本快照

**决策**：日程任务关联食谱内容版本、规则版本及必要的生成上下文。

**原因**：

- 保留历史推荐依据。
- 支持内容撤回后的影响排查。
- 支持安全规则升级后的重新校验。
- 避免历史记录随当前内容更新而变化。
