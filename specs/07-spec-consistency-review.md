# 07 — Spec Consistency Review

> 文档类型：工程治理规范  
> 适用项目：食刻——孕期与婴幼儿喂养日程助手  
> 审查范围：PRD V1.2、01—06 号项目 Spec  
> 文档状态：Draft  
> 主要用途：指导 AI Agent / Cursor 对项目 Spec 进行跨文档一致性审查

---

## 1. 文档目标

本文件定义项目 Spec 的一致性审查标准、审查流程、问题分级、冲突处理原则和审查报告格式。

目标不是要求所有文档使用完全相同的表达，而是确保：

1. 业务定义一致。
2. 核心数据模型一致。
3. 业务规则与安全规则不存在相互矛盾。
4. 技术架构能够承载已经定义的业务流程。
5. 关键状态、字段、错误码和规则具有统一定义。
6. 文档之间不存在未经说明的重复定义或隐式依赖。
7. 未确认的设计决策不会被 Agent 擅自当作既定事实。
8. Spec 能够作为后续开发、测试和验收的可靠依据。

**核心原则：先识别问题，再判断是否需要修改；不为了追求文档表面统一而改变已经确认的业务决策。**

### 2.1 必须读取的文档

| 文档                         | 主要审查职责                                       |

| PRD V1.2                     | 产品目标、用户范围、核心闭环、产品原则、已确认决策 |
| 01-business-flow.md          | 业务流程、用户操作、状态流转、异常流程             |
| 02-data-model.md             | 实体、字段、关系、约束、数据生命周期               |
| 03-content-spec.md           | 内容结构、食谱体系、审核、版本、发布               |
| 04-schedule-rules.md         | 阶段识别、日程生成、候选筛选、排序、调整           |
| 05-safety-rules.md           | 安全规则、风险等级、拦截机制、审核要求             |
| 06-technical-architecture.md | 技术栈、模块边界、云函数、数据存储、部署和测试     |

如果某个文件不存在：

- 在报告中标记 `MISSING_INPUT`。
- 不得根据文件名推测其具体内容。
- 不得自行补写缺失文档并将其视为已经通过审查。
- 可以继续审查其他可用文档，但必须标注审查覆盖范围。

### 2.2 权威关系

采用以下原则确定设计依据：

1. 已明确确认的产品决策优先于未确认的技术建议。
2. PRD 中已确认的产品目标、范围和决策，是业务定义的上位依据。
3. `01`—`06` 分别负责其领域内的详细定义。
4. 跨领域定义发生冲突时，不能简单按照文件编号决定谁覆盖谁，应先确定冲突涉及的业务归属。
5. 技术架构不能擅自改变产品行为或安全边界。
6. 安全规则不能因为技术实现困难而被降级。
7. 尚未确认的设计方案必须保留为待决策项。

### 2.3 已确认产品决策基线

审查时必须检查以下决策是否得到完整贯彻。

| ID   | 已确认决策                                      | 审查重点                           |
| ---- | ----------------------------------------------- | ---------------------------------- |
| D-01 | 一个账号支持多个孕期/婴幼儿档案，一期 UI 可简化 | 数据模型和业务流程是否支持多档案   |
| D-02 | 每日执行，提前生成未来 7 天日程                 | 日程生成周期、补齐机制和幂等性     |
| D-03 | 一期以单一主要照护者为主，暂不开发复杂家庭协作  | 是否意外引入复杂家庭权限系统       |
| D-04 | 一期采用轻量受控后台，不建设复杂 CMS            | 技术架构是否过度设计               |
| D-05 | 过敏状态记录用户声明及信息来源，不由产品诊断    | 数据字段和业务文案是否越过诊断边界 |
| D-06 | 特殊状况规则由具备相应专业能力的人员审核        | 安全规则审核、发布和追溯机制       |

过敏状态必须区分：

- `none_known`：用户主动声明目前没有已知食物过敏。
- `confirmed_allergy`：用户声明存在已知过敏食物。
- `observing`：正在观察或尝试新食物。
- `skipped`：暂时跳过过敏信息设置。

特别检查：

- `none_known` 不等于医学排除所有过敏。
- `skipped` 不等于没有已知过敏。
- 过敏检测信息不是建档、基础日程和基础辅食功能的强制前置条件。
- 已知过敏食物必须参与所有相关候选过滤。
- 手动替换不能绕过过敏限制。
- 疑似反应后停止该食物自动安排，不自动安排未来重新试吃。
- 过敏信息变更后，必须重新校验尚未执行的日程。

## 3. 审查原则

### 3.1 领域归属原则

每类信息必须有明确的权威定义来源。

| 信息类型           | 权威定义文档 | 其他文档的处理方式         |
| ------------------ | ------------ | -------------------------- |
| 产品目标与用户范围 | PRD          | 引用，不重新定义           |
| 业务流程           | 01           | 其他文档描述实现时保持一致 |
| 数据实体与字段     | 02           | 其他文档引用或声明使用方式 |
| 内容结构与审核     | 03           | 其他文档引用内容能力       |
| 日程生成与调整     | 04           | 其他文档引用日程规则       |
| 安全约束与风险处理 | 05           | 其他文档调用或落实安全约束 |
| 技术实现与系统边界 | 06           | 不得反向改变产品和安全定义 |

如果某项定义需要跨领域共同决定，应在相关文档中明确引用同一个定义，不得各自创造独立版本。

### 3.2 单一事实来源原则

以下内容应避免在多个文档中独立维护：

- 状态枚举。
- 数据字段名称及类型。
- 错误码。
- 日程任务状态。
- 规则优先级。
- 安全校验结果结构。
- 内容审核状态。
- 版本关联方式。
- 业务时间和日期计算口径。

如果多个文档必须提及同一概念：

- 只有一个文档负责完整定义。
- 其他文档注明引用来源。
- 如有领域特有的扩展字段，应明确标记为扩展，而不是另建一套定义。

### 3.3 安全优先原则

任何一致性修复都不能降低已经确认的安全要求。

以下要求必须保持：

1. L0 安全硬拦截优先于其他规则。
2. 安全校验失败或异常时不得默认放行（Fail Closed）。
3. 自动生成、手动替换、顺延、重生成均必须经过安全校验。
4. 已知过敏食物必须强制过滤。
5. 安全规则必须支持审核、发布、版本管理和审计。
6. 候选不足时允许返回不足，不得放宽安全条件强行凑数。

### 3.4 最小修改原则

发现问题后：

- 优先修正定义不一致的源头。
- 优先修正少量明确冲突的字段或规则。
- 不得以一致性审查为理由重写全部 Spec。
- 不得擅自增加一期产品范围。
- 不得为了统一技术风格而替换现有技术选型。
- 不得删除仍然有效的业务约束。

## 4. 一致性审查维度

### 4.1 产品目标与业务流程一致性

检查内容：

- PRD 的核心闭环是否在业务流程中完整体现。
- 孕期和婴幼儿是否存在清晰的业务域区分。
- 多档案能力是否得到支持。
- 档案创建、阶段识别、日程生成、任务执行和反馈是否能够形成完整闭环。
- 跳过、未完成、延期等状态是否具有明确业务含义。
- 一期范围是否被技术文档或其他 Spec 无意扩大。

重点检查：

| 检查项   | 预期结果                   |
| -------- | -------------------------- |
| 档案归属 | 日程和任务明确归属具体档案 |
| 阶段识别 | 阶段依据和生效时间明确     |
| 日程生成 | 能够关联对应档案及生成周期 |
| 任务执行 | 支持完成、跳过等合法行为   |
| 弹性调整 | 不破坏安全约束             |
| 行为反馈 | 不产生惩罚性育儿 KPI       |
| 多档案   | 不发生跨档案数据污染       |

### 4.2 数据模型一致性

以 `02-data-model.md` 为唯一数据结构定义基准。

检查：

- 03—06 中提到的实体是否已经在 02 中定义。
- 同名实体是否存在不同字段定义。
- 字段类型、可空性、默认值是否一致。
- 主键、外键或逻辑关联是否一致。
- 一对多、多对多关系是否明确。
- 枚举值是否统一。
- 删除、撤回、失效和历史保留策略是否一致。
- 是否存在没有明确归属的集合或字段。

重点关注以下实体：

- User
- Profile
- PregnancyProfile
- ChildProfile
- FoodItem
- Recipe
- RecipeIngredient
- StageTemplate
- ScheduleSlot
- ConstraintRule
- RecipeCandidate
- ScheduleInstance
- ScheduleTask
- UserSafetyProfile
- AllergyRestriction
- FoodObservation
- SafetyRule
- SafetyRuleVersion
- TaskOperationLog
- ScheduleGenerationLog
- AuditLog

上述名称仅作为审查线索，最终以 `02-data-model.md` 实际定义为准。不得因为本表列出了某个名称，就直接认定它必须成为独立数据库集合。

**特别检查：**

06 中建议的 `recipe_versions`、`idempotency_records`、`background_jobs` 等集合，必须与 02 的实体定义进行核对。

如果确实需要新增：

1. 说明业务用途。
2. 说明与现有实体的关系。
3. 判断是否需要独立集合。
4. 明确数据生命周期。
5. 更新 02。
6. 同步更新引用该数据结构的文档。

不能仅因为技术架构建议了一个集合，就直接将其认定为已批准的数据模型。

### 4.3 内容体系一致性

以 `03-content-spec.md` 为内容定义基准。

检查：

- FoodItem 与 Recipe 的关系是否明确。
- 食谱是否通过结构化食材明细关联食物。
- 食谱适用阶段是否明确。
- 内容审核状态是否统一。
- 内容版本是否可追溯。
- 未审核内容是否可能进入生产候选池。
- 食谱撤回后是否影响未来未执行日程。
- 孕期和婴幼儿内容是否分别经过适用性审核。
- 营养数据缺失时是否避免精确营养匹配。
- AI 生成内容是否默认作为草稿处理。

三层内容体系必须保持：

1. 营养结构层。
2. 标准食谱层（食物交换份）。
3. 场景适配层。

不得将三层内容结构混淆为三个互相独立的食谱数据库。

### 4.4 日程规则一致性

以 `04-schedule-rules.md` 为日程生成和调整规则基准。

检查：

- 阶段识别是否使用统一的档案数据。
- 日程槽位是否与内容适用阶段一致。
- 候选查询、过滤、匹配和排序的先后顺序是否一致。
- 安全过滤是否先于普通偏好排序。
- 候选不足时的返回策略是否一致。
- 未来 7 天日程是否按档案生成。
- 日程补齐是否具备幂等能力。
- 是否保护已完成、已跳过和用户主动替换的任务。
- 顺延、重生成和手动替换是否重新进行安全校验。
- 日程任务是否关联具体内容版本、规则版本。

日程生成流程应能与安全规则及技术架构相互映射。

参考流程：

读取档案 → 阶段识别 → 槽位生成 → 查询候选 → 阶段过滤 → 安全过滤 → 营养匹配 → 个性化排序 → 完整性校验 → 写入日程任务。

如果实际 `04` 已定义了不同的合理流程，不应仅凭参考流程直接判定冲突；必须检查其安全约束、业务结果和执行顺序是否满足已确认要求。

### 4.5 安全规则一致性

以 `05-safety-rules.md` 为安全规则基准。

检查：

- 安全规则优先级是否统一。
- 安全校验是否覆盖所有入口。
- 过敏状态是否统一。
- 过敏限制是否不可绕过。
- 疑似反应后的处理是否一致。
- 严重反应是否有紧急求助提示。
- 安全规则版本是否可追溯。
- 安全校验失败是否 Fail Closed。
- 特殊状况是否要求专业审核。
- 内部风险分级是否被错误表述为医学诊断或官方临床标准。

安全优先级：

`L0 安全硬拦截 > L1 阶段规则 > L2 营养结构规则 > L3 个性化规则`

以下情况必须判定为高优先级问题：

- 手动操作可以绕过 L0。
- 安全服务异常时仍继续生成日程。
- 已知过敏食物进入推荐结果。
- 疑似过敏反应后自动安排再次试吃。
- 未审核的特殊状况规则直接发布生效。

### 4.6 技术架构一致性

以 `06-technical-architecture.md` 为技术实现基准，但技术方案不得覆盖业务和安全定义。

检查：

- 技术栈是否符合已经确定的微信小程序原生框架和微信云开发方向。
- 是否采用适合一期规模的模块化单体。
- 孕期和婴幼儿业务域是否保持合理边界。
- 核心业务数据是否由可信服务端控制写入。
- 档案归属是否经过服务端校验。
- Safety Service 是否是生产安全判断的统一入口。
- 规则引擎是否与业务逻辑保持合理解耦。
- 定时任务是否支持幂等、重试和失败恢复。
- 数据版本是否可以追溯。
- 技术架构是否引入超出一期范围的复杂系统。

**必须进行能力验证，不得直接假设：**

- 微信云数据库事务和条件更新能力。
- 云函数运行时和执行时长限制。
- 定时触发器执行可靠性。
- 云函数之间的调用和共享代码方式。
- 共享 TypeScript/JavaScript package 的构建与运行方式。
- 数据查询、索引和批处理限制。
- 并发生成时的幂等与冲突处理。

无法从 Spec 得到依据的内容应标记为 `NEEDS_TECH_VALIDATION`，而不是直接写成已验证结论。

## 6. 状态、字段和接口契约检查

### 6.1 枚举检查

重点收集并对照：

- Profile 类型。
- 档案阶段。
- 过敏状态。
- 食物观察状态。
- 内容审核状态。
- 日程状态。
- 任务状态。
- 安全风险等级。
- 安全校验结果。
- 任务操作类型。
- 内容版本状态。

检查规则：

1. 同一个业务状态只能有一套权威枚举。
2. 相同名称不能表达不同业务含义。
3. 不同名称不能在没有说明的情况下表达同一业务含义。
4. 终态和可流转状态必须明确。
5. 非法状态迁移必须有处理规则。

### 6.2 字段检查

对跨文档引用的字段，核对：

| 检查项   | 说明                           |
| -------- | ------------------------------ |
| 字段名称 | 命名一致                       |
| 数据类型 | 不存在隐式类型差异             |
| 是否必填 | 必填与可选定义一致             |
| 默认值   | 不存在冲突                     |
| 枚举范围 | 使用统一定义                   |
| 数据来源 | 明确由用户、系统或专业审核产生 |
| 更新时间 | 明确修改规则                   |
| 版本信息 | 明确关联对象                   |
| 隐私等级 | 不违反数据最小化原则           |

### 6.3 接口与错误码检查

如果不同文档描述了云函数、服务接口或模块调用，应检查：

- 入参字段是否一致。
- 返回结构是否一致。
- 成功与失败语义是否明确。
- 错误码是否统一。
- 幂等键是否一致。
- 超时和重试是否会产生重复任务。
- 安全异常是否可能被当作普通业务失败处理。
- 调用方是否能够区分候选不足、安全拦截和系统异常。

建议统一检查以下概念：

- `SafetyCheckResult`
- `ScheduleGenerationResult`
- `ScheduleTask`
- `ContentVersion`
- `RuleVersion`
- `IdempotencyKey`

这些名称是审查对象，不代表其字段结构已经确定。具体定义必须以对应领域 Spec 为准。

## 7. 问题分级

审查发现的问题必须分级。

### P0 — Critical

影响安全、数据完整性或核心业务正确性。

示例：

- 已知过敏食物进入日程。
- 手动替换绕过安全规则。
- 安全校验失败时默认放行。
- 多档案之间发生数据串用。
- 日程生成覆盖已完成任务。

处理要求：

- 阻止进入开发或发布验收。
- 必须修复或明确阻断相关功能。
- 修复后重新审查关联文档。

### P1 — High

造成跨文档核心定义冲突，可能导致开发结果不一致。

示例：

- 同一任务状态在不同 Spec 中定义不同。
- 数据模型和技术架构使用不同字段结构。
- 内容版本关联方式不一致。
- 日程生成规则与实际业务流程冲突。

处理要求：

- 开发前修复。
- 明确权威定义。
- 同步更新引用文档。

### P2 — Medium

不一定立即造成系统错误，但影响实现、维护或测试。

示例：

- 字段缺少来源说明。
- 错误码未定义。
- 重试策略不明确。
- 历史数据保留策略不明确。
- 缺少部分异常流程。

处理要求：

- 记录责任文档。
- 在对应功能开发前处理。
- 可以在不影响其他功能的情况下分批修复。

### P3 — Low

文档表达、组织或可读性问题。

示例：

- 名词不统一。
- 说明重复。
- 表格格式不一致。
- 引用路径错误。

处理要求：

- 可以集中清理。
- 不得以文档优化为由改变业务含义。

### 问题分级原则

如果同一个问题同时满足多个级别，按最高级别处理。

不能因为问题只发生在文档中，就将安全定义错误降级为 P2 或 P3。

## 8. 问题类型分类

每个问题除优先级外，还应标记问题类型。

| 类型       | 标记                   | 说明                             |
| ---------- | ---------------------- | -------------------------------- |
| 定义冲突   | CONFLICT               | 两份或多份文档对同一概念存在矛盾 |
| 定义缺失   | MISSING_DEFINITION     | 必需定义没有明确来源             |
| 重复定义   | DUPLICATE_DEFINITION   | 多份文档独立定义同一事实         |
| 引用错误   | BROKEN_REFERENCE       | 引用文件、字段或规则不存在       |
| 实现不可行 | IMPLEMENTATION_RISK    | 技术方案可能无法实现             |
| 安全缺陷   | SAFETY_GAP             | 安全约束不完整或可能绕过         |
| 业务遗漏   | BUSINESS_GAP           | 核心流程或异常流程缺失           |
| 待技术验证 | NEEDS_TECH_VALIDATION  | 需要通过实际平台能力验证         |
| 待产品决策 | NEEDS_PRODUCT_DECISION | 当前信息不足以确定唯一方案       |
| 合理差异   | ACCEPTABLE_VARIANCE    | 不同领域有合理差异，不构成冲突   |

## 9. 审查执行流程

### Step 1：建立审查上下文

Agent 必须：

1. 检查项目目录。
2. 确认 PRD V1.2 实际文件位置。
3. 确认 01—06 文件是否存在。
4. 记录文档版本、状态和更新时间。
5. 读取全部可用文档。
6. 建立输入文档清单。

不能假设文件路径、字段和内容与预期一致。

输出：

`review-input-inventory.md`

### Step 2：提取各文档权威定义

逐份提取：

- 核心概念。
- 实体和字段。
- 状态枚举。
- 业务规则。
- 安全规则。
- 接口和返回结构。
- 版本管理要求。
- 未决策事项。

建立统一的定义索引。

输出：

`review-definition-index.md`

### Step 3：执行单文档内部审查

分别检查每份文档：

- 定义是否完整。
- 前后是否矛盾。
- 是否存在未经说明的假设。
- 是否引用不存在的概念。
- 是否有未明确的异常路径。
- 是否将建议误写为已确认决策。

注意：单文档内部正确，不代表跨文档一致。

### Step 4：执行跨文档审查

按照第 5 章矩阵逐项核对。

每个检查项必须有：

- 涉及文档。
- 实际定义。
- 差异说明。
- 问题类型。
- 严重程度。
- 证据位置。
- 建议处理方式。

不能只根据文档标题或目录结构判断一致性。

### Step 5：执行安全专项审查

单独检查：

1. 过敏状态和过敏限制。
2. 食物观察和疑似反应。
3. 安全规则优先级。
4. 手动替换、顺延和重生成。
5. 安全校验异常。
6. 内容审核与发布。
7. 特殊状况专业审核。
8. 历史日程版本追溯。

安全专项审查不能被普通一致性检查替代。

### Step 6：生成审查报告

输出：

`07-spec-consistency-review-report.md`

报告至少包括：

- 输入文件清单。
- 审查覆盖范围。
- 总体结论。
- 跨文档矩阵。
- 问题清单。
- P0/P1/P2/P3 数量。
- 待决策事项。
- 待技术验证事项。
- 建议修复顺序。
- 是否具备进入开发的条件。

### Step 7：修复与复审

修复必须遵循：

1. 先确定问题的权威定义来源。
2. 明确本次允许修改的文档。
3. 先修复源头定义。
4. 再同步修复受影响文档。
5. 不修改无关内容。
6. 不覆盖用户已有修改。
7. 修复后重新运行受影响的检查项。
8. 保留修复前后的差异记录。

如果发现问题需要修改已确认的产品决策，必须暂停并提交产品决策，不得由 Agent 自行决定。

- 核心跨文档检查项已完成。
- 不存在未处理的 P0。

- 核心状态、字段、规则和版本定义一致。
- 安全约束没有被弱化。
- 已确认产品决策没有被擅自修改。
- 未验证技术能力已明确标记。
- 未决策事项已登记并明确责任人。

### 11.2 部分通过

以下情况可以标记为 `PARTIAL`：

- 非核心文档缺失。
- 部分 P2 不影响当前开发范围。
- 部分技术能力需要实际环境验证。
- 部分产品决策尚未确认，但已经明确隔离，不影响当前开发。

必须说明不能通过的具体范围。

### 11.3 不通过

以下情况必须标记为 `FAIL`：

- 存在未解决的 P0。
- 存在影响当前开发的 P1。
- 关键数据定义互相冲突。
- 核心业务流程无法闭环。
- 安全规则存在绕过路径。
- 关键技术假设被当作已验证事实。

**通过一致性审查不等于通过医学、营养学或产品安全专业审核。**

## 12. Agent 执行约束

执行审查的 Agent 必须遵守：

### 12.1 禁止行为

- 不得根据文件名推测文档内容。
- 不得虚构字段、状态、接口或测试结果。
- 不得将建议方案写成已确认决策。
- 不得擅自修改 PRD 已确认决策。
- 不得擅自改变安全规则。
- 不得为追求统一而大规模重写文档。
- 不得删除仍有效的业务约束。
- 不得将技术推测当作平台能力验证结果。
- 不得将内部风险等级描述为官方医学标准。
- 不得在没有依据时宣称审查通过。

### 12.2 输出约束

审查阶段默认只输出报告，不直接修改 01—06。

只有在用户明确批准修复后，才可以修改对应文档。

修复时必须：

- 明确修改文件。
- 明确修改原因。
- 明确修改范围。
- 保留无关内容。
- 提供修改摘要。
- 提供复审结果。

### 12.3 审查证据要求

每个 FAIL 或 PARTIAL 项必须提供：

- 文件路径。
- 章节标题。
- 相关字段或规则。
- 必要的原文摘录或精确定位。
- 判断理由。

没有证据的内容只能列为待验证或待决策，不得作为确定冲突。

## 13. 建议的后续工程治理

建议将一致性审查作为后续每个开发阶段的固定检查项。

| 阶段              | 审查内容                          |
| ----------------- | --------------------------------- |
| Spec 定稿前       | 完整跨文档一致性审查              |
| 数据模型实现前    | 02 与 03—06 的实体和字段核对      |
| 日程引擎实现前    | 04 与 05 的规则执行顺序核对       |
| 安全模块实现前    | 05 与 06 的安全接口及异常处理核对 |
| 每个 Phase 完成后 | 实现与 Spec 一致性审查            |
| 版本发布前        | 业务、安全、数据和技术验收        |

建议后续逐步建设：

1. Spec Consistency Review Skill：负责跨文档审查。
2. Data Model Consistency Skill：负责数据模型和字段核对。
3. Safety Rules Review Skill：负责安全规则专项检查。
4. Implementation Consistency Review Skill：负责代码与 Spec 的一致性检查。

这些 Skill 应共享统一的审查分级、证据要求和报告格式，避免每个 Skill 独立发明一套审查标准。
